Spring Data JPA 和 JPA

Spring 中的 JPA 和 Hibernate 有什么区别？Spring Data JPA 能不能脱离 Hibernate 用？

名称 负责什么 典型内容
JPA / Jakarta Persistence 定义对象关系映射和持久化行为的标准 @Entity、EntityManager、JPQL、Criteria API
Hibernate ORM 实现规范，生成 SQL，管理实体状态 Session、脏检查、代理、批处理；另有 Hibernate 扩展
Spring Data JPA 在 JPA 上封装数据访问接口 JpaRepository、方法名派生、分页、Specification

JPA 是 Java 官方定义的 ORM 规范，只定义了接口和注解，不提供实现，Spring Data JPA 是 Spring 对 JPA 的再封装，不是 JPA 实现，底层默认用 Hibernate；

Hibernate 是 JPA 规范的一个具体实现，是真正负责把 Java 对象和数据库表之间做映射、执行 SQL。而 Hibernate 的一个依赖就是 JDBC

而且 Spring Data JPA 能脱离 Hibernate 使用，因为 Spring Data JPA 是一个抽象层，支持任何符合 JPA 规范的实现框架，但是更换通常注意其中的特有实现的内容。

JPA 和 Hibernate 的”全自动 ORM”到底全自动在哪？代价是什么？

首先，JPA 是 Java 的持久化规范，Hibernate 是它的一种主流实现。所谓全自动 ORM，是框架能够根据实体映射关系，自动完成对象和关系型数据之间的转换，以及大部分常规的 SQL 生成和持久化操作。

全自动主要体现在

  1. 对象关系映射的自动化

    发者通过注解等定义实体、表、字段和关联关系，Hibernate 就可以自动完成查询结果到 Java 对象的映射，以及对象状态向数据库记录的转换。

  2. SQL 生成和执行的自动化

    对于常规的 CRUD，开发者可以直接操作实体对象，而不需要手动编写 SQL。Hibernate 会根据映射元数据、实体状态和持久化操作，生成并执行相应的 SQL。

  3. 实体生命周期管理的自动化

    Hibernate 通过持久化上下文管理实体状态，支持一级缓存、脏检查和自动 Flush。

代价是也很明显

  1. 性能和 SQL 可控性问题

    Hibernate 生成的 SQL 不一定适合复杂查询场景，尤其需要关注懒加载引发的 N+1 查询、关联对象加载以及不必要的数据查询。

  2. 隐式行为带来的理解和排查成本

  3. 对象模型和关系模型之间的差异

所以在技术选型上，如果是领域模型比较清晰、实体关系比较稳定、常规 CRUD 较多的业务系统，JPA/Hibernate 能提高开发效率；但如果是复杂报表、多表聚合、需要精细优化 SQL 的场景，我更倾向使用 MyBatis 或原生 SQL。

选择标准是：固定简单条件用 find 方法名派生方法，固定复杂结构用 JPQL，动态组合条件用 Criteria/Specification，数据库特有能力用原生 SQL。

方式 适合场景 注意点
findBy... 方法名派生 按业务键查询、少量条件、存在性判断 条件多时名字难维护，难表达复杂括号逻辑
@Query + JPQL 固定关联、聚合统计、DTO 查询 写实体和属性名，字符串重构需验证
Criteria API / Specification 管理后台可选筛选项、动态 AND/OR Java 代码较长；字符串路径仍可能拼错
@Query(nativeQuery = true) 窗口函数、数据库 JSON 运算、特定 SQL 方言绑定，复杂分页通常显式写 countQuery

第一种是方法名派生查询。

  • Spring Data JPA 会解析 Repository 方法名，方法名由主题和条件组成，根据关键字生成查询。

第二种是通过 @Query 编写 JPQL。

  • JPQL 是面向实体的查询语言，操作的是实体类和实体属性，而不是直接操作数据库表和字段。它支持 JOIN、聚合、子查询、DTO 投影等能力，比较适合多表关联、统计和复杂但结构固定的业务查询。它的可读性和查询结构控制能力通常优于复杂的方法名派生。

第三证是 Criteria API。

  • 它使用 Java API，以编程方式构建查询，支持动态拼装 Predicate（查询条件）、JOIN、排序、分组等查询组成部分。在 Spring Data JPA 中，一般会配合 JpaSpecificationExecutor 和 Specification 使用，来对 Criteria 条件进行封装和组合，适合后台管理系统中多条件可选、动态筛选和高级检索场景。

第四种是原生 SQL

  • 当查询涉及复杂报表、窗口函数、数据库特有函数或执行计划精细优化时，可以使用 @Query(nativeQuery = true)，直接控制 SQL

JPQL 和 Criteria API 都是 JPA 标准查询机制，最终通常都由 Hibernate 等 JPA Provider 转换成数据库 SQL。

通过 JPQL 和 Criteria 优化复杂查询，有如下好处

  1. 对于动态查询，显然不应该为了适配不同条件组合，去定义大量 Repository 方法，应该使用 Specification 实现动态过滤

  2. 精确控制 JOIN 和关联加载，方法名查询在复杂 JOIN 下既不清晰，也在懒加载条件下就可能发生 N+1 查询

    方法名派生查询也可以搭配 @EntityGraph 控制关联加载，并不是只能靠 JPQL 才能解决 N+1。

  3. JPQL 可以直接执行 DTO 投影，减少不必要的数据加载

  4. 灵活构建分组、聚合和子查询

  5. 避免不必要的查询条件，Criteria 可以只拼接必要条件

所以说，方法名派生的优势在于简单查询的声明效率，但它的查询条件和逻辑组合主要依赖方法名解析。随着查询条件增多，会出现方法名过长、条件组合不灵活、复杂括号逻辑难以表达等问题。

另外，当查询需要多表 JOIN、聚合统计、子查询、复杂 DTO 投影或者动态查询结构时，方法名派生的表达能力就不够理想。

这个时候，如果查询结构固定，我会使用 JPQL，让查询语义更加清晰；如果查询条件是动态组合的，我会使用 Criteria API 或 Specification 来封装和组合查询条件。

四种主键生成策略 AUTO / IDENTITY / SEQUENCE / TABLE 你项目里用哪个？为什么？你都是如何选择主键的？@SequenceGenerator 的 name 和 sequenceName 有什么区别？

策略 原理 主要取舍
AUTO自动 让 JPA 根据数据库方言自己去猜 便捷，但升级和换库时实际策略可能变化
IDENTITY自增 数据库 INSERT 时生成自增主键，无法配合批量插入 MySQL 常见；通常限制 Hibernate 实体 INSERT 的 JDBC 批处理
SEQUENCE序列 先从序列取得 ID，再 INSERT，它能支持批量插入 PostgreSQL 常见；可预分配 ID，利于批处理
TABLE表模拟 专用表保存并分配 ID，不依赖数据库特性 可移植，但分配表有竞争和额外访问成本

@SequenceGenerator 的 name 与 sequenceName是两个不同层面的名字

  • name 是 JPA 元数据中的生成器逻辑名，供 @GeneratedValue 中通过 generator 引用；
  • sequenceName 才是数据库序列名。allocationSize 影响 ID 段分配，使用 pooled 优化器时要与序列的步长配置匹配；不能只改注解而不管已有序列。分配导致 ID 有空洞是正常现象，主键不承诺连续。

allocationSize在默认情况下，每次要生成一个 ID，应用都要发一条 SELECT nextval(...) 到数据库。高并发下，这条往返本身就是瓶颈。Hibernate 提供了 pooled 优化器（@GenericGenerator 或 @SequenceGenerator 配合 optimizer = "pooled"），它的思路是，一次向数据库要一批 ID，缓存在应用内存里，用完了再去要下一批。allocationSize = 50 就是“一批要 50 个”。

它涉及到一个与数据库序列步长的匹配的问题

  • 如果数据库序列的 INCREMENT BY 是 1，而 allocationSize 是 50，Hibernate 的 pooled 算法会按自己的逻辑跳跃取值。在单实例下通常没问题，但多实例部署或与其它系统共用同一个序列时，就可能产生冲突或大量浪费。

  • 更稳妥的做法是让 序列的 INCREMENT BY 与 allocationSize 保持一致（比如都设为 50），这样每个应用实例拿到的 ID 段天然不重叠。

选择时会看数据库能力、批量写入需求、跨服务标识、排序和索引成本。MySQL 单库的话，如果是普通 CRUD 较多一般选择自增，因为 MySQL 习惯自增；PostgreSQL/Oracle 这种有原生序列，SEQUENCE 更自然；跨服务生成业务 ID 的场景就需要用分布式 ID 的方案

实体类为什么必须有或最好有无参构造器？

按 JPA 3.1 的可移植要求，实体需要 public 或 protected 无参构造器，供 Provider 实例化；业务构造器可以另外提供

JPA Provider 在从数据库加载数据时，必须先实例化实体对象，再往字段里填值。 它不知道你的业务构造器需要什么参数，所以需要一个空壳构造器来创建对象。

当执行 SELECT 加载实体时，Hibernate 的流程大致是：

  • 通过无参构造器创建实体实例（此时所有字段都是默认值）。
  • 通过反射或 setter 把结果集的列值填入字段。
  • 返回填充完毕的对象。

如果没有无参构造器，Hibernate 会尝试用字节码增强或其他方式绕过，但这并不优雅。

一般用 protected 的好处是，业务代码不能 new ResearchProject()，必须走有参构造器，这种在 DDD 下是需要的

spring.jpa.open-in-view 默认是 true，你怎么看？关掉之后要注意什么？

Spring Boot 把 open-in-view 默认设为 true，是一个便利性优先的设计选择。它把 EntityManager 的可用范围延伸到 Web 请求处理阶段，而且将 Hibernate Session 生命周期延长到整个 HTTP 请求周期，以支持事务结束后仍有机会懒加载关联。延长的是持久化上下文的生命周期，不是把数据库事务自动延长到整个请求。

好处是页面渲染方便；代价是 Controller、Jackson 序列化时也可能触发 SQL，N+1 难发现，事务外查询可能不共享前面业务读取的一致性边界。因此在当前以 REST API 为主流的架构下，这个默认值带来的代价往往大于收益。通常关掉

  • 让问题尽早暴露，而不是隐藏

    OSIV 开启时，懒加载可以在 Controller 返回后、Jackson 序列化阶段“偷偷”执行 SQL。N+1 问题不会报错。关闭 OSIV 后，事务边界外的懒加载会立即抛出 LazyInitializationException，强迫你在 Service 层就把数据加载完整。

  • 连接占用时间更可预测

    EntityManager 保持打开意味着它在整个请求期间可能随时从连接池借用连接，直到请求结束才释放。对于 SSE 长连接等场景，如果 OSIV 开启，HTTP 连接不关闭，数据库连接也可能被持续占用，最终耗尽连接池。关闭后，连接在事务提交时就归还，占用时间与事务时长绑定，而不是与请求时长绑定。

  • 事务一致性边界更清晰

    OSIV 开启时，序列化阶段触发的查询处于事务之外，可能读到与业务逻辑读取时不一致的数据版本。关闭后，所有数据加载都在明确的 @Transactional 边界内完成，一致性边界清晰

关掉之后要注意

  • 关联字段是否在返回后才访问：检查 DTO 映射和序列化过程中，是否有字段依赖懒加载。如果有，必须在 Service 事务内加载完，或改用 DTO 投影。
  • 列表查询是否需要 fetch join / EntityGraph：OSIV 关闭后，列表接口如果逐个访问懒加载关联，会直接抛异常或产生大量查询。需要用 JOIN FETCH、@EntityGraph 或批量查询在事务内一次性加载。
  • 异步任务是否带出了实体代理：如果 @Async 方法或 CompletableFuture 在事务外访问实体代理，会失败。异步边界内应传入已加载的 DTO 或 ID，而不是实体引用。
  • 序列化是否递归遍历双向关系：Jackson 序列化双向关系时，OSIV 开启可能掩盖了循环引用问题

不能为消除 LazyInitializationException 就把所有关系改 FetchType.EAGER ，这会换来另一类加载和性能问题。

save()、persist()、merge()、saveOrUpdate() 有什么区别？为什么我 save() 一条新对象，日志里先出现一条 SELECT？

首先需要区分，save() 通常指 Spring Data JPA 的 JpaRepository.save()，而persist() 和 merge() 是 JPA EntityManager 的标准方法，而 saveOrUpdate() 是 Hibernate 原生 Session 的历史 API，在 Hibernate 6 中已经被弃用。另外，Hibernate 原生 Session.save()和 Spring Data JPA 的 Repository.save()也不是同一个方法。

Spring Data JPA 的 save() 本身并不是直接执行 INSERT 或 UPDATE，而是通过实体判新机制判断当前实体是否为新实体。

Spring Data JPA 默认采用以下顺序判断

  • 实现 Persistable，就委托实体的 isNew()
  • 存在 @Version，版本为 null 认为是新实体
  • 检查 @Id，ID 为 null 认为是新实体；基本数值类型的零值有特殊判定

如果是新实体，就调用 EntityManager.persist()，将瞬时对象变成托管对象；如果判断为已有实体，就调用 EntityManager.merge()，将传入对象的状态合并到持久化上下文中的受管理的托管实体，一般是将对象状态复制到托管实体

persist() 和 merge() 最大的区别是对象身份。persist() 会使传入的新实体成为托管对象，而 merge() 通常不会让传入的游离对象变成托管对象，它会返回一个托管实例，因此后续应该使用 merge() 的返回值。

至于为什么 save() 一个新对象会先出现 SELECT，常见原因是实体提前分配了非空主键，例如雪花 ID、UUID 或手动赋值的 Long ID。如果这个实体还没有可用于判新的包装类型 @Version 字段，通常会根据 ID 是否为 null 判断实体是不是新的。非空 ID 可能使它误判为已有实体，于是调用 merge()。

如果该实体在持久化上下文中不存在，Hibernate 可能查询数据库，以判断对应记录是否存在，然后根据实体映射、主键策略及版本决定插入、更新或者抛出异常。

Hibernate 6.6 开始，如果能够明确判断对象是游离实体（例如使用生成式主键或非基本类型版本字段），merge 时发现数据库没有对应行，会抛出乐观锁异常，而不再一律退化为 INSERT

解决这个问题可以考虑实现 Persistable<ID>，显式控制 isNew()，或者使用包装类型 @Version 辅助判新。

不过需要注意，并不是所有 SELECT 都由 merge 造成。例如 SEQUENCE 主键可能先执行获取序列值的 SQL。关联对象需要加载，生命周期回调或业务逻辑查询，唯一性检查，这种都有可能引起这种情况

findById()、getById()、getOne()、getReferenceById() 有什么区别？

findById 是获取实体状态；getReferenceById 是获取可代表该身份的引用。旧的 getOne/getById 已废弃，现代代码优先使用 getReferenceById。

  • findById()代表老老实实去数据库查，调用时会立即发出 SQL，从数据库加载完整实体，返回 Optional<T>。实体不存在时返回 Optional.empty()，由调用方显式处理 没找到 的情况。
  • getReferenceById()只给一个代理，不立刻查，调用时通常不发出 SQL，返回的是一个代理对象。只有当你访问该实体的非 ID 字段时，才会触发真正的数据库查询。如果实体不存在，异常往往在访问字段或提交事务时才抛出，而不是调用方法时立即抛出。

getReferenceById() 返回的代理必须在事务范围内使用。如果把它带出事务边界，后续访问字段会触发 LazyInitializationException。

getById() 和 getOne()历史上语义混乱

  • getOne()：早期 JPA API 中的名字，行为就是 getReferenceById。
  • getById()：在 Spring Data JPA 2.7 之前，它的实际实现是调用 EntityManager.getReference()，行为等同于 getReferenceById()，不会立即查库。但从 2.7 开始，getById() 被标记为 @Deprecated，文档建议直接使用 getReferenceById()

JPQL 里执行 update/delete 为什么必须加 @Modifying？你了解 @Modifying的具体行为吗？为什么 SQL 执行了内存里的对象却没变？

Spring Data JPA 对 @Query 标注的方法有一个默认假设，它是一条 SELECT 查询，用来读取数据，而不是修改数据。

当你写的 JPQL 实际是 update 或 delete 时，如果不加 @Modifying，底层调用的就是 getResultList() 或 getSingleResult() 这类只读 API，结果就是运行时报错

所以 @Modifying 的本质是一个显式声明，这个语句是修改语句，请改用 executeUpdate() 来执行。

除此之外，它还有两个可选的开关属性：

  • flushAutomatically：执行修改语句前，先强制把持久化上下文里攒着的变更刷到数据库。不加的话，你之前在事务里改过但还没 flush 的实体，可能不会被这条批量语句“看到”。
  • clearAutomatically：执行修改语句后，清空整个持久化上下文。这是解决“内存对象不变”问题的关键开关。

为什么 SQL 执行了内存里的对象却没变？

这个是 JPA 一级缓存（持久化上下文）的设计使然。当你用 findById() 加载了一个实体，这个对象就进入了当前事务的持久化上下文，被 JPA 管理着。之后你执行 @Query 的 update/delete，它会直接绕过持久化上下文，以原生 SQL 的形式打到数据库上。这样数据库里的行确实变了，但持久化上下文并不知道，它缓存的还是那个旧对象。

delete 执行后，你再用 findById() 查同一个 ID，JPA 会直接从一级缓存返回那个已经被删除的对象，看起来就像“删了但没删掉”。update 执行后，你从一级缓存拿到的还是旧值，因为你没有重新从数据库加载。

解决办法是 @Modifying(clearAutomatically = true)，修改语句执行完后，清空持久化上下文。这样下一次 findById() 因为没有缓存可用，会真正去数据库查，拿到最新状态。

CascadeType 都有哪些？orphanRemoval 和 CascadeType.REMOVE 有什么区别？

CascadeType 定义的是父实体上的某个操作，是否要传播到关联的子实体，有如下六个

取值 传播的操作 典型场景
PERSIST 保存父实体时，一并保存子实体 新建订单时连带保存订单项
MERGE 合并父实体时，一并合并子实体 更新父实体时同步子实体状态
REMOVE 删除父实体时，一并删除子实体 删除订单时连带删除订单项
REFRESH 刷新父实体时，一并刷新子实体 较少用
DETACH 父实体脱离持久化上下文时，子实体也脱离 较少用
ALL 以上全部 父子生命周期完全绑定

CascadeType 只影响操作是否传播，不决定数据库层面。 真正决定能否删掉子实体的，数据库层面的内容和删除顺序。

orphanRemoval 和 CascadeType.REMOVE 的区别在于触发删除的时机和语义。

  • CascadeType.REMOVE：父删子跟着删

  • orphanRemoval = true：子被抛弃，就删

其实吧，orphanRemoval = true 实际上隐含了 CascadeType.REMOVE 的效果，删除父实体时，子实体也会被删。所以如果你设置了 orphanRemoval = true，通常不需要再额外加 CascadeType.REMOVE。

@Embedded/@Embeddable 用在哪？@Embeddable + @ElementCollection 有什么区别？

一般这对注解解决的是值对象如何映射到同一张表的问题。

@Embeddable 标注在一个类上，声明这个类是一个“可嵌入的值对象”，它自身没有独立的主键，不是一个实体

@Embedded 标注在实体类的字段上，表示这个字段是一个嵌入的值对象，它的属性会被映射到当前实体所在的表的列中

  • 如果多个实体嵌入同一个值对象、列名冲突，可以用 @AttributeOverride 覆盖列名。

如果实体里有一个值对象，就使用@Embeddable + @Embedded的注解组合，值对象的字段平铺进实体表

如果实体里有一组值对象，那么就使用@Embeddable + @ElementCollection的注解组合，把一组值对象放进独立的集合表

示例如下

表结构：是两张表。

user 表：

id name
1 张三

user_address 表（集合表）：

user_id province city street
1 河北省 石家庄市 XX路
1 北京市 北京市 YY路
1 上海市 上海市 ZZ路

每个 Address 是集合表里的一行，通过 user_id 外键关联回 user。

对于@Embedded，一条 SQL 就拿到全部数据，因为值对象字段就在实体表里。没有 N+1 问题。

对于@ElementCollection，默认是两条 SQL。加载 User 时，addresses 是懒加载的，访问时才发第二条。如果有多个 User，就会产生 N+1，你虽然可以优化掉 N+1，但是本质上它就是比 @Embedded 多了一次关联

JPA 实体为什么要小心重写 equals/hashCode？如何重写他们才能保证不出问题？

Java 的 equals/hashCode 契约假设对象身份稳定，而 JPA 实体的身份在生命周期中是变化的。

一个 JPA 实体在生命周期中，字段的状态会经历三个阶段，以 id 为例子

阶段 id 状态 说明
新建（transient） null 刚 new 出来，还没保存
持久化（persistent） 有值 已保存，id 由数据库/生成器分配
游离（detached） 有值 已从持久化上下文分离

如果 equals/hashCode 基于 id，那么新建时 id 为 null，hashCode 返回一个值，保存后 id 又被赋值了，hashCode 返回值就变了。这就违反了 Java 契约。

Object 的默认实现是基于对象内存地址的，同一个数据库行，两次查询可能返回两个不同的 Java 对象，而且这可能涉及到持久化上下文是否缓存的问题，必须重写

一般是基于业务键重写，业务键是实体的自然唯一标识，如身份证号、订单号、用户名。它在实体创建时就确定且唯一的，不依赖数据库生成。

用 instanceof 还是 getClass()

instanceof允许子类与父类相等。但 Hibernate 代理是子类，用 instanceof 能让代理与真实对象相等。getClass()严格同类型才相等。代理情况下大部分会失效。

一般用 instanceof

这个也就是为什么不要直接用 @Data的原因，Lombok 的 @Data 会基于所有字段生成 equals/hashCode

JPA 多表关联的相关注解了解吗？他们是如何实现关联的？双向关联里谁是维护方？为什么必须在一端配 mappedBy？

JPA 用四个注解表达实体间的关联基数：

注解 语义 外键位置
@ManyToOne 多对一 多的一方持有外键
@OneToMany 一对多 多的一方持有外键（一的一方用 mappedBy 指向）
@OneToOne 一对一 任意一方持有外键，由 @JoinColumn 决定
@ManyToMany 多对多 需要中间表，由 @JoinTable 定义

双向关联里，持有外键或中间表定义的一方作为维护方，它的变更会同步到数据库。而反向方用 mappedBy 指向维护方，它的变更不会同步到数据库。外键在哪张表，哪端就是维护方。mappedBy 永远配在 没有外键 的那端。

关联类型 维护方 反向方
@ManyToOne / @OneToMany @ManyToOne 端（持有外键） @OneToMany 端（配 mappedBy）
@OneToOne 配 @JoinColumn 的一端 配 mappedBy 的一端
@ManyToMany 配 @JoinTable 的一端 配 mappedBy 的一端

为什么必须在一端配 mappedBy？如果双向关联两端都配 @JoinColumn，JPA 会认为这是两个独立的单向关联，而不是一个双向关联。结果是生成了两个外键列或者中间表，行为不一致了

Sort 和 Pageable 一起用的时候，是 SQL 排序还是内存排序？

Sort 和 Pageable 一起用时，排序是在数据库（SQL）层面执行的，不是内存排序。

Spring Data JPA 会把 Pageable 中的分页信息（LIMIT / OFFSET）和排序信息（ORDER BY）都翻译成 SQL，交给数据库执行。Sort 参数本身就是 Pageable 接口的一部分。

很明显，如果排序在内存里做，分页就错了，数据库先按物理顺序返回 LIMIT 20 OFFSET 0 的 20 条，你再在内存里排序，得到的只是这 20 条内部的有序，而不是全表排序后的前 20 条。真正的分页排序必须由数据库在 ORDER BY 后配合 LIMIT/OFFSET 完成。

用 Pageable 做排序时，建议在排序条件末尾加一个唯一字段，比如 Sort.by("name").and(Sort.by("id"))。否则当 name 有重复值时，数据库对相同排序键的行返回顺序可能不稳定，翻页时会出现记录重复或丢失。

为什么用 JPA 时能不用实体查询就不用？我们都写 DTO 进行查询结果的封装。投影（Projection）和 DTO 查询怎么写？

实体受持久化上下文管理，而 DTO 不受管理

查询实体时，Hibernate 需要将结果放入一级缓存并执行脏检查，以追踪对象状态变化。对于只读查询而言，这完全是额外开销。选择 DTO 查询可以直接规避这些成本，同时减少不必要的数据传输。

主要有三种写法

  • 基于接口的投影

    定义一个接口，其 getter 方法名与实体属性名精确匹配，这样 Spring Data 能在运行时自动生成代理实现

  • 基于类的投影

    定义一个普通的 Java 类或 record，作为查询返回类型。与接口投影不同，DTO 不涉及代理，且不能嵌套投影

    Spring Data 会自动将查询结果映射到该 DTO。对于 record，字段顺序需与查询选择顺序一致；对于普通类，需要一个全参构造器。

  • JPQL 中显式使用 DTO

    在 @Query 中通过构造函数表达式 new 来实例化 DTO，适用于自定义连表查询等场景

saveAll() 是批量插入吗？saveAll() 为什么常常还是一条一条 INSERT，甚至每条前面还多一个 SELECT？

saveAll() 不自动等于批量插入，它只是一个在应用层代表批量插入的语义表达，底层仍然逐条遍历实体去执行 persist 或 merge。默认情况下，逐条 INSERT 甚至每条前面多一个 SELECT 都是正常现象。

根源在于 Spring Data JPA 的 save() 方法，它先判断实体是不是新的，再决定用 persist（纯插入）还是 merge（先查再决定插入或更新）。

当实体被判定为已存在时，save() 会调用 merge，而 merge 需要先从数据库查出当前状态才能合并，于是就有了 SELECT + INSERT或 SELECT + UPDATE。

那什么时候会被误判为已存在

  • 主键已手动赋值，且没有 @Verson 字段
  • 使用了复合主键
  • 实体是从数据库外（比如接口）拿到的，它们处于游离态，JPA 无法确定其是否已存在，只能先查。

即使 saveAll() 逐条执行，Hibernate 也可以把它们攒起来一次性发。但 JDBC 批量默认是关闭的，需要手动开启：

开启后，Hibernate 才会把多个 INSERT 合并成一次网络往返

如果主键是 数据库自增或者序列生成，saveAll() 的实体在保存前 ID 为 null，isNew() 返回 true，会走 persist，不会有多余 SELECT，配上 batch_size 就能真正批量插入。

用 @Version 做乐观锁，它是怎么实现的？失败时你怎么处理？@Version 支持哪些类型？时间戳可以吗？@Version 乐观锁有哪些失效场景？乐观锁冲突了怎么重试才安全？

@Version 是 JPA 规范定义的乐观锁实现方式。它的核心机制是，读时记录版本，写时校验版本，如果版本不匹配就说明数据在读取后被修改过，从而抛出异常

当你在实体中声明一个 @Version 字段后

  • 更新时：在生成的 UPDATE 语句中，WHERE 条件会额外带上版本号（如 WHERE id = ? AND version = ?），同时把版本号加一。
  • 冲突检测：如果另一个事务在此期间已经修改了这条记录，版本号已经变了，那么 WHERE 条件就无法匹配到任何行。数据库返回“影响行数为 0”

冲突意味着你基于旧数据做出的修改已经失效了。一般是接入重试和快速失败，最简单的方式是捕获异常。

根据 JPA 规范，@Version 支持以下类型：

  • int / Integer
  • short / Short
  • long / Long
  • java.sql.Timestamp

时间戳（Timestamp）是可以的，但是几乎不用。因为时间戳的精度可能成为问题，同一毫秒内的并发更新可能无法区分，而数值型版本号（如 int/Long）更简单、更可靠。

@Version 的失效场景如下

  • 长事务/分离实体场景下手动覆盖版本

    当你把实体从数据库读取后，经过序列化传输到前端，用户编辑提交后再反序列化回来，JPA 管理的实体已经被脱离了持久化上下文。此时如果你手动给这个脱离实体的 version 字段赋值，JPA 并不会用你设置的值去比较，它依然使用读取时的原始版本。

    对于长事务，仅在实体上标注 @Version 是不够的，在更新前还需要手动比较版本。如果直接从客户端传来的版本值覆盖实体字段，乐观锁会失效 。

  • 关联修改不会自动增加父实体版本

    这是双向关联的经典陷阱。当子实体被修改时，父实体的版本号默认不会变化。只有单向关联且外键在父端时，父版本才会增加 。

  • 原生 SQL 更新绕过 JPA

乐观锁冲突了，安全重试需要三个步骤

  • 重新读取最新状态
  • 重新应用业务变更
  • 限制重试次数

如果重试的操作涉及外部副作用，还需要保证幂等，这时候一般是用业务唯一键 + 乐观锁版本号双重保障。业务唯一键负责同一个业务意图的多次表达是一致的，乐观锁负责在并发下只有一个执行者。

悲观锁怎么写？@Lock注解代表什么？@Lock(PESSIMISTIC_WRITE) 背后的 SQL 是什么？@Lock 加了但没生效，可能是什么原因？

悲观锁是在读取时就要求数据库锁住相关数据，使冲突写入等待或失败；锁通常持有到事务结束。悲观锁的写法很简单，在 Repository 的查询方法上加 @Lock(LockModeType.PESSIMISTIC_WRITE)。

MySQL/PostgreSQL 的典型 SQL 是 SELECT ... FOR UPDATE。FOR UPDATE 让数据库在读取这一行时直接加上排他行锁。其他事务如果想对这同一行执行 FOR UPDATE 或 UPDATE，就会被阻塞，直到当前事务结束。

调用这个方法的 Service 方法必须开启事务，因为锁的生命周期跟随事务，事务一结束，锁自动释放。

@Lock 只有一个作用，告诉 JPA 执行这条查询时，使用指定的 LockModeType。

@Lock 加了但没生效

  • @Transactional 没生效，这个一般就是动态代理失效了，典型就是自调用

  • 数据库的 MVCC 让“读”被绕过：在 PostgreSQL 这类支持 MVCC 的数据库里，即使你加了 FOR UPDATE 锁住了行，普通的 SELECT不带 FOR UPDATE仍然可以读到旧版本快照，不会被阻塞。这是正常行为。

    真正的验证方式是：两个线程都执行 FOR UPDATE，或者一个执行 FOR UPDATE、另一个执行 UPDATE，这时候才能看到阻塞。

  • 锁的不是同一行：@Lock 只对查询结果命中的行加锁。如果你的查询条件返回了多行，或者两个事务锁的不是同一行，自然不会有冲突。

JPA 审计 (JPA Auditing) 是怎么做的？@CreatedDate/@LastModifiedDate/@CreatedBy 靠什么生效？Auditing 和你们用 AOP + 自定义注解做的操作审计框架有什么区别？为什么不用同一个方案？

JPA 审计就是实体层的自动填充一些字段。在实体持久化（persist）或更新（update）时，自动给实体的特定字段填上时间戳或操作人。

要让 @CreatedDate 这类注解生效，需要三个条件

  • 实体上声明监听器和注解：在实体类上加 @EntityListeners(AuditingEntityListener.class)，然后在字段上标注 @CreatedDate、@LastModifiedDate、@CreatedBy 等

    AuditingEntityListener 是 Spring Data JPA 提供的 JPA EntityListener。当 Hibernate 在 flush 阶段触发 @PrePersist 或 @PreUpdate 回调时，这个监听器就会介入，读取当前时间或从 AuditorAware 获取操作人，然后通过反射写入实体字段。

  • 配置类启用审计：在 Spring 配置类上添加 @EnableJpaAuditing。

  • 提供操作人来源：如果用了 @CreatedBy，必须实现 AuditorAware<T> 接口，告诉框架“当前操作人是谁”。

Auditing 和用 AOP + 自定义注解做的操作审计框架是两个不同层面的东西，解决的问题不一样

  • JPA 审计管的是实体字段的自动填充。它只关心这条记录是谁在什么时候创建的/修改的，结果写回实体自身的字段上。处理的是数据库层面上的变更
  • AOP + 自定义注解的操作审计框架，一般倾向于业务动作的记录，然后把这些信息写入独立的审计日志表或日志系统，处理的是用户的动作

因此，目标不同，强行合一会让两边都做不好。

多数据源下 JPA 的配置核心在于：每个数据源需要一套独立的 DataSource、EntityManagerFactory、TransactionManager，并且要通过包路径或显式引用将它们绑定起来，避免 Spring 在自动装配时混淆

一个 @Transactional 能管理两个数据库吗？不能，多个TransactionManager 分别管理不同的资源事务，即使一个业务方法使用了两个数据库，指定一个 JpaTransactionManager 也只能保证它所管理的那套本地事务。两个独立数据库之间不具有天然的原子性。此时如果需要一致性就需要分布式事务

EntityManagerFactory 负责创建 EntityManager 实例，用于管理和操作数据库实体。那么，多数据源也不一定等于多个 EntityManagerFactory，例如一个系统采用 MySQL 主从架构：写操作走主库。读操作走从库。主从数据库具有相同的实体模型。这种场景可以利用 AbstractRoutingDataSource，根据路由键动态选择实际连接。这时候只需要一套 EntityManagerFactory 就够了

Hibernate 支持哪几种多租户隔离方式？Hibernate 6 的 @TenantId 是怎么工作的？有什么盲区？多租户下唯一索引、序列和二级缓存要注意什么？

Hibernate 的多租户隔离主要有三种策略

  • Database（独立数据库）：每个租户拥有完全独立的数据库。
  • Schema（独立 Schema）：共享数据库实例，但每个租户使用独立的 Schema（在 MySQL 中通常对应独立的 Database）。
  • Discriminator（共享 Schema + 租户列）：所有租户的数据存在同一张表里，通过一个 tenant_id 列来区分

@TenantId的工作机制是，Hibernate 会在实体第一次被持久化（persist）时，自动将当前会话（Session）绑定的租户标识符填入该字段，然后操作数据时 Hibernate 会自动在 SQL 的 WHERE 子句中加上 tenant_id = ? 的条件，实现数据过滤。

神秘小知识，如果 @TenantId 字段同时也被标注为 @Id，那么 tenant_id 就会成为复合主键的一部分

@TenantId 的租户过滤在 UPDATE 和 DELETE 语句中默认是不生效的

但是如果此时，将 tenant_id 加入复合主键（使用 @IdClass 或 @EmbeddedId），这样 Hibernate 生成的 WHERE 条件自然会包含它。

多租户下唯一索引的问题经常会不符合预期，在共享 Schema 模式下，全局唯一索引很可能失效。比如，你希望 email 字段全局唯一，但在多租户下，正确的做法通常是 (tenant_id, email) 组成复合唯一索引，这样能允许不同租户使用相同的邮箱。

而需略也会有问题，因为数据库序列通常是全局的，不会自动按租户隔离。

多租户场景下，二级缓存必须启用租户感知。好消息是，Hibernate 的二级缓存天然支持多租户，因为缓存 Key 中包含了租户标识符，因此不同租户的相同实体 ID 不会冲突。但如果你自定义缓存实现，比如集成了 Spring Cache 接入了 Redis，需要显式使用 TENANT_* 标记的缓存管理器，确保缓存命名空间按租户隔离，否则可能串数据。

事务管理

你怎么理解 Spring 事务？@Transactional 的失效场景有哪些？事务同步回调和事务事件怎么用？长事务怎么治理？

这道题一般会连着问，从用法问到失效，再问到事务和业务的边界怎么划，最后问到 NESTED 到底能不能用。

事务是怎么生效的？

@Transactional只是声明。工作的是 Spring AOP 代理 + TransactionInterceptor 拦截器 + PlatformTransactionManager 事务管理器三者的配合：

  1. 容器启动时，AbstractAutoProxyCreator 在 postProcessAfterInitialization 阶段发现 Bean 上有 @Transactional，就为它创建代理（有接口用 JDK 动态代理，否则用 CGLIB），这也是为什么只有走代理的调用才会被拦截；
  2. TransactionAttributeSource 解析注解得出一份事务属性（传播行为、隔离级别、回滚规则、超时、只读），只有真正的写方法才会开启事务，只读方法在 readOnly=true 时是优化而非不开启；
  3. 调用时，TransactionInterceptor 先通过事务管理器拿到或新建事务，把连接绑到当前线程（TransactionSynchronizationManager 的 ThreadLocal）；
  4. 目标方法执行完，由拦截器决定提交还是回滚。

失效场景

按照”为什么不生效”的根因分成四类，

第一类：调用没走代理

场景 原因 解决
自调用：同一个类里 A 方法调 B 方法，B 上有 @Transactional this 指向原始对象，不是代理对象，调用没经过拦截器 拆到另一个 Bean；自注入 @Autowired private XxxService self; 再 self.B()；AopContext.currentProxy()（需 @EnableAspectJAutoProxy(exposeProxy=true)）；或者把事务方法下沉到独立的 Service
Bean 没被 Spring 管理 直接 new 出来的对象，或者没加 @Component/@Service 注册 交给容器管理，通过注入获取实例

自调用是所有 AOP 增强注解的通用陷阱：@Async、@Cacheable、@Validated 的自调用一样失效，区别只是”失效”的表现不同——@Transactional 表现为不回滚，@Async 表现为变成同步，@Cacheable 表现为每次都查库。

第二类：代理没法拦截这个方法

场景 原因 解决
private 方法 代理无法拦截私有方法 改成 public
final 方法 / final 类 CGLIB 靠继承生成子类，无法覆写 final 去掉 final
static 方法 静态方法属于类，不属于 Bean 实例 改成实例方法
protected 方法 JDK 代理只能拦接口方法；CGLIB 能拦 public/protected，但 Spring 的规则是只有 public 才生效 改成 public

Spring Boot 2.x 起 spring.aop.proxy-target-class 默认是 true，也就是默认走 CGLIB，所以”类没有实现接口”这件事本身不是失效原因，这一点很多人答错。

第三类：异常没触发回滚

场景 原因 解决
rollbackFor 配错或没配 默认只对 RuntimeException 和 Error 回滚，受检异常不回滚 明确写 @Transactional(rollbackFor = Exception.class)，业务异常继承 RuntimeException
异常被 catch 吞掉 提交/回滚发生在方法返回之后，方法正常返回 → 提交 要么 throw 出去，要么在 catch 里 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
异常被包装成别的类型 包装成了受检异常，或者包装后不再匹配 rollbackFor 统一异常体系，或者 rollbackFor 用父类
方法返回前就 return 了 逻辑分支提前返回，写操作在返回之后 检查代码路径，确保事务内的写操作都在同一个方法里完成

第四类：上下文不对

场景 原因 解决
多线程里：事务内 new Thread(...) 或丢线程池 事务是绑定在当前线程的，子线程拿到的是另一个连接，看不到未提交数据，子线程异常也不会让主线程回滚 全程单线程；必须异步的用 @TransactionalEventListener(AFTER_COMMIT) + @Async
@Transactional 与 @Async 同方法 异步执行在新线程，事务上下文不会传递，等于没有事务 拆成两个方法，先提交事务再异步
多数据源用错事务管理器 @Transactional 默认用容器里 @Primary 的那个管理器，操作非主库时事务不生效（自动提交） 显式指定 @Transactional(transactionManager = "xxxTransactionManager")
接口上的 @Transactional JDK 代理下注解在接口上不一定被代理类”继承” 规范做法是写实现类的 public 方法上

TransactionSynchronization 与 @TransactionalEventListener 是什么关系？

这一块是事务回调

先说 TransactionSynchronization：每个事务都对应一个同步器集合，由 TransactionSynchronizationManager 维护（同样存在 ThreadLocal 里）。实现这个接口，就能在事务的生命周期上挂回调，顺序是：

回调方法 执行时机 典型用途
suspend() / resume() 事务被挂起 / 恢复时（比如内层用了 REQUIRES_NEW） 上下文的保存与还原
beforeCommit(status) 提交之前，此时回滚仍然有效 补充校验、最终一致性检查
beforeCompletion() 提交/回滚前最后一步 资源清理，别在这里写库
afterCommit() 已提交之后 清缓存、发消息、发通知
afterCompletion(status) 无论提交还是回滚都执行 清理 ThreadLocal、释放自定义资源、记录结果

注册方式有两种写法：

@TransactionalEventListener 底层就是 TransactionSynchronization，Spring 提供了一个 TransactionSynchronizationEventAdapter（本质是一个 TransactionSynchronization 实现），在对应的回调里把事件发布出去。所以说：

  • @TransactionalEventListener 是”事务同步器 + 事件机制”的封装，它让我们不必在每个业务方法里手写 registerSynchronization，只要在事务提交前后发布一个事件就行，业务代码更干净；
  • 手动 TransactionSynchronization 的优势是”就在当前方法里、不需要额外定义事件类”，适合一次性、跟当前方法强绑定的收尾逻辑。

再补充几个参数：

  • phase：BEFORE_COMMIT（默认值是排在后面的 AFTER_COMMIT，注意默认是 AFTER_COMMIT）、AFTER_COMMIT、AFTER_ROLLBACK、AFTER_COMPLETION；
  • fallbackExecution = false（默认）：没有活跃事务时监听器不执行。这就是为什么有的同学写了监听器却发现”没有事务时逻辑丢了”——要么给调用的地方加事务，要么显式设成 true；
  • @Async 可以叠加使用，让回调在独立线程里跑，但要注意它拿不到原事务，也不能指望它回滚；
  • AFTER_COMMIT 里不能再写库：此时事务已结束，新写库是自动提交、没有事务保护，如果需要落库，应单独开一个 REQUIRES_NEW 事务，或者落成补偿任务。

为什么值得花力气用它？ 因为它解决的是”事务内不能干的事”：发邮件、发 MQ、清缓存、调第三方。这些动作如果放在事务里，一旦后续回滚，副作用已经发生了，收不回来。用 AFTER_COMMIT 把它们挪到”确定提交之后”，才能保证”业务真的发生了，副作用才发生”。

长事务怎么治理？

长事务的危害是连锁的：连接被占住 → 连接池耗尽 → 其他请求全排队 → 服务雪崩；同时锁持有时间长会让别的会话锁等待甚至死锁，还会让 undo log / binlog 膨胀、主从延迟变大。所以说长事务不是慢一点的问题，而是要主动治理的对象。

1. 只读事务 readOnly = true

它有两个作用：一是给数据库一个明确的信号，MySQL 下可以省去 undo log 的写入、优化查询计划；二是给 Hibernate/JPA 一个信号，把 FlushMode 设为 MANUAL，避免脏检查触发无意义的 UPDATE。

注意两个坑：一是设了 readOnly = true 之后执行增删改可能直接报错（MySQL 会拒绝，或者乐观锁失效），所以纯查询方法才加；二是 readOnly 不会传播给内层，内层如果自己是写事务，要按自己的语义声明。

2. 事务内不要做 RPC、不要循环里逐个写

这是长事务最常见的成因。@Transactional 方法里调第三方接口（微信、短信、外部 API），网络 I/O 可能几秒钟，这几秒里数据库连接一直是占着的。治理方式是”事务边界和工作边界对齐”：

  • 先把本地状态落库（比如记为 pending）并提交事务；
  • 提交后再去同步或异步调外部接口；
  • 回调/重试里再用新事务更新最终状态。

循环里逐个 insert 同理，应该改成批量操作（foreach 批量插入）或者分批提交；如果确实数据量大，就分批 + 幂等 + 断点续跑，别指望一个事务吞下十万条。

3. 给事务设超时

别让慢操作无限期拖住连接，@Transactional(timeout = 3) 让超时直接抛出 TransactionTimedOutException，把问题暴露在代码层而不是连接池层。

4. REQUIRES_NEW 与连接池大小的关系

关键在于：REQUIRES_NEW 是”挂起外层 + 开一个全新的独立事务”，它需要从连接池里再拿一条连接，而外层那条连接并不会释放。

后果是：一次请求就可能占用 2 条甚至更多连接。如果并发 100、每条链路嵌套两层，就要 200 条连接；而 maximum-pool-size 假设只有 20，就会出现”外层全部占用连接、等着内层拿连接，内层又拿不到”的连接池死锁，典型表现是 connection-timeout 超时异常。

所以结论是：REQUIRES_NEW 要当”稀缺资源”用——常见于”审计日志/操作记录必须独立提交”、“失败重试要开新事务不受外层回滚影响”这类场景。用的时候要同步评估连接池大小：线程池并发数 + 嵌套层数，配合 HikariCP 的 maximumPoolSize 和 connectionTimeout 一起算，并监控活跃连接数。

5. 分清 REQUIRES_NEW 和 NESTED

REQUIRES_NEW NESTED
底层机制 挂起外层事务，新建一个独立事务 外层事务内的 savepoint（保存点）
连接 需要另拿一条连接 复用同一条连接
内层回滚的影响 只影响自己，外层不受影响但双方提交时机独立 只回滚到 savepoint，外层可以继续提交
外层回滚的影响 内层已提交则无法回滚，数据会残留 外层回滚时，内层的修改一起回滚
是否原子 不原子 整体仍然是一个事务，可保证原子性

一句话选择标准：“内层的失败不能拖累外层，且内层要真的提交”→ REQUIRES_NEW；“内层失败只回滚自己这一小段，整体还要保持一致”→ NESTED。

NESTED 的实现依赖什么？

NESTED 的本质是数据库的 savepoint，而 savepoint 是连接级别的能力，所以要求两个条件同时成立：

  • 事务管理器要支持 savepoint：DataSourceTransactionManager / JdbcTransactionManager 是支持的（isNestedTransactionAllowed() 为 true）；
  • 底层 JDBC 驱动和数据库要支持：MySQL、PostgreSQL 都支持 savepoint。

所以各个组合的结论是：

组合 NESTED 支持情况
MyBatis + DataSourceTransactionManager ✅ 支持最直接，就是 connection.setSavepoint() 的原生能力
JDBC JdbcTemplate + JdbcTransactionManager ✅ 支持
JPA/Hibernate + JpaTransactionManager 需要确认：它委托给底层的 JdbcTransactionManager，理论上有 savepoint 能力，但要和 Hibernate 的 FlushMode、Session 生命周期配合。坑在于”回滚到 savepoint 之后，Hibernate 一级缓存里可能还留着已回滚的实体状态”，容易出现”数据库回滚了但内存里的对象还以为是脏的”这种不一致。所以我一般不在 JPA 场景用 NESTED，用 REQUIRES_NEW 或者干脆拆事务更稳

还有三个容易踩的细节：

  1. 没有外层事务时，NESTED 会退化成 REQUIRED，也就是自己开一个新事务，此时就没有 savepoint 可言了；

  2. 内层要正确声明回滚：内层方法上也要写 rollbackFor，否则受检异常一样不回滚，savepoint 也就不会触发；

  3. 外层必须”消化”内层的异常：因为内层回滚后异常还会向上抛，如果不 catch，外层也会连带整体回滚——那就失去了”内层失败不影响外层”的意义。

实战里我是怎么划事务边界的

  1. 事务方法必须是 public、必须有明确的 rollbackFor，这是底线规范；
  2. 查询用 readOnly = true，写操作才开事务，别让只读接口占用写事务的资源；
  3. 事务内不调第三方、不发消息、不写缓存，这些统统通过 @TransactionalEventListener(AFTER_COMMIT) 挪到提交之后；
  4. 事务粒度尽量小：能在一个方法里几步写完就写完，别跨方法拼装一个巨大的逻辑事务；
  5. REQUIRES_NEW 和 NESTED 按需用，并且评估连接池，别在循环里开新事务；
  6. 跨库/跨服务的一致性不要靠 @Transactional 硬扛，用本地消息表、补偿任务或者分布式事务框架。

REQUIRES_NEW 在 JPA 场景有什么额外代价？为什么 NESTED 在 JPA 里要慎用？

REQUIRES_NEW 的核心行为是挂起当前事务，开启一个全新且独立的事务。但是会带来如下代价

  • 持久化上下文分裂。一般情况下，一个事务对应一个 EntityManager 和一个一级缓存。REQUIRES_NEW 挂起外层事务时，外层的持久化上下文也被挂起。新事务拥有自己的 EntityManager 和全新的持久化上下文。这意味着，外层事务中已加载的实体，在内层事务里不可见；内层事务提交后，外层事务的持久化上下文不知道这些变更。
  • 连接占用翻倍。外层事务持有自己的数据库连接，内层新事务需要从连接池再借一条连接。如果外层事务本身持有悲观锁或长时间运行，内层事务又去竞争同一批数据，极易引发死锁。
  • 数据可见性问题。内层事务看不到外层事务未提交的变更。

那么，REQUIRES_NEW 的唯一合理用途是审计日志，因为无论外层业务成功还是失败，日志都必须落库。

IBM 的开发者文档明确建议：除非有类似审计这样的理由，否则应始终使用 REQUIRED 或 MANDATORY，而不是 REQUIRES_NEW。

NESTED 事务是在已有事务中创建的嵌套子事务，但是实际上，Spring Data JPA + Hibernate 下 JpaTransactionManager 不支持真正的嵌套事务。而 Savepoint 回滚的是 JDBC 连接层面的操作，但 Hibernate 的 EntityManager 和一级缓存感知不到 Savepoint 的回滚。这会导致数据不一致

@Transactional(readOnly = true) 对 Hibernate 做了什么？能随便加吗？

主要是把当前 Session 的默认只读属性设为 true，并禁止自动 flush

Spring 的 JpaTransactionManager 在开启事务时，如果检测到 readOnly = true，会调用 Hibernate 的 session.setDefaultReadOnly(true)，并将 FlushMode 设为 MANUAL来禁止自动 flush

带来的直接后果是

  • 关闭脏检查：Hibernate 不再为加载进 Session 的实体维护一份加载时快照，也不做脏检查对比，也省下了不少内存
  • 修改不持久化：即便你在代码里改了实体的字段，因为没有脏检查，也没有自动 flush，这些修改不会被同步到数据库。

不能随便加

  • 它不阻止你写数据库。真正会报错的是数据库连接层面的 Connection.setReadOnly(true)。如果你的数据库驱动和连接池支持这个设置，那么写操作会被数据库拒绝；如果不支持，这个设置就被静默忽略了。因此，会带来行为不确定的后果。
  • 在服务层滥用它可能加剧连接占用。 Spring Data 的 Repository 方法（如 findAll）默认已经带了 readOnly = true，连接在查询返回后就释放了。但如果你在服务层方法上加 @Transactional(readOnly = true)，连接会被持有到整个服务方法结束。

因此，它需要精确地加在那些纯粹只读、不包含任何写操作的服务方法上。

@Transactional 和持久层的关系是什么？为什么 JPA 的懒加载依赖事务？MyBatis 的 SqlSession 又依赖什么？

@Transactional 是 Spring 提供的事务管理抽象，它本身不直接属于任何持久层框架，而是通过 AOP 来方法调用前后控制数据库事务的边界。持久层框架则负责在事务边界内执行具体的数据库操作。

JPA 懒加载依赖事务，本质上就是依赖持久化上下文EntityManager。持久化上下文通常由 EntityManager 管理，负责跟踪实体状态并保证懒加载代理能按需查询数据库。

当你在事务方法内访问一个未被初始化的懒加载属性时，Hibernate 需要利用当前仍然存活的持久化上下文去数据库补发查询。如果事务已结束，EntityManager 随之关闭，实体变为游离态，懒加载代理就失去了查询能力

而在 Spring 中，@Transactional 方法执行期间会绑定一个事务同步的 EntityManager 到当前线程。方法一旦返回，事务提交，该 EntityManager 就被关闭。Spring Boot 默认开启的 OpenEntityManagerInView 配置也只不过是把EntityManager 的关闭延迟到视图渲染之后了，这个依赖的本质没有改变。

MyBatis 的 SqlSession 直接依赖 JDBC 来进行数据库连接和事务管理器。SqlSession 本身是 MyBatis 执行 SQL、获取映射器的门面，它内部持有一个 Executor，而 Executor 在执行语句时需要通过事务管理器获取 JDBC Connection。

与 JPA 通过 EntityManager 间接关联事务不同，MyBatis 的 SqlSession 与事务的绑定关系更直白

  • 非 Spring 环境：SqlSession 需要手动从 SqlSessionFactory 打开，并在使用后关闭。提交或回滚由 SqlSession 自身的方法控制。
  • Spring 环境：SqlSessionTemplate 会确保 SqlSession 与 Spring 的 @Transactional 同步。当 @Transactional 方法执行时，MyBatis 使用的 SqlSession会参与到 Spring 管理的 JDBC 事务中，这时事务提交或回滚由 Spring 统一指挥。

同一个事务里 find 两次同一个 ID，是同一个对象吗？同一事务里 save 之后再查同一实体，查到的是新值吗？在事务里修改了一个实体，但不调用 save，提交时会更新吗？save 返回的对象和我传进去的对象，是同一个吗？

是的，在同一个事务，确切地说是同一个持久化上下文里，find 两次同一个 ID 会返回同一个 Java 对象实例。save 之后再查同一实体，查到的是新值，因为查询会命中持久化上下文里那个已被修改的托管对象，而不是重新去数据库捞旧数据。

JPA 的持久化上下文，也就是在 Hibernate 中的一级缓存，会保证，在一个 EntityManager 的生命周期内，同一个数据库行只对应一个 Java 对象实例。第一次 find 从数据库加载后，这个对象就被纳入了持久化上下文；第二次 find 相同 ID 时，JPA 直接返回上下文中已有的那个引用，不再发起 SQL 查询。

你在事务内任何地方拿到的同一个实体，修改它，其他引用也能立刻看到变化。这也就是为什么是一致性

save改变的是内存中那个托管对象的状态。随后你再查询同一实体时，JPA 会优先从持久化上下文里取对象。因为那个对象已经被你改过了，所以返回的自然就是新值。

如果数据库被绕过 JPA 的外部手段修改了，事务内再次 find 同一 ID，拿到的就是旧值了，因为持久化上下文不会自动感知外部变化，它只信自己缓存的那份对象。

在事务里修改了一个实体，但不调用 save，提交时会更新。因为只要实体处于托管状态，Hibernate 的脏检查机制会在 flush 时比对快照，自动生成 UPDATE 语句。save 不是必须的。

save 返回的对象和我传进去的对象不一定是同一个，如果实体是新建的，save 走 persist，通常返回传入的实例。如果实体是已经存在的，save 走 merge，返回的就是持久化上下文中的托管副本。所以官方建议始终使用 save 的返回值进行后续操作

为什么 GenerationType.IDENTITY 会让 Hibernate 批量插入彻底失效？你怎么解决？Hibernate 6 里 @GeneratedValue(strategy = AUTO) 的行为变了，你了解吗？

GenerationType.IDENTITY 让 Hibernate 批量插入失效，根本原因在于主键生成时机与 JDBC 批处理的冲突

IDENTITY 要求每条 INSERT 立即执行以拿回数据库生成的自增 ID，而 JDBC 批处理的前提是把多条 INSERT 攒起来一起发。所以说批处理会退化成一条条发。即使你配置了 hibernate.jdbc.batch_size，只要实体使用 IDENTITY，Hibernate 也会主动关闭该实体的 INSERT 批处理。

解决方法如下

  • 改用 SEQUENCE 策略
  • 应用层生成 ID
  • 直接用 JDBC 批量插入

Hibernate 6 移除了 hibernate.id.new_generator_mappings 属性，GenerationType.AUTO 的语义变得更加“倾向于序列”。

在 Hibernate 5 时代，AUTO 的行为受该属性影响：设为 false 时，部分数据库（如 HSQLDB）会走 IDENTITY；设为 true 或默认情况下走序列。Hibernate 6 统一了方向：AUTO 会优先选择序列风格的生成器，只要当前数据库方言支持序列。

详细说说实体的四种状态，以及它们之间怎么转换？persist() 和 merge() 的区别是什么？游离对象修改后，怎样更新到数据库？

在 JPA/Hibernate 中，实体通常有四种状态：瞬时态（Transient）、持久态（Persistent/Managed）、游离态（Detached） 和 移除态（Removed）。它们之间的转换由 EntityManager的操作以及事务边界决定。

  • 瞬时态

    通过 new 创建，尚未与持久化上下文关联。没有 ID，数据库中没有对应记录。对它的修改不会被数据库感知。

  • 持久态

    对象已被纳入持久化上下文管理。拥有 ID，并且与数据库中的记录对应。对持久态对象的修改会被 Hibernate 的脏检查追踪，在事务提交或 flush 时自动同步到数据库

  • 游离态

    对象曾经处于持久态，但持久化上下文已经关闭或对象被显式移出。它仍然拥有 ID，数据库里也可能还有对应记录，但不再受管理。对它的修改不会被自动同步。

  • 移除态

    对象与持久化上下文关联，但已被标记为删除。在 flush 或事务提交时，数据库中对应的记录会被删除。此后该对象不应再被使用。

状态之间的转换

  • 瞬时 → 持久：调用 persist()或 Hibernate 的 save()。对象被纳入持久化上下文，通常会在 flush 时生成 INSERT。
  • 持久 → 游离：事务提交/持久化上下文关闭，或显式调用 detach() / evict() / clear()。对象脱离管理，但数据还在。
  • 游离 → 持久：调用 merge()。注意merge() 不会把你传入的游离对象本身变成持久态，而是返回一个受管理的副本，后续操作应使用返回的对象。
  • 持久 → 移除：调用 remove()或 Hibernate 的 delete()。对象被标记为删除，flush 时执行 DELETE。

persist() 用于瞬时对象，将其纳入持久化上下文管理，merge() 用于游离对象，返回值为受管理的副本，原对象仍保持游离。对已存在 ID 的对象误用 persist() 可能抛异常。

游离对象修改后，在事务内调用 merge() 合并回持久化上下文，或直接用 JPQL/原生 SQL 的 UPDATE 语句。

什么是持久化上下文（Persistence Context）？EntityManager 是线程安全的吗？

持久化上下文是一组受管理的实体实例的集合。

它保证同一数据库行在同一个上下文里只对应一个 Java 对象，并维护该对象在加载时的快照，用于脏检查。

这个上下文有生命周期边界。事务开始，上下文创建或加入；事务结束，上下文关闭，其中所有实体变为游离态。

EntityManager 不是线程安全的，代理也不是。EntityManagerFactory 是线程安全的、可共享的工厂；但 EntityManager 本身代表一个数据库连接/事务的边界，不能并发操作。

Spring 的事务管理器，如 JpaTransactionManager，在事务开始时把真实的 EntityManager 绑定到当前线程，代理找到它并转发调用，事务结束后解绑，真实 EntityManager 关闭。

那为什么 Spring 单例 Service 里注入 EntityManager 看起来没事？

因为注入的是 SharedEntityManagerCreator 生成的代理。这个代理本身不持有持久化上下文，它把每次方法调用委托给当前线程绑定的真实 EntityManager。

Spring 的事务绑定是 ThreadLocal 的，父线程开启的事务和绑定的 EntityManager，在子线程里完全看不到。子线程通过 @PersistenceContext 代理拿到的，是一个新创建的 EntityManager，没有父事务上下文

正确的做法是：每个并行工作任务在自己的线程内、用自己的事务边界完成数据库操作。跨线程传递的应该是 ID 或不可变 DTO，而不是托管实体或 EntityManager。

如果子任务需要写入，让子任务自己开启事务，父线程等待所有子任务完成后再做后续处理。

Hibernate 的脏检查（dirty checking）是怎么实现的？

Hibernate 的脏检查核心机制是快照比对，实体被加载或纳入持久化上下文时，Hibernate 会保存一份该实体状态的快照；在 flush 时，将当前实体状态与快照逐属性比较，不一致的实体被标记为脏，进而生成 UPDATE 语句。

当实体从数据库加载到持久化上下文时，Hibernate 会保存一份“加载状态”（loaded state）的快照，代表该实体在数据库中的最后已知状态。在 flush 周期中，Hibernate 需要判断 Session 中哪些实体已被修改，默认做法是逐个检查实体的每个属性值，与快照中的对应值进行比较。如果发现差异，该实体就被视为脏，其变更会在 flush 时通过 UPDATE 语句同步到数据库。

这个比对过程是深度比较，发生在每次 flush 时，对持久化上下文中关联的每一个实体执行。这也解释了为什么批量处理时建议定期 flush() 后 clear()：上下文中的实体越多，每次 flush 的脏检查开销就越大。

Hibernate 也支持通过字节码增强来跟踪脏状态。增强后的实体类会在属性被修改时自行记录变更，flush 时直接检查这些标记，而不必逐字段比对。

另一个扩展点是 CustomEntityDirtinessStrategy 接口，允许应用程序接管脏检查逻辑。

Hibernate 的脏检查不依赖 equals() 或 hashCode()。它比较的是属性值本身，而不是通过对象相等性来判断。

Hibernate 什么时候会把 SQL 发到数据库（flush 的时机）？

Hibernate 默认采用 AUTO 刷新模式，它并不会在每次修改实体后立刻发送 SQL，而是把变更攒在持久化上下文里，在特定时机才同步到数据库。

  • 事务提交前：这是最常见的时机。当你调用 Transaction.commit() 时，Hibernate 会先 flush，把攒下的 INSERT、UPDATE、DELETE 一次性发出去，然后再提交数据库事务。
  • 执行 JPQL/HQL 查询前：如果队列中待执行的变更可能影响即将执行的查询结果，Hibernate 会先 flush。
  • 执行原生 SQL 查询前：使用 JPA EntityManager API 执行原生 SQL 时，总是会触发 flush，因为 Hibernate 无法判断原生 SQL 会影响哪些表，只能保守地全部刷出。但使用 Hibernate 原生 Session API 时，默认不会触发 flush
  • 显式调用 flush()：无论什么模式，你都可以手动调用 Session.flush() 或 EntityManager.flush()，强制立即同步。

如果实体使用 GenerationType.IDENTITY，INSERT 会在调用 persist() 时立刻执行，而不是等到 flush。

除了默认的 AUTO，Hibernate 还提供其他模式来控制 flush 频率：

  • COMMIT：尽量延迟到事务提交时才 flush。但执行 JPQL 查询时可能返回过期数据，原生 SQL 查询仍可能触发提前 flush。
  • ALWAYS：每次查询前都 flush，几乎总是低效的。
  • MANUAL：完全由应用控制，只有显式调用 flush() 才同步。适合长事务或需要精细控制批处理节奏的场景。

延迟加载（懒加载）在 JPA 里是怎么实现的？LazyInitializationException 什么情况下出现？你们项目怎么解决？

JPA 的懒加载主要依靠代理（Proxy） 实现

当你在实体上配置了 @OneToOne(fetch = FetchType.LAZY) 或 @ManyToOne(fetch = FetchType.LAZY) 时，Hibernate 从数据库加载主实体后，并不会立刻去查关联对象。它会在关联字段里放入一个代理对象（通常是实体类的运行时子类）。

这个代理对象只持有关联实体的主键 ID。当你第一次访问该代理的非 ID 属性（比如 book.getAuthor().getName()）时，代理才会拦截这次调用，利用当前仍然打开的 Session 去数据库发出真正的 SELECT 语句，加载完整数据并填充代理。

LazyInitializationException 出现的根本原因是在持久化上下文（Session/EntityManager）关闭后，才去触发代理的初始化。

  • 在 Session 打开时完成所需数据的加载，然后返回 DTO
  • 使用 @EntityGraph 按需覆盖查询的抓取策略。

为什么 JOIN FETCH 一对多集合再分页会报警告/结果不对？ 一次 JOIN FETCH 两个 List 集合为什么会抛 MultipleBagFetchException？怎么破？

集合 JOIN 会把一条主实体展开成多条数据库行，而 API 通常要按主实体分页。如果直接对 JOIN 行加 LIMIT，分页时，数据库返回的行数不等于父实体数量，Hibernate 无法在 SQL 层面正确 LIMIT，只能把所有匹配行拉回内存再分页，于是出现警告且结果可能不对。，例如一对多查询项目和成员关系的时候，可能截断一个项目的成员集合，或者一页实际只包含少量项目。

假设一个父实体有 10 个子实体。执行 SELECT p FROM Parent p JOIN FETCH p.children 时，数据库返回的不是 1 行，而是 10 行，因为父实体的每一列在每行里重复出现。如果加上 LIMIT 10，你期望拿到 10 个父实体，但数据库实际只会返回 10 行，而这 10 行可能只对应 1 个父实体。结果是父实体数量严重不足，分页完全失真。

两种方式解决这个问题

  • 先用一个不 JOIN FETCH 集合的查询分页拿到父实体 ID 或父实体本身，再用第二个查询根据这批 ID 去加载子集合。两段查询的粒度都是可控的。
  • 另一种是用窗口函数在 SQL 层完成分页，但这需要脱离标准 JPQL，写原生 SQL。

一次 JOIN FETCH 两个 List 时，膨胀更严重，Hibernate 无法安全地把膨胀后的行还原成两个无序集合，于是直接拒绝执行。

解决方案

  • 一次只 JOIN FETCH 一个集合，其余用批量加载。

    第一个查询 JOIN FETCH 一个集合，拿到父实体列表；第二个查询用 WHERE p IN :posts 去加载另一个集合

    关键点在于，第二个查询不对 tags 做 JOIN FETCH，而是让 Hibernate 在需要时通过批量抓取（@BatchSize 或 hibernate.default_batch_fetch_size）去加载。如果你配置了批量大小（比如 100），第二个集合的加载会以批量 IN 查询的形式完成，而不是 N+1 次单条查询。

  • 用 DTO 投影绕过实体集合映射。

FetchType.LAZY 和 @Fetch(FetchMode.SUBSELECT) 有什么区别？

关联数据是立刻加载，还是等到第一次被访问时才加载。

FetchType.LAZY

  • LAZY 表示延迟加载，主实体加载时不会去查关联集合，直到你调用才触发查询。

@Fetch(FetchMode.SUBSELECT)：控制加载策略

  • 把“加载集合”这件事的 SQL 从“逐条查”改成了“用子查询批量查”。SUBSELECT 的策略是，在初始查询执行后，把初始查询的 SQL 嵌入到一个 IN (子查询) 里，从而批量加载当前结果集中所有父实体的关联集合，而不是为每个父实体单独发一条 SQL。

SUBSELECT 这种抓取策略同时兼容 eager 和 lazy 两种加载方式。

  • LAZY + 默认 SELECT：访问某个父实体的集合时，发一条 WHERE parent_id = ? 的查询。如果有 N 个父实体被访问，就是 N+1 问题。
  • LAZY + SUBSELECT：第一次访问任意一个父实体的集合时，Hibernate 不会只查这一个父实体的子记录，而是用初始查询作为子查询，一次性把所有当前已加载父实体的关联集合都查出来。
  • EAGER + SUBSELECT：主查询一执行完，立刻用子查询把关联集合批量加载出来，不需要等待访问触发。

SUBSELECT 的一个典型用途，恰恰是解决“一次 JOIN FETCH 两个集合”的困境。比如用 join 抓取第一个集合，用 SUBSELECT 抓取第二个集合，从而避免笛卡尔积和 MultipleBagFetchException。

JPA 的一级缓存和二级缓存分别是什么？二级缓存默认开吗？JPA 的二级缓存和 Redis 缓存的定位区别？你项目里两者怎么分工？

一级缓存就是持久化上下文中的实体身份管理范围，随 EntityManager/Session 存在，强制开启且无法关闭

二级缓存是，通常在 SessionFactory/EntityManagerFactory 层面，跨多个 EntityManager 和事务共享。启用后，当按主键加载实体时，Hibernate 会先查二级缓存，命中则跳过数据库。默认关闭

JPQL 查询默认不经过二级缓存，查询返回的实体也不会自动进入二级缓存

二级缓存主要加速的是 find(id) 和关联对象按 ID 的获取，而不是列表查询。

需要显式设置 hibernate.cache.use_second_level_cache=true，并指定缓存提供者，然后在实体上标注 @Cache 并选择并发策略，该实体才会被纳入二级缓存。

二级缓存是 Hibernate 帮你管实体缓存，Redis 是你自己管任意数据的缓存。你可以用 Redis 作为二级缓存的存储后端，例如通过 Redisson 等 RegionFactory

一般情况下

  • 二级缓存只放 按 ID 高频读取、极少修改 的实体。 Redis 独立缓存用于业务查询结果和跨请求的聚合数据。

hibernate.jdbc.batch_size、order_inserts、order_updates 分别解决什么？

这三个配置项协同工作，核心目标是让 Hibernate 尽可能地把多条 SQL 攒成一批发给数据库，减少网络往返

  • hibernate.jdbc.batch_size：开启批处理并设定上限

    设置一个正整数后，Hibernate 会把待执行的 INSERT/UPDATE 语句攒起来，达到这个数量或 flush 时一次性发给 JDBC 驱动。设为 0 或负数则关闭批处理。

  • hibernate.order_inserts：让插入语句按表排序

    批处理有一个前提，连续执行的语句必须操作同一张表。开启 order_inserts 后，Hibernate 在构造批次前会重新排序 INSERT 语句，把同一张表的插入聚在一起，从而形成更大的批次。

  • hibernate.order_updates：让更新语句按主键排序

    作用类似，但针对 UPDATE。

@DynamicUpdate / @DynamicInsert 是干什么的？

@DynamicUpdate 和 @DynamicInsert，让 Hibernate 在每次执行 INSERT 或 UPDATE 时，根据实体当前的实际状态动态生成 SQL，而不是复用包含所有列的固定 SQL。

  • @DynamicUpdate：只更新脏字段

    默认情况下，Hibernate 在启动时就为每个实体生成一条固定的 UPDATE 语句，包含所有映射列。即使你只改了一个字段，flush 时发出去的 SQL 仍然会 SET 所有列。开启 @DynamicUpdate 后，Hibernate 会在 flush 时根据脏检查结果，只把发生变化的列放进 UPDATE 语句。可以减少不必要的列写入和锁开销

  • @DynamicInsert：忽略 null 值，让数据库默认值生效

    默认 INSERT 语句会包含所有映射列。如果某个字段在 Java 对象里是 null，Hibernate 会把 NULL 显式写进 INSERT 语句。开启 @DynamicInsert 后，值为 null 的列会被排除在 INSERT 语句之外，数据库的 DDL 默认值就有机会生效。

MyBatis

为什么说 MyBatis 是半自动 ORM 映射工具？它与全自动的区别在哪里？

Hibernate 属于全自动 ORM 映射工具，使用 Hibernate 查询关联对象或者关联集合对象时，可以根据对象关系模型直接获取，所以它是全自动的。

而 MyBatis 在查询关联对象或关联集合对象时，需要手动编写 sql 来完成，所以，称之为半自动 ORM 映射工具。

Mybatis里的 # 和 $ 的区别？为什么有了 #{} 还要 ${}？

  • Mybatis 在处理 #{} 时，会创建预编译的 SQL 语句，将 SQL 中的 #{} 替换为 ? 号，在执行 SQL 时会为预编译 SQL 中的占位符 ? 赋值，调用 PreparedStatement 的 set 方法来赋值，预编译的 SQL 语句执行效率高，并且可以防止 SQL 注入，提供更高的安全性，适合传递参数值。
  • Mybatis 在处理 ${} 时，只是创建普通的 SQL 语句，然后在执行 SQL 语句时 MyBatis 将参数直接拼入到 SQL 里，不能防止 SQL 注入，因为参数直接拼接到 SQL 语句中，如果参数未经过验证、过滤，可能会导致安全问题。

XML Mapper 映射文件中，除了常见的 select、insert、update、delete 标签之外，还有哪些标签？resultType 和 resultMap 怎么选？<id> 标签是干嘛的？

结果映射类：用于处理Java对象与数据库字段之间的复杂映射关系

  • <resultMap>：自定义结果集映射规则，解决字段名与属性名不一致、或处理复杂的关联对象
    • <id>：映射主键字段。
    • <result>：映射普通字段。
    • <association>：处理一对一的关联关系。
    • <collection>：处理一对多的关联关系。

动态SQL类：在XML中编写灵活的、条件化的SQL语句，避免在Java代码中拼接SQL。

  • <if>：条件判断，如果test条件为真，则拼接其内部的SQL片段。
  • <choose>, <when>, <otherwise>：实现多条件分支选择
  • <where>：智能处理WHERE子句。它会自动去除第一个条件前多余的AND或OR，并处理是否要插入WHERE关键字。
  • <set>：智能处理UPDATE语句的SET子句。它会动态地添加SET关键字，并自动去除最后一个多余的逗号。
  • foreach>：遍历集合，常用于构建IN条件或批量插入语句。

其他功能类

  • <selectKey>：用于在插入（<insert>）操作前后，从数据库获取新生成的主键值
  • <sql>：定义可重用的 SQL 片段，比如常用的列名列表。
  • <cache>：开启当前命名空间的二级缓存

resultType 和 resultMap选择的标准是：查询结果的列名或别名与目标 Java 对象的属性名是否完全一致，以及映射是否涉及复杂关系。

  • resultType

    当数据库列名与 Java 属性名完全匹配，或者通过 SQL 别名 AS 对齐了，且不涉及一对一、一对多等嵌套关系时，用 resultType 指定目标类即可。

  • resultMap

    列名与属性名不一致；需要处理复杂关系；需要精细控制映射

而且，在同一个 <select> 标签里，resultType 和 resultMap 不能同时使用，只能二选一。

在 <resultMap> 内部，<id> 和 <result> 都用于映射列到属性，但 <id> 承担了一个特殊职责，标记出哪个或哪些组合属性是对象的主键。

MyBatis 能执行一对一、一对多的关联查询吗？都有哪些实现方式，以及它们之间的区别？association 和 collection 分别映射什么？一对多 join 出 100 行怎么变成 5 个主对象？

MyBatis 完全支持一对一和一对多的关联查询。它通过 <resultMap> 标签下不同的子标签来实现

  • 嵌套查询

    这种方式会执行多条SQL。先查主表，再根据主表的结果，去关联表执行额外的查询。

    • 一对一/多对一（<association>）：通过单独的 SQL 查询关联对象。
    • 一对多（<collection>）：通过单独的 SQL 查询关联的集合。
    • select：指定要执行的额外SQL的ID。
    • column：作为参数传递给该SQL的字段。
    • fetchType：可选 lazy（懒加载）或 eager（立即加载），用于控制性能。

  • 嵌套结果

    只执行一条多表关联查询（JOIN） 的SQL，一次性查出所有数据，然后在 <resultMap> 中通过映射关系，将结果集填充到对象中。

    • 一对一/多对一（<association>）：使用 javaType 指定关联对象的类型。
    • 一对多（<collection>）：使用 ofType 指定集合中元素的类型。

关于一对多 JOIN 出 100 行怎么变成 5 个主对象的问题，关键在于 <resultMap> 里 <id> 标签配合 <collection> 的自动合并机制

假设查 5 个订单，每个订单平均 20 个订单项，JOIN 后返回 100 行。MyBatis 处理时，会读取每一行的 <id> 列。当它发现连续多行的订单 ID 相同，就知道这些行属于同一个订单。它会复用已经创建的那个订单对象，而不是新建一个。最终，100 行数据在内存中被折叠成 5 个 Order 对象，每个对象的 items 列表里装着对应的 20 个明细。如果 <id> 配置缺失或错误，MyBatis 可能会把每一行都当成一个新订单，导致返回 100 个重复的订单对象。

Mapper 就是个接口没有实现类，为什么能调通？MapperProxy 和 MapperMethod 各干什么？ Mapper 方法能重载吗？为什么？

Mapper 接口没有实现类却能调通，是因为 MyBatis 在运行时用 JDK 动态代理为接口生成了一个代理对象。

MapperProxy 是代理逻辑的入口，它实现了 InvocationHandler。当你调用 Mapper 接口的任何一个方法时，实际上进入的是 MapperProxy.invoke()。它负责两件事：如果是 Object 类的方法，直接放行；否则，从缓存中取出或创建对应的 MapperMethod，把调用委托给它。

MapperMethod 是单个 Mapper 方法的执行封装，包含

  • SqlCommand：记录了这条 SQL 的名称和类型
  • MethodSignature：记录了方法的参数和返回类型

MapperProxy 负责拦截并分发，MapperMethod 负责执行这一个方法对应的数据库操作。

Mapper 接口中的方法不能重载

原因在于 MyBatis 定位 SQL 的方式，它使用 接口全限定名 + 方法名 作为唯一键，去 Configuration 中查找对应的 MappedStatement，重载后全限定名 + 方法名也是完全相同的，就出现冲突

从调用 Mapper 到拿到结果，完整链路讲一遍。

整条链路可以概括为：代理拦截 → 方法封装 → SqlSession 委派 → Executor 执行 → JDBC 操作 → 结果映射。

当你通过 sqlSession.getMapper(UserMapper.class) 拿到 Mapper 时，返回的并不是一个实现了 UserMapper 接口的普通对象，而是一个由 JDK 动态代理生成的 MapperProxy 实例。它实现了 InvocationHandler，所以你对接口方法的每一次调用，实际进入的是 MapperProxy.invoke()。

在 invoke() 里，它会先排除 Object 类的方法，然后从缓存中取出当前方法对应的 MapperMethod，MapperMethod 是单个 Mapper 方法的执行封装，其中有方法参数和真正要执行的 sql 语句，然后，它会调用 sqlSession 中的方法

默认情况下，SqlSession 内部持有的 Executor 是 CachingExecutor，它装饰了真正干活的 SimpleExecutor。它会先查二级缓存，如果命中了直接返回结果，没有命中请求会进入真正的 Executor，此时会检查一级缓存，也没命中才去数据库查询。

在准备执行 SQL 的阶段，Executor 会通过 MappedStatement 获取 BoundSql（包含最终要执行的 SQL 语句和参数映射信息），然后交给 StatementHandler，它负责与 JDBC 打交道，这里涉及到参数绑定的过程，发送 sql 到数据库。

最后，SQL 执行返回 ResultSet 后，ResultSetHandler 负责把它转换成 Java 对象。根据 resultType和resultMap进行映射，最终，结果沿着调用链逐层返回。

MyBatis 中一级缓存是什么级别？它的 key 由什么组成？什么时候失效？我在 Service 里连续调两次同一个 Mapper 方法，为什么一级缓存没生效？

MyBatis 的一级缓存是 SqlSession 级别的，默认开启且无法关闭。

在 Service 里连续调两次同一个 Mapper 方法却未命中，最常见的原因是，没有开启 Spring 事务，导致两次调用使用了不同的 SqlSession，在执行完 SQL 后立即关闭了，因为一级缓存的生命周期在每次查询后就已经结束了。

一级缓存绑定在 SqlSession 上。每个 SqlSession 内部持有一个私有的缓存区域（本质是 HashMap），不同 SqlSession 之间的缓存互不影响。因此它的生命周期与 SqlSession 完全一致，会话关闭，缓存即释放。

一级缓存的 key 是一个 CacheKey 对象

  • Statement ID（即 Mapper 接口全限定名 + 方法名）
  • SQL 语句（最终发往数据库的 SQL 文本）
  • 参数

因此，只有当两次查询的 Statement ID、SQL 文本和参数完全一致时，key 才会相同，缓存才可能命中。

以下情况会清空当前 SqlSession 的一级缓存

  • 执行了任意写操作（保证一致性）
  • 调用了 commit()、rollback() 或 close()，导致会话生命周期结束或重置。

MyBatis 中二级缓存怎么开？为什么大厂规范普遍禁用它？二级缓存和 Spring 事务一起用会有什么坑？

MyBatis 二级缓存默认关闭，需要在配置中显式开启`cache-enabled: true，并在 Mapper 中声明 <cache> 标签才能生效。

普遍禁用的核心原因是它在分布式环境下无法保证跨节点、跨命名空间的数据一致性，且与 Spring 事务结合时存在多个隐蔽的失效与脏读陷阱。

二级缓存的作用域是 Mapper 命名空间（Namespace）级别，多个 SqlSession 共享同一份缓存

  • 跨命名空间无法联动失效。如果两个 Mapper 都查询了同一张表，A 命名空间的缓存不会因为 B 命名空间执行了更新而失效。只要查询路径涉及多张表或多 Mapper 的关联，缓存数据就可能与数据库脱节。
  • 分布式节点之间缓存不共享。默认的二级缓存存储在 JVM 内存中。在多实例部署下，节点 A 的更新只会清空节点 A 的缓存，节点 B 的缓存依然持有旧数据，直接导致用户看到不一致的结果。
  • 二级缓存在事务提交后才真正写入。如果事务最终回滚，缓存不会写入。但如果事务在提交前被其他会话读取了旧数据并放入了缓存，回滚后缓存里可能残留基于未提交数据生成的结果

MyBatis 延迟加载的原理是什么？有哪些失效场景？

MyBatis 延迟加载的原理是动态代理，MyBatis 为配置了懒加载的关联属性生成一个代理对象，当程序首次调用该属性的 getter 方法时，代理对象才触发真实的 SQL 查询，把数据加载进来并填充到主对象中。

当你在 resultMap 中使用 <association> 或 <collection> 并配置了 select 属性，且开启了懒加载后，MyBatis 在映射主对象时，不会立即执行关联查询，而是给该关联属性塞入一个代理对象，代理拦截这次调用，发现数据还没加载，于是通过 SqlSession 执行预先配置的那条关联 SQL 把结果查出来，后续再访问同一属性，直接返回已加载的数据，不再查库。

失效场景如下

  • aggressiveLazyLoading 设为 true，只要你访问主对象的任意一个属性都会懒加载，这会让懒加载形同虚设。
  • 调用了 toString()、equals() 或 hashCode()，MyBatis 默认将 equals、clone、hashCode、toString 配置为触发懒加载的方法。用 IDE 的 Debug 模式查看对象就会意外触发所有懒加载查询
  • 使用了 resultType 而非 resultMap，或者在其中用了 JOIN 查询而非分步查询
  • 在 SqlSession 生命周期之外访问

PageHelper 的原理是什么？为什么 startPage 之后必须紧跟查询？

PageHelper 的原理是基于 MyBatis 拦截器（Interceptor）机制，在 Executor 执行查询前拦截 SQL，根据当前线程绑定的分页参数动态改写 SQL（追加 LIMIT 或数据库对应的分页语法）。

startPage 之后必须紧跟查询，是因为分页参数存储在 ThreadLocal 中，且 PageHelper 只在拦截到的第一个查询上消费这些参数，拦截完成后立即清除；如果中间插入了其他逻辑，ThreadLocal 可能未被正确清理，导致后续请求或查询被错误分页。ThreadLocal 的清理依赖拦截器的 finally 块。

当你调用 PageHelper.startPage(pageNum, pageSize) 时，分页参数被存入当前线程的 ThreadLocal，随后，当 Mapper 查询触发 Executor.query 时，拦截器从 ThreadLocal 中取出分页参数，判断是否需要分页，再根据数据库方言改写原始 SQL

MyBatis 中如何处理类型转换？TypeHandler 是干什么的？在哪个环节被调用？

MyBatis 的 TypeHandler 是负责 Java 类型与 JDBC 类型之间双向转换的组件。

它定义了四个核心方法：

  • 写库方向：setParameter系列方法，负责把 Java 值（parameter）转换成 JDBC 类型，并设置到 PreparedStatement 的第 i 个占位符上。
  • 读库方向：getResult(ResultSet rs, ...) 系列方法。负责从 ResultSet 的指定列中取出 JDBC 值，并转换成你需要的 Java 类型返回。

TypeHandler 的调用时机非常明确，贯穿 SQL 执行的前后。

  1. 参数绑定环节

    执行一个 Mapper 方法时，MyBatis 的 DefaultParameterHandler 负责处理参数。它会根据参数的类型，从 TypeHandlerRegistry（注册中心）中找到对应的 TypeHandler，然后调用其 setParameter 方法，把 Java 值写入 PreparedStatement。

  2. 结果映射环节

    当 SQL 执行完毕返回 ResultSet 后，DefaultResultSetHandler 会根据目标属性的 Java 类型，找到对应的 TypeHandler，然后调用其 getResult 方法，从 ResultSet 中取出值并转换成 Java 类型

枚举怎么入库？EnumTypeHandler 和 EnumOrdinalTypeHandler 有什么区别？

EnumTypeHandler 是 MyBatis 的默认枚举处理器，以枚举名称（name） 入库，写入数据库时调用枚举的 name() 方法，存入如 "ENABLE"、"DISABLE" 这样的字符串；读取时用 Enum.valueOf(type, s) 将字符串还原为枚举实例。

EnumOrdinalTypeHandler，枚举的 ordinal() 值，即声明顺序索引（从 0 开始）。例如 ENABLE 是第一个，存 0；DISABLE 是第二个，存 1。

使用 MyBatis，你们 MySQL 里的 JSON 或者 PG 里的 JSONB 怎么映射？

MyBatis 默认不识别 JSON 类型字段，需要借助 TypeHandler 来转换。

  • 使用 MyBatis-Plus 的 JacksonTypeHandler：

    在字段上添加 @TableField(typeHandler = JacksonTypeHandler.class)。实体类上同时标注 @TableName(autoResultMap = true)。

  • 手写自定义 TypeHandler

PG 的 JSONB 处理与 MySQL 类似，但 MyBatis-Plus 官方文档指出，针对 PG 的 JSONB 字段，建议创建自定义的 TypeHandler 来处理。

MyBatis 怎么做多数据源？@DS 或 AbstractRoutingDataSource 的原理是什么？多数据源下 MyBatis 有哪些坑？

MyBatis 做多数据源，主流方案是基于 Spring 的 AbstractRoutingDataSource 做动态路由，或者直接用 MyBatis-Plus 的@DS 注解封装好的方案。（@DS 底层同样依赖 AbstractRoutingDataSource，只是额外帮你做了注解解析和 ThreadLocal 管理）

Spring 的 AbstractRoutingDataSource 是一个路由数据源。它内部维护一个 Map，存放“查找键 → 真实 DataSource”的映射。这个查找键通常来自 ThreadLocal。

@DS 注解的拦截器在方法执行前，扫描类或方法上的 @DS 值，把数据源名存入内部的 ThreadLocal。随后当 MyBatis 通过动态路由数据源获取连接时，从 ThreadLocal 中取出这个名字，路由到对应的真实数据源。方法结束后，拦截器会清理 ThreadLocal，防止线程池复用导致数据源串用。

多数据源下 MyBatis 的主要问题

  • 事务内切换数据源失效

  • AOP 切面不生效导致切换静默失败

    @DS 依赖 AOP 拦截。如果方法不是 public 的、在同一个类内部直接调用（绕过了代理对象），或者切面类没有被 Spring 管理，就不行

  • ThreadLocal 泄漏导致数据源错乱

  • 缺少 @Primary

    容器中存在多个 DataSource Bean 时，Spring 不知道默认注入哪个，启动会失败。需要给其中一个标注 @Primary。

我会先看业务写模型和查询形态，再看数据库、数据规模、团队经验与已有技术栈，而不是先选一个喜欢的框架。

而是主要看两个维度：业务模型的复杂程度，以及对 SQL 和数据访问过程的控制要求。

首先，如果项目以 CRUD、动态条件查询、复杂报表以及大批量数据处理为主，我会更倾向 MyBatis Plus。因为这类业务的数据访问逻辑相对明确，MyBatis Plus 能减少基础 CRUD 的重复代码，同时保留 MyBatis 对 SQL 的控制能力。尤其是复杂关联查询、数据库特定语法和大数据量场景，能够更直接地控制执行计划、分页和数据读取方式。

其次，如果业务有比较复杂的领域模型，状态流转和较多的业务约束，我会优先考虑 Hibernate，也就是通过 Spring Data JPA 来进行持久化。它提供了完整的 ORM 能力，包括持久化上下文、脏检查、实体状态管理、关联映射和乐观锁等机制，可以减少领域对象和数据库之间的映射代码。

比如之前涉及到的科研项目管理平台，项目涉及科研项目、任务协作和权限管理等业务，规则繁杂，而且对象通常来说比较复杂，且批量处理的内容较少，因此我选择了 Spring Data JPA + Hibernate。开发中使用 @Version 处理并发更新，通过 JPQL 和 Criteria 实现查询，同时也针对 N+1 查询等 ORM 性能问题进行过优化。

而我另外一个项目中，业务涉及百万级水文数据处理，数据模型相对简单，但是整体的查询逻辑和批量查询内容涉及的多而且复杂。所以采用了 MyBatis Plus，其中我就使用了 MyBatis 的游标，避免一次性将大量结果加载到内存中，缓解了 OOM 和 Full GC 问题。这也是为什么在数据处理场景下，我会更加重视 SQL 和数据读取行为的可控性。

最后，选型原则是选择在当前业务场景下，能够以更低复杂度满足性能、可维护性和开发效率要求的方案。 如果是存量项目，我还会综合考虑现有技术栈和团队熟悉程度，不会为了技术选型而引入不必要的迁移成本。

N+1 在 JPA 和 MyBatis 里分别怎么产生、怎么解决？说说的你的思路？

N+1 本质上是一个数据库访问次数膨胀的问题，比如查询 100 条主记录执行了 1 条 SQL，但获取每条主记录的关联数据，又分别执行了 100 条 SQL，最后就变成了 101 次数据库查询。

在 JPA 中，最典型的是实体关联的延迟加载。例如查询一个科研项目列表，每个项目都有多个任务，如果使用 @OneToMany(fetch = FetchType.LAZY)，第一次只会查询项目。当我们遍历项目并调用 getTasks() 时，Hibernate 可能为每个项目分别执行一条关联查询，从而产生 N+1。

解释一下在 Dubbo 项目中写的 PageableAdapter，为什么不能直接把 Page 传给 Dubbo？为什么 Pageable 不适合直接跨服务（比如 Dubbo）传？你写的 PageableAdapter 解决了什么？

不是 Page 和 Pageable 在任何情况下都不能通过 Dubbo 传输，而是它们属于 Spring Data 的框架内部抽象，不适合作为稳定的跨服务 RPC 契约。PageableAdapter 主要解决的是分页模型的序列化兼容性和服务间耦合问题。

Spring Data JPA 的分页主要有两个抽象：Pageable 用于描述分页请求，包括页码、每页大小和排序信息；Page<T> 则用于封装分页结果，包括当前页内容、总记录数和总页数。

但是 Dubbo 的 RPC 调用需要对请求参数和返回值进行序列化与反序列化。因此，直接将它们暴露在 Dubbo 接口中，不仅可能遇到 Hessian2 反序列化兼容问题，还会要求服务提供方和消费方同时依赖 Spring Data 的类型及其实现细节

不能直接把 Page 传给 Dubbo 和为什么 Pageable 不适合直接跨服务传。都是因为，它们本身是面向 Spring Data 框架设计的，并没有把跨 RPC 协议的序列化兼容性作为主要契约。

大批量写入 JPA 和 MyBatis 各怎么做？为什么 JPA 容易踩坑？

JPA 和 MyBatis 都能实现批量写入，但因为底层持久化机制不同，优化重点也不一样

MyBatis 主要通过 ExecutorType.BATCH 实现批处理。它会复用相同 SQL 对应的 PreparedStatement，通过 addBatch() 累积参数，再在 flushStatements() 时执行 JDBC Batch。MyBatis-Plus 则封装了 saveBatch() 等批量操作。

除此之外，也可以用 MyBatis XML 的 <foreach> 拼接多 VALUES INSERT，或者针对海量数据直接使用 JDBC Batch、数据库原生导入。

JPA/Hibernate 则需要先配置 hibernate.jdbc.batch_size，让 Hibernate 把持久化操作合并为 JDBC 批次。同时，在大量 persist() 时需要定期执行 flush() 和 clear()，避免大量实体一直保留在一级缓存中，导致内存增长和 GC 压力。

JPA 最容易出现的问题是 主键生成策略。如果使用 GenerationType.IDENTITY，Hibernate 的常规 INSERT 批处理通常会被禁用，因为它需要及时执行 INSERT 来获取数据库生成的主键。即使设置了 batch_size=50，也不代表最终会以 50 条为一批执行。

第二个问题是 持久化上下文的内存开销。Hibernate 需要管理实体状态、脏检查和关联关系。如果一次持久化几十万个实体却不清理 Persistence Context，可能导致内存不断增长甚至 OOM。

同时，应该分批产生输入数据，而不是事先将全部百万级数据加载到内存。

第三个问题是 saveAll() 不等于真正的 JDBC Batch，因为可能走 merge()，产生额外查询。它只是批量调用实体保存逻辑，而不一定实现。而且 JDBC Batch 通常需要能够复用相同 SQL 结构，才能进行整批的提交。

第四个问题是 flush 和事务提交。如果外面仍然只有一个 @Transactional，即使你每 500 条 flush 并 clear 一次持久化上下文，整个 100 万条写入仍可能处于同一个数据库事务内

实际选型时，如果业务需要完整的实体生命周期、级联关系和领域模型管理，我会使用 JPA，但会特别关注主键策略、批次大小和 Persistence Context。如果只是大批量数据同步、计算结果入库或 ETL，我更倾向 MyBatis Batch 或 JDBC Batch，以获得更直接的 SQL 控制和更低的 ORM 管理成本。

最终通过 SQL 执行次数、JDBC Batch 是否真正生效、堆内存占用、吞吐量以及事务耗时来验证，而不是仅凭调用了批量 API 就认为优化完成。

分页在 JPA 和 MyBatis 里分别怎么实现？深分页怎么办？

JPA 的分页实现是Pageable + Page 或 Slice

在 Repository 方法中传入 Pageable 参数，返回 Page<T> 或 Slice<T>。PageRequest.of(page, size, Sort) 构造分页参数。

  • 返回 Page<T>：Spring Data 会额外执行一条 COUNT 查询来填充 totalElements 和 totalPages。这在百万级表上本身就是一笔开销。
  • 返回 Slice<T>：只查当前页数据，并告知 hasNext()，不执行 COUNT 查询。适合不需要 共 N 条/共 M 页 的场景。

MyBatis 原生没有分页 API，依赖拦截器插件在 SQL 执行前改写语句

  • PageHelper：调用 PageHelper.startPage(pageNum, pageSize) 后，紧跟着的第一个查询会被自动追加 LIMIT。

    原理是 ThreadLocal 存参数 + 拦截器改写 SQL。注意 startPage 后必须紧跟查询，否则参数会被错误消费或泄漏。

  • MyBatis-Plus：使用 Page<T> 对象作为参数传入 selectPage 或 page 方法，分页插件自动改写 SQL。

JPA 和 MyBatis 的分页实现路径不同，但深分页的根因和优化思路是相通的：传统 LIMIT offset, size 在偏移量大时，数据库必须扫描并丢弃 offset 行，耗时随页码线性增长。

优化方向要么是减少扫描量（延迟关联），要么是换掉分页方式（游标分页）。

  • 延迟关联

    先用覆盖索引查出目标页的主键，子查询只查 id，再拿这 20 个主键去回表取完整数据。

  • 游标分页

    B+ 树可以直接二分定位到游标位置，只读 20 行，与页码深度无关，始终是毫秒级。代价是不支持跳页，只能上一页/下一页或 加载更多。需要为排序字段建立复合索引，且排序字段必须包含唯一键（如 id）来兜底稳定性。

  • 直接限制最大翻页深度

UUID 主键有什么利弊？你能说清楚吗？

UUID 最直接的好处是全局唯一。多个应用实例、多个数据库分片各自生成 ID，合并数据时也不会冲突。 UUID 在应用层调用 UUID.randomUUID() 就能直接拿到，没有网络开销。

另一个附带好处是对外暴露时不会泄露业务量。自增 ID 很容易被外部推算各种信息，UUID 没有这个信息量。

但是在 InnoDB 里，随机 UUID 是 索引杀手

  • 存储大

    CHAR(36) 存 UUID 占 36 字节，更关键的是，InnoDB 的每个二级索引叶子节点都会存一份主键值，所有二级索引都会跟着变大。

  • 写入乱

    这是 UUIDv4 最大的问题，InnoDB 的数据按主键顺序存储在聚簇索引里。自增主键永远往 B+ 树最右边插，页满了就在右边开新页，写入接近顺序 IO。UUIDv4 的值完全随机，新行可能插到树中间任意位置。目标页满了就触发页分裂，把一半数据挪走，留下空洞，碎片越来越多，写入从顺序 IO 退化成随机 IO。

如果业务使用 UUID，首选 UUIDv7 或 ULID，它们把时间戳放在了 ID 的高位，生成的 ID 随时间递增，写入 B+ 树时接近顺序追加，页分裂大幅减少。存储用 BINARY(16) 而非 CHAR(36)。这能把存储从 36 字节压到 16 字节，缓解空间膨胀。

如果没有分布式唯一性需求，通常不使用 UUID
