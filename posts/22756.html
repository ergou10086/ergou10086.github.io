前言

我们一直在用 Netty，是一直把它当成一个整体：启动一个 ServerBootstrap，挂几个 Handler，然后发消息、收消息。用起来是这样的，但是当出现问题，什么出现回调顺序不对、消息没到业务、写出去的数据卡住这类问题，只靠 API 文档很难解释清楚，就需要我们把 Netty 拆成一个个模块来看

哦别忘了这个。

对象 它负责什么 阅读时最容易混淆的地方
ServerBootstrap / Bootstrap 保存启动配置，组织 Channel 的创建、初始化、注册、绑定或连接 它们不持续执行后续每一次 Socket 读写

读源码前的准备

版本与源码结构

先固定版本。Netty 4.2 做了一次比较大的模块和事件循环重构，很多旧文章里的 NioEventLoop.run、ioRatio 在 4.2 已经换了位置甚至被移除。本文以 4.2.17.Final 为准，4.1 只在对比时出现。

4.2.17 的源码按模块拆开，读启动和事件循环主要看：

  • transport：Bootstrap、Channel、Pipeline、EventLoop、EventLoopGroup；
  • buffer：ByteBuf；
  • codec-base：ByteToMessageDecoder、LengthFieldBasedFrameDecoder、String 编解码；
  • handler：IdleStateHandler、SslHandler、WebSocket 等；
  • codec-http：HTTP 编解码器。

六层运行时

Netty 的源码看起来庞大，也确实很庞大，真正和一次请求相关的主线可以拆成六层：

  1. 启动：bind/connect → 创建 Channel → 初始化 Pipeline → 注册 EventLoop → 绑定/连接；
  2. 事件循环：select 等待事件 → 处理就绪 key → 跑任务队列与定时任务；
  3. 读写：读到的字节进 Pipeline，写出的对象经 Pipeline 进 ChannelOutboundBuffer，flush 才写 Socket；
  4. 传播：Context 双向链表、executor 切换、head/tail 兜底；
  5. 编解码：累积、拆帧、编码、HTTP/WebSocket/TLS 等协议 Handler；
  6. 资源与生命周期：Promise、ByteBuf 引用计数、内存池、close/deregister。

ChannelInitializer 什么时候执行

ChannelInitializer 是 Netty 里最常用的延迟装配工具。它的关键在 handlerAdded：

initChannel(ctx) 会调用子类实现的 initChannel(ch)，然后 ctx.pipeline().remove(this) 把自己移除。

  1. ChannelInitializer 只在 Channel 已经注册后执行 initChannel；如果 Channel 还没注册，handlerAdded 不会立刻装配，而是等注册完成后由 invokeHandlerAddedIfNeeded() 补发。

EventLoop

4.2 的类结构和 4.1 的差异

4.1 里我们熟悉的 NioEventLoop 在 4.2.17 已经被标记为 @Deprecated：

4.2 把 单线程事件循环 和 IO 多路复用实现 拆开了：

  • SingleThreadIoEventLoop：线程、任务队列、run() 循环；
  • NioIoHandler：Selector、select、processSelectedKeys、注册 key；
  • MultiThreadIoEventLoopGroup + NioIoHandler.newFactory()：替代 NioEventLoopGroup。

旧代码里的 NioEventLoopGroup 仍能跑，但新项目应该用新的写法。读源码时也要注意：4.1 文章里的 NioEventLoop.run，在 4.2 要拆成 SingleThreadIoEventLoop.run 和 NioIoHandler.run 两段看。

EventLoopGroup 与 chooser

NioEventLoopGroup 继承自 MultithreadEventExecutorGroup，内部是一个 EventExecutor[]。创建时按线程数创建 children，每个 child 是 SingleThreadIoEventLoop；next() 通过 chooser 选一个 executor。

chooser 的实现很值得看：

线程数是 2 的幂时，next() 用 idx.getAndIncrement() & (length - 1) 取模；否则用 % length。这是为了把取模的除法开销省掉。线程数不是 2 的幂时，源码用 long 计数器避免 32 位溢出后轮询不均匀。

一个 Channel 注册到哪个 EventLoop，由 group.register(channel) 时的 next() 决定；一旦注册，后续所有 I/O 都在这个 EventLoop 线程上执行。这就是“一个 Channel 绑定一个 EventLoop”的源码位置。

任务队列与定时任务

SingleThreadEventExecutor 有两个队列：

  • taskQueue：普通任务，execute/submit 提交；
  • scheduledTaskQueue：定时任务，schedule/scheduleAtFixedRate 提交，按 deadline 排序。

普通任务队列在 4.2 里通常是 MPSC 队列，多个线程可以并发 offer，只有 EventLoop 线程 poll。这样跨线程提交任务不需要锁。

schedule 与定时任务

schedule(task, delay, unit) 创建 ScheduledFutureTask，按 deadline 放进优先队列。每轮 runAllTasks 的 fetchFromScheduledTaskQueue 只把到期的任务搬进普通队列：

select 策略与 wakeup

NioIoHandler.select 的核心逻辑可以概括成：

  • 先看有没有到期任务，算出 timeoutMillis；没有任务就阻塞等待；
  • 如果任务队列里有任务，canBlock() 为 false，先 selector.selectNow() 不阻塞；
  • 正常 selector.select(timeoutMillis)；
  • select 返回后再检查 wakenUp 和任务队列，避免“任务提交了但 select 还在睡”的竞态；
  • 被用户 wakeup() 或中断时及时退出。

关键代码：

wakeup 的细节很值得看：execute() 提交任务时会尝试 selector.wakeup()，让阻塞的 select 立刻返回。wakenUp 是一个 CAS 标记，避免重复 wakeup 的系统调用开销。源码里有一段长注释专门解释 wakeup 和 select 的竞态，读一遍就能理解为什么“提交任务后 EventLoop 能马上醒”。

把 select 的完整循环展开，它其实在解决四个问题：

  1. 没有任务时阻塞，避免空转；
  2. 有任务时先 selectNow()，不阻塞；
  3. select 被唤醒后，再检查一次任务队列，避免“任务已提交但 select 还没返回”的丢失；
  4. 连续空轮询时重建 Selector。

关键分支：

runner.canBlock() 的定义是“没有普通任务、没有定时任务”。如果业务在别的线程提交了一个任务，canBlock 变 false，select 会立刻返回。这个设计让 EventLoop 在 I/O 和任务之间保持低延迟。

select 的 timeoutMillis 来自最近一个定时任务的 deadline；没有定时任务时，delayNanos 返回 SCHEDULE_PURGE_INTERVAL，不是无限大。这样 EventLoop 至少会定期醒来清理取消的定时任务。

任务与优雅退出

runAllTasks(maxTaskProcessingQuantumNs) 每轮最多跑一个时间片，避免任务太多把 I/O 饿死。任务来源包括 execute、schedule、scheduleAtFixedRate 和跨线程提交的写任务。

优雅退出时，shutdownGracefully() 设置状态，confirmShutdown() 在循环里检查是否还有任务，canSuspend() 还会检查 numRegistrations == 0。这解释了一个常见现象：只调用 shutdownGracefully() 而不关闭 Channel，EventLoop 可能不会立刻退出，因为还有注册的 Channel。

confirmShutdown 的逻辑比想象中复杂：

三个参数：

  • quietPeriod：没有任务之后，还要等多久才退出，用来兜住“关掉之后还有任务提交”的情况；
  • timeout：整个优雅关闭的最长时间，超过就强制退出；
  • shutdown()：不等待，直接标记为关闭。

runAllTasks() 在关闭阶段还会执行已提交的任务，所以 shutdownGracefully() 之后提交的任务可能仍被执行。业务要把“停止接收新任务”和“等待已有任务完成”分开处理。

canSuspend() 是 4.2 新增的挂起机制：没有注册的 Channel、没有任务、没有定时任务时，线程可以挂起而不是空转。这也是 4.2 相对 4.1 的一个运行效率改进。

EventLoopWalkthrough 不直接打印源码内部状态，而是从外部观察：线程名、任务执行顺序、inEventLoop()、定时任务延迟。它和源码对照，能确认“任务确实在 runAllTasks 阶段执行”。

传播

Context 链表与两个方向

Pipeline 内部是 AbstractChannelHandlerContext 的双向链表，head 和 tail 是两个哨兵。每个 Context 记录 handler、executor、executionMask，以及前后指针。

  • 入站：findContextInbound 从 next 往后找，跳过不处理入站事件的 Handler；
  • 出站：findContextOutbound 从 prev 往前找，跳过不处理出站事件的 Handler；
  • 如果下一个 Handler 的 executor 不是当前线程，事件会被投递到它的 executor 执行。

skipContext 里有一个细节：只有“executor 相同且 mask 不匹配”才跳过；executor 不同时不能跳过，否则会破坏 handler 的执行顺序。这是业务线程组场景下的关键逻辑。

ChannelFuture 与 Promise 的区别

Future 是只读的结果，Promise 是可写的 Future。Netty 里：

解码器源码

ByteToMessageDecoder.channelRead

ByteToMessageDecoder 是帧解码器的基类。它的 channelRead 做四件事：

  • 第一次读时 cumulation 为空，把输入直接作为累积区；
  • 之后每次把新读到的 ByteBuf 追加到 cumulation；
  • 调用 callDecode 尝试解码；
  • 如果 cumulation 没有可读字节，释放并置空；否则每 16 次读后 discardSomeReadBytes()，避免累积区无限增长。

fireChannelRead 会把 out 里的消息逐个传给后面的 Handler。如果 out 里有多个消息，一次 channelRead 就会触发多次下游 channelRead。

cumulation 的三种处理

ByteToMessageDecoder 的累积器不是每次都拷贝。它有两种 Cumulator：

  • MERGE_CUMULATOR：把新 ByteBuf 合并到旧 cumulation，必要时扩容；
  • COMPOSITE_CUMULATOR：把多个 ByteBuf 组合成 CompositeByteBuf，尽量避免拷贝。

默认用 MERGE_CUMULATOR，因为大多数协议帧不大，连续内存对后续解析更友好。first 为 true 时直接把输入当 cumulation，省掉一次拷贝；之后才走合并逻辑。

累积区什么时候释放？

  • cumulation 没有可读字节：释放并置空，下一轮重新开始；
  • 还有可读字节：每 discardAfterReads（默认 16）次读后 discardSomeReadBytes()，把已经读过的部分丢掉，避免 cumulation 无限增长；
  • discardSomeReadBytes() 只移动 readerIndex/压缩内存，不改变未读数据。

discardAfterReads 不是“每 16 个字节”，是“每 16 次 channelRead”。所以一个只发了半帧、之后长时间没数据的连接，cumulation 会一直保留那半帧，直到有更多数据或连接关闭。这是半包场景的正常行为，不是泄漏。

解码器的释放责任

ByteToMessageDecoder 只负责 cumulation 的释放，不负责 out 里消息的释放：

  • decode 里 out.add(...) 的消息，所有权交给下游 Handler；
  • 下游如果是 SimpleChannelInboundHandler，它自动释放；
  • 下游如果是 ChannelInboundHandlerAdapter，业务必须自己释放；
  • 如果 decode 抛异常，尚未交给下游的 out 消息由解码器/异常路径释放。

自定义解码器最常见的泄漏是：在 decode 里 readBytes 出一个新 ByteBuf，既没 out.add，也没 release。只要记住“要么交出去，要么释放”，就能避免大部分问题。

  3. 它是有状态的，每个 Channel 一个实例，不能加 @Sharable。
  4. FullHttpRequest 的 content 是一个 ByteBuf，业务处理完要释放；SimpleChannelInboundHandler<FullHttpRequest> 会自动释放。

HttpObjectAggregator 的源码在 codec-http 模块，和 HttpObjectDecoder 一起，构成了“字节流 → HTTP 消息 → 完整请求”的两级转换。

HttpObjectAggregator 还会处理 Expect: 100-continue、请求体超过上限时的 413、以及部分非法请求。它是有状态的，不能加 @Sharable；每个 Channel 需要独立实例。

Chunk、Page 与 Subpage

PoolChunk 是一块 4MB 的连续内存，按 8KB 的 Page 切分。PoolChunk 用一棵完全二叉树（memoryMap）记录每个节点的分配状态：

  • 叶子节点对应 Page；
  • 非叶子节点记录子树的空闲状态；
  • 分配 Page 时从根往下找第一个足够大的空闲节点；
  • 释放时把节点标记回空闲，并向上合并。

小对象（小于一个 Page）不会直接占一个 Page，而是走 PoolSubpage：把一个 Page 再切成固定大小的槽位，用 bitmap 记录哪些槽位被占用。PoolSubpage 适合 tiny/small 对象，避免每个小 ByteBuf 都浪费 8KB。

PoolArena 的 PoolChunkList 按使用率把 Chunk 分成 qInit、q000、q025、q050、q075：

  • qInit：新分配或几乎全空的 Chunk；
  • q000/q025/q050/q075：使用率逐渐升高；
  • 分配时从 q050 开始找，尽量保持 Chunk 的使用率在中间区间；
  • 释放时按使用率把 Chunk 移到合适的链表，必要时合并/回收。

这套设计的目的是减少内存碎片，同时让分配/释放的复杂度保持在可接受范围。业务不需要直接操作这些结构，但是这个解释了，为什么池化分配器的内存占用不是线性的。

Handler 顺序的共同规律

IdleStateHandler、SslHandler、WebSocket、HTTP 的源码都在回答同一个问题：这个 Handler 看到的是字节、帧还是业务对象？

  • SslHandler 看到 ByteBuf（密文/明文），要放在 codec 前；
  • HttpServerCodec 看到 ByteBuf，产出 HttpObject；
  • HttpObjectAggregator 看到 HttpObject，产出 FullHttpRequest；
  • IdleStateHandler 不改变消息，只观察读写时间，放哪一层都可以，但通常放最前面；
  • 业务 Handler 看到的是解码后的对象。

顺序错了，拿到的类型就不对，通常会在 ClassCastException 或解码异常里体现。

启动失败时的关闭路径

不是所有 Channel 都会走到完整的 close 流程。启动阶段失败有三种情况：

  1. channelFactory.newChannel() 抛异常：initAndRegister 直接返回失败的 promise，没有 Channel 可关；
  2. init(channel) 抛异常：channel.unsafe().closeForcibly()，只调 doClose()，不触发 Pipeline 事件；
  3. register 失败：如果已经注册，走 channel.close()；否则 closeForcibly()。

doBind0 里还有一个 ChannelFutureListener.CLOSE_ON_FAILURE：bind 失败会关闭 Channel。这个 listener 是启动失败时最常见的“自动清理”入口。

closeForcibly 和 close 的区别：

  • closeForcibly() 只调 doClose()，不保证 channelInactive/channelUnregistered；
  • close() 走完整流程，失败 pending 写、触发 inactive、deregister、unregistered。

所以启动失败时不要假设业务 Handler 一定收到 channelInactive；如果要清理资源，最好在 initAndRegister/bind/connect 的失败 listener 里做。

ChannelPipeline#addLast(EventExecutorGroup, handler) 4.2 已 deprecated 推荐手动 dispatch，或直接使用 MultiThreadIoEventLoopGroup
NioEventLoop 内部 invokeChannelRead/invokeWrite0 4.2 的 Pipeline 做了 flatten，事件分派直接在 fireXxx/write 里完成 旧文章里的“invoke 方法”在 4.2 可能找不到
SslHandler 对 NioSocketChannel 的类型判断 4.2 的 setOpensslEngineSocketFd 会 instanceof UnixChannel classpath 缺 netty-transport-native-unix-common 时会 NoClassDefFoundError
WebSocketClientProtocolHandler 的握手回调 4.2 的构造/回调有变化 很多场景直接用 WebSocketClientHandshaker 更稳

读旧文章时，先确认它讲的类在 4.2 里是否还存在；如果不存在，找对应的新类，不要硬套方法名。

注意

  1. “handlerAdded 一定在 addLast 返回前执行”：错。Channel 未注册、或当前线程不是 Context 的 executor 时，handlerAdded 会延迟。
  2. “channelRead 一定在 EventLoop 线程”：只有 Channel 注册的 EventLoop 线程才会；如果 Handler 被挂到独立 executor group，事件会切线程。
  3. “write 成功就是对端收到了”：write 只是入队，flush 才写 Socket，promise 成功只代表本端写缓冲接受。
  4. “tail 不会释放消息”：tail 的 onUnhandledInboundMessage 会 release，未消费的 ByteBuf 不会泄漏，但业务也不该依赖它兜底。
  5. “池化分配器一定更快”：池化有线程缓存、arena 竞争、内存滞留的代价；小对象/低分配场景 unpooled 可能更简单。
  6. “4.2 和 4.1 只是版本号”：EventLoop、Pipeline flatten、SslHandler 依赖、WebSocket 客户端 API 都有实际变化，照搬旧代码会踩坑。
