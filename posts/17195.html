如何实践OAuth2

前言

从授权服务器的搭建、客户端的配置，到令牌的生成与验证，Spring Security OAuth2 等组件已将协议细节封装为可复用的接口与注解，让开发者无需深入钻研协议底层，即可快速实现 “用微信登录自研系统”“用 GitHub 账号接入企业平台” 等场景。

正好，我的项目需要引入第三方登录，我们以 github 第三方登录为例子，来在 Spring Security 中使用 OAuth2

至于为什么不用微信，QQ，钉钉等这种国内更常用的，你可以去看看，申请这些东西有多复杂，不仅需要整体的备案，还需要上线服务，显然，对于第三方登录的实践，国内平台是不太合适的

有空我也想使下 OSU！的三方登录））

先给大家看一下基本的项目结构

OAuth2的第三方登录的业务应该如何设计

那么，最重要的部分就是 OAuth2 业务如何设计

在老式的设计中，开发人员可能会在 User 表里加 google_id, github_id 字段。

我个人认为这是极其糟糕的设计，因为你无法预知未来要接多少家第三方。

但是实际上，这种方法也可能是好的，如果在不会接入太多是三方登录的情况下，这样还会保证其数据库不会太多跨表查询

我个人倾向于采用“主账号 + 绑定关系”的模式：

  1. User 表 (主账号)：只存储属于你平台的唯一身份（ID、昵称、头像、注册时间、状态）。
  2. UserConnection 表 (第三方关联)：存储 user_id 与 provider (如 Google) + provider_user_id (OpenID) 的对应关系。

所以，我们需要两张核心表，也就是 平台主用户表 和 第三方绑定表，第三方绑定表是专门用于 OAuth2 关联的表。

那么，实际产生的业务应该如何设计呢？

如果用户是第一次来（纯新人），它没有该平台的账号，期望直接点“使用 GitHub 登录”进行三方登录

那么，Spring Security 应该引导用户去 GitHub 授权 -> 回调拿到 UserInfo。然后用 GitHub 返回的 sub (OpenID) 去 sys_user_social 查。结果发现查不到记录，那么此时就有两种策略

  • 静默注册：

    系统自动在 sys_user 创建一个新账号。

    • Username: 如果能获取到，就是用用户在第三方平台的用户名，如果获取不到，按照特定规则设计一个随机字符串作为临时的用户名。

    • Email: 使用 GitHub 返回的邮箱，如果有，这个通常能够获取到

    • Avatar: 使用 GitHub 头像。

    • Password: 空 (或者生成一个随机密码并不告诉用户)。

      • 那么问题来了，一直让用户的密码空着，这可以吗？如果纯OAuth2用户注册进入平台日后希望使用平台进行登录注册，怎么办？

      • 实际上，这是业务的设计特性，有密码代表用户可以通过“账号/邮箱 + 密码”的方式进行表单登录。无密码代表该账号不支持表单登录，仅支持第三方登录或验证码登录。

        因为在 Spring Security 层面，当用户尝试用空密码登录时，校验逻辑（PasswordEncoder.matches）会直接失败，天然保证了安全性。没有密码不代表不安全，而是代表该通道关闭。

      • 那么如果用户一开始嫌麻烦用了 GitHub 登录，后来觉得还是设置个密码稳妥，或者想在不支持 GitHub 登录的设备上登录，那么业务如何设计？其实通过通过“忘记密码”流程找回是最合适的。

    在 sys_user_social 插入一条记录，关联新生成的 user_id。

    执行登录

  • 强制绑定：

    跳转到一个中间页：“您是新用户，请完善账号绑定”或“关联已有账号”。

    这种体验较差，现在主流 App 多采用策略 A，进去后再引导绑定各种需要的内容。

那么，还有一个场景，就是用户之前有账号（邮箱注册的），现在点“使用 GitHub 登录”，那么如何保证，用户使用OAuth2登录进去的是对应用户希望登录的账号，邮箱匹配逻辑如何思考

首先。流程还是获取 GitHub UserInfo。发现用户是第一次使用OAuth2登录，查不到 GitHub 的绑定记录。此时，应该使用一些策略保证能够正确关联，我们通常先检查 GitHub 返回的 email 是否存在于 sys_user 表中。

  • 情况 A：Email 匹配成功（GitHub 邮箱 = 平台邮箱）。

    • 系统判定这是同一个人。

    • 自动在 sys_user_social 插入一条记录，将 GitHub ID 绑定到那个已存在的 user_id 上。

    • 执行登录。

  • 情况 B：Email 不匹配（或者 GitHub 没返回邮箱）。

    • 系统无法判断这俩是不是同一个人。

    • 处理：这会被视为一个新用户（走上面场景中静默注册的逻辑）。用户会获得一个新的账号

    • 结果：用户会有两个账号（一个邮箱账号，一个 GitHub 账号）。

那么这样肯定是不行的，这样会不小心为用户创建很多小号，也就是，我在平台注册用a@test.com，GitHub 用 b@test.com。

所以，应该有这样的一个逻辑，用户已登录，可以在“个人中心”手动绑定自己关联的第三方平台账号，实现手动合并

  • 用户已用账号 A 登录。
  • 点击“绑定Github”。用户选择了自己的Github邮箱进行绑定，其中，这里无论OAuth2提供商给的邮箱和用户在该平台注册的账号的邮箱是否相同，都不影响，因为这样就认为了用户强行绑定了这个OAuth2提供商账号就是自己的
  • OAuth 流程结束后，拿到 Github OpenID
  • 需要有一个校验，查 sys_user_social，看这个微Github OpenID 是否已经被其他用户绑定了？
    • 如果已绑定：提示“该 Github 账号已被其他账号占用，请先解绑”。
    • 如果未绑定：在 sys_user_social 插入 {user_id: A.id, provider: ‘wechat’, …}。

通过OAuth2.0实现Github第三方登录

在 Spring Security 5+ / 6+ 中，主要通过自定义 DefaultOAuth2UserService 来实现上述逻辑。

模块设计

首先，从我们的项目结构看，zhiyan-common-* 系列模块都是提供通用能力的，而 OAuth2 作为通用的认证协议，适合抽象到 common 层，然后auth模块依赖 zhiyan-common-oauth 最后在其中完成全部的OAuth2三方登录的内容

这样，OAuth2 的核心逻辑（协议交互、token 管理）与具体业务解耦且逻辑清晰

  • zhiyan-common-oauth: 纯技术实现，不涉及业务
  • zhiyan-auth: 业务逻辑，用户管理、绑定关系等

这样的设计易于之后扩展新的服务提供商

数据库表设计

那么，为了应对新出现的业务，我们需要设计新的数据库表，我们需要设计一个OAuth2用户绑定关系表

这个仅供参考，但是大部分还是通用的

我实际项目设计的表是这样的，所以说，实体类和其持久层照着写就差不多

配置类

实际上，开发 OAuth2 貌似不需要特意引入新的 OAuth2 依赖

但是，该有的配置类肯定要有

首先，肯定要定义有哪些内容需要写道配置文件中，根据这个写配置类，我习惯先写总配置属性，再写各个厂商的单独的自己的配置属性

再写自动配置类，统一初始化 OAuth2 相关的核心 Bean，然后绑定自定义的 OAuth2 配置属性，再将所有实现OAuth2Provider接口的第三方登录提供商收集，方便后续根据提供商名称快速获取对应的实现类。

这个自动配置类是自定义 OAuth2 框架的初始化入口，负责注册 HTTP 工具 Bean、管理第三方登录提供商的实例映射。

模块化可插拔配置的管理就完成了，然后自己根据需要的内容，在配置文件中进行对应配置项目的编写就可以了

申请Github的OAuth app

https://github.com/settings/applications/new

这里除了最后一项Authorization callback URL，其它内容对后续的代码处理都没有影响(用于用户点击第三方登录时展示网站的信息)

在本地实现 GitHub OAuth2 登录时，这两个地址的填写需结合你的项目启动端口和 Spring Security OAuth2 的默认回调路径来配置：

  • Homepage URL：填写你本地项目的主页地址，例如若你的项目在本地以 8080 端口启动，可填写 http://localhost:8080。等上线了再换回来真实的域名就可以

  • Authorization callback URL：这是回调地址，GitHub 在用户完成授权后，将用户重定向回你项目的地址，同时会附带授权码（code）。这个地址是 OAuth 2.0 授权流程的关键环节 —— 后端需要通过这个地址接收授权码，再换取用户的 Access Token，最终完成登录。

    这个地址存在一个填写规则，填写规则是：你的项目域名/login/oauth2/code/github，因为login/oauth2/code/github 是Spring Security OAuth2 的默认回调路径（github 是你注册的客户端标识），后端会自动监听这个路径来处理 GitHub 的授权回调。

    你需要在后端的这个路径，完成一个处理临时授权码code的接口

这样配置后，GitHub 会在用户授权后，将请求正确重定向到你本地项目的 OAuth2 回调处理端点，从而完成登录流程。

注册完毕获取 clientId 和 client Secret，这些内容是需要填写到配置文件的

通常情况下，本地和线上是会分开配置的

编写OAuth2组件之第三方登录提供商服务

这部分代码是做什么呢？他们需要构成一个符合设计模式的 OAuth2 客户端集成框架，在 OAuth2 业务逻辑中扮演着“驱动程序”的角色，负责与不同的第三方平台（如 GitHub、Google、Gitee 等）进行协议对接。

首先，编写一个OAuth2Provider (接口) ，定义标准，定义了一个 OAuth2 提供商必须具备哪些核心能力，用于屏蔽底层差异，对于业务层（如 LoginService）来说，它们都是一个 OAuth2Provider。这样编写符合开闭原则

然后，我们需要拥有一个AbstractOAuth2Provider (抽象基类)，用于流程复用，它控制并实现了 OAuth2 标准流程中通用且重复的代码。因为 OAuth2 的授权码模式（Authorization Code Grant）流程在大多数平台下是标准的（拼接 URL -> 请求 Token -> 请求 UserInfo）。通过这个抽象类，我们不需要为每个新平台重写网络请求逻辑，实现了代码的 DRY (Don’t Repeat Yourself) 原则。

最后，为Github平台编写具体的实现，进行特性的定制，GithubOAuth2Provider，因为每个平台的返回数据格式（JSON 结构）、特殊的权限控制（如 GitHub 隐藏邮箱）都不同。此类专门解决这些“最后一步”的差异。

可以看到 Github 比较特殊，所以，你获取到邮箱的策略需要进行修改，来确保能够应对不同的情况

编写OAuth2组件之Client通信层

Client 这部分差不多就是核心调度层（Manager层），编写这部分是希望屏蔽不同三方平台带来的差异，对外给你的 Controller 或 Service提供统一的操作接口，属于 OAuth2 基础设施。

Controller 层只需要调用 OAuth2Client 的方法，而不需要关心具体是去连 GitHub 还是 Google，也不用关心 State 怎么存取。

首先，Client 中需要有什么呢？分析一下，OAuth2 登录必须做的其实只有两件核心大事，拆解成接口中这样的两个方法

  • getAuthorizationUrl：
    • 作用：这是第一步。用户点击“GitHub登录”时，后端需要生成一个 URL（比如 https://github.com/login/oauth/authorize?client_id=xxx…）给前端，让前端跳转过去。
  • getUserInfoByCode：
    • 作用：第二、三步。用户在 GitHub 授权后，跳回你的平台带了一个 code。这个方法负责用 code 换 token，再用 token 换 用户信息。
