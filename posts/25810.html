Web 实时消息推送的两种方案：WebSocket 与 SSE

在接触服务端消息主动推送的时候，做业务遇到需要一个”新消息提醒”、“订单状态变化”、“进度条实时更新”这种，其实第一反应是加一个定时器轮询接口。但是很明显，在你的业务压力不是很大的时候，这种方式会白白浪费很多宝贵的系统资源。。。因此，在一个事件完成之后，服务端主动推送消息是很有必要的。

从轮询到推送，实时消息到底难在哪

HTTP 的本质就不支持服务器主动说话

要理解实时推送难在哪，得先接受一个有点反直觉的事实：HTTP 从设计之初就不是为了”服务器主动找客户端”而生的。

在经典的 HTTP 请求响应模型里，通信永远是客户端发起的：

这个模型有三个隐含前提：

  1. 通信由客户端发起，服务端只负责应答；
  2. 服务端处理完就忘掉这次连接，不保证还有下一次；
  3. 服务端手里没有一张”当前在线的客户端”名单，它无法主动构造出一个响应。

于是矛盾就出现了：业务上我们需要，服务端有新数据时立刻告诉客户端，这样的时候，但协议层面服务端根本没有一条现成的路可以走。

历史上为了绕开这个矛盾，工程师们想出了一系列曲线救国的办法，它们构成了实时推送技术的完整演进阶梯。

短轮询

其实，短轮询最致命的其实是第一条。每一次轮询都是一次完整的请求响应周期

而如果你为了省资源把间隔拉长到 30 秒，那么最坏情况下要等 30 秒才看到新消息。这就是短轮询的问题：实时性和资源消耗只能二选一，没有中间地带。

长轮询

长轮询（Long Polling）是第一次真正意义上的改进。它的思路是把短轮询中立刻返回空的响应，改成了请求先挂住，等到有数据或者超时再返回。

sequenceDiagram
    participant C as 客户端
    participant S as 服务端
    C->>S: GET /api/messages/poll
    Note over S: 没有新数据，把请求挂起（不返回）
    Note over S: ...等待中...
    S-->>C: 数据到达，返回响应
    C->>S: 立即发起下一次 GET
    Note over S: 再次挂起

它带来的收益非常明显，空响应的次数大幅减少。没有新数据时，请求一直挂在服务端，不消耗带宽也不浪费序列化开销。延迟也降下来了，因为一旦有数据，响应是立刻推出去的，客户端收到后又马上发起下一轮，这是一种近实时方案。

但长轮询引入了新的复杂度，而且这些复杂度都不好处理：

  • 连接状态变成了业务状态。 服务端必须为每个挂起的请求保存一个”待唤醒”的句柄，还要给它配上超时时间。
  • 超时与重连的边界很微妙。 超时时间设得太短，请求会不断返回空响应，退化成短轮询；设得太长，中间的代理会先替你断掉（nginx 默认 60 秒，见后文）。
  • 重连风暴。 服务端一旦重启或抖动，所有挂起的连接会在同一瞬间断开，然后客户端会在同一瞬间重新发起连接，形成一波新的压力峰值。
  • 仍然不是真正的推送。 每次收到数据后都要重新建一次请求，请求头、鉴权、路由全部重来一遍。

HTTP 流式推送能做到一次请求，持续输出

再往前一步就是 HTTP 流式推送（HTTP Streaming）。既然长轮询的问题是每次都断开重连，那就不断开：服务端返回一个永不结束的响应，用分块传输的方式持续往同一个连接里写数据，客户端边读边解析。

这一次，一个连接对应一整条会话，请求头只发一次，鉴权只做一次。这就是 SSE 的技术底座。

不过裸的 HTTP 流式推送也是有问题的：响应体是什么格式？客户端怎么切分消息？断线了怎么知道断在哪里？这些如果不统一约定，就是各个团队自己造轮子。

SSE 把这个做法标准化了。 它规定了两件事，一是 MIME 类型必须是 text/event-stream，二是事件流必须遵循一份严格的 ABNF 语法；再加上浏览器原生提供的 EventSource 接口，把连接管理、消息解析、断线重连这一整套规范都定下来了。

WHATWG 规范对它的定位说得很直白，我用中文讲一下大意：这套东西存在的目的，是让服务器能够通过 HTTP（或者专门的服务器推送协议）把数据推给网页，为此规范引入了 EventSource 这个接口。 换句话说，它不是发明了新的传输方式，而是给”服务端往浏览器推数据”这件事定了一套标准的做法。

WebSocket 与 SSE 是两条完全不同的设计路线

走到这里，实时推送已经分裂成了两条路线，它们的设计哲学完全不同：

WebSocket 认为 HTTP 不适合双向通信，那就在 HTTP 的基础上做一次”协议升级”，之后脱离 HTTP，用自己的帧格式进行通信。 它的目标是真双向、低开销的实时通信。

SSE 认为 HTTP 已经够用了，问题只是缺一个格式约定和客户端 API，那就把它标准化。 它要解决的是服务端到客户端的单向高效推送。

这两个东西都是实打实的标准：

方案 标准来源 标准化时间 传输层
WebSocket IETF RFC 6455（Proposed Standard） 2011 年 12 月 独立协议，借 HTTP 完成握手
SSE WHATWG HTML Living Standard 第 9.2 节 随 HTML 标准持续演进 就是 HTTP

WebSocket 的设计目标也很明确：为浏览器应用提供一种不依赖多条 HTTP 连接的双向通信机制。

这个协议要解决的，是让一段运行在受控环境里的不可信客户端代码，能和一个”同意接受这段代码通信”的远端主机之间建立双向通信；它采用的安全模型，是浏览器世界里通用的那套基于来源（Origin）的模型。

这句话里有两个信息值得留意，一是它明确假设客户端代码是不可信的，所以后面才会有掩码、Origin 校验这些设计；二是它把安全责任交给了 Origin 模型，这正是它和普通 HTTP 接口最大的不同，后面讲安全时我会展开。

整个协议由两部分组成，一个开场的握手，加上基本的分帧（framing），两者都跑在 TCP 之上。

一条贯穿全文的结论

WebSocket 和 SSE 是两种不同的取舍。

  • 如果客户端只需要被动接收，而你的团队又不想为了一套新协议去改网关、改鉴权、改监控，那么 SSE 几乎是免费的午餐；
  • 如果确实需要客户端频繁上行（聊天、协同编辑、游戏操作），或者消息频率和体量都很大，那 WebSocket 才是那个便宜的选项，因为用 SSE 模拟双向反而更贵。

什么时候不该用 WebSocket，Spring 官方文档在 WebSocket 那一章里给的判断标准，我觉得比大多数博客都靠谱。它说的是这么一层意思：延迟高低本身不是决定性的因素。如果消息量相对较低（比如监控网络故障这种场景），那么 HTTP 流式或轮询就已经是有效的方案了；真正让 WebSocket 成为最佳选择的，是”低延迟 + 高频 + 大流量”这三者同时成立。

提炼成一句就是：光有低延迟需求还不足以让你上 WebSocket，只有三者叠加，才是它最合适的场合。 这个判断标准和前面那条设计哲学是完全一致的。

请求方必须满足的条件

RFC 6455 第 4.1 节用 MUST 逐条规定了客户端的要求。下面这份清单里的”必须”，对应的都是规范里的强制要求，不是建议：

要求 具体内容
方法 必须是 GET，HTTP 版本必须至少 1.1
Host 必须包含主机名，非默认端口时还要带端口
Upgrade 必须包含 websocket 关键字
Connection 必须包含 Upgrade 令牌
Sec-WebSocket-Key 必须是一个随机选取的 16 字节值做 base64 编码，且每连接都必须重新随机
Origin 浏览器客户端必须携带；非浏览器客户端可选
Sec-WebSocket-Version 必须是 13
Sec-WebSocket-Protocol 可选，逗号分隔的子协议列表，按偏好排序
Sec-WebSocket-Extensions 可选，希望使用的协议级扩展

关于 Sec-WebSocket-Key，它的本质是一个每连接唯一的随机 nonce，编码成 base64 只是为了放在 HTTP 头里方便传输，解码之后必须正好是 16 字节。规范特意强调了这个值必须”每个连接都重新随机选取”，不能复用——这一点很重要，因为它决定了这个字段是一个真正的挑战值，而不是某个固定标识。

这里还有一个很容易被误解的点，我在后面讲 Sec-WebSocket-Accept 时会展开：这个 Key 不是用来做认证或加密的，它只是一个”挑战值”。

服务端如何校验：SHA-1 + 固定 GUID

服务端收到请求后，要计算 Sec-WebSocket-Accept。拆开看是三步：

  1. 取客户端 Sec-WebSocket-Key 的原始字符串值（注意，是 header 里那段 base64 文本本身，不是解码之后的 16 字节）；
  2. 拼接上固定的魔数 GUID：258EAFA5-E914-47DA-95CA-C5AB0DC85B11；
  3. 对拼接结果做 SHA-1，得到一个 20 字节的摘要，再对它做 base64 编码，就是 Sec-WebSocket-Accept。

关于那个 GUID，规范给了一句解释，说明为什么它不容易冲突。大意是：这个 GUID 写成了字符串形式，它的取值使得那些”不理解 WebSocket 协议”的网络端点，几乎不可能碰巧用到它。

关键就是这后半句：一个不理解 WebSocket 协议的端点，不可能碰巧把这个 GUID 当成正常数据。 这正是整个握手校验能成立的前提。

用规范里的示例验证一遍，dGhlIHNhbXBsZSBub25jZQ== 经过上述计算得到的正是 s3pPLMBiTxaQ9kYGzzhZRbK+xOo=。这个对应关系是规范的官方向量，可以直接拿来写单元测试。

自己实现时要注意一个细节，因为规范明确说了服务端不需要对 Sec-WebSocket-Key 做 base64 解码，直接拿字符串参与拼接就行。所以服务端只需要校验它的 base64 解码结果是 16 字节，然后按字符串拼接计算摘要即可。

另外，服务端在读取客户端握手时有几项必须验证的内容，我用中文列一下，这样你对照代码时不容易漏：请求必须是 HTTP/1.1 或更高的 GET；Host 头必须包含服务端的 authority；Upgrade 头必须包含 websocket（大小写不敏感）；Connection 头必须包含 Upgrade 令牌；Sec-WebSocket-Key 解码后必须是 16 字节；Sec-WebSocket-Version 必须是 13。这几项里任何一项不满足，服务端就应该停止处理这个握手，返回一个合适的 HTTP 错误码（比如 400）。

为什么一个安全协议会用 SHA-1

SHA-1 早就被弃用了，为什么 WebSocket 握手还在用它？

官方给了很明确的一句话，中文大意是：这个握手不依赖 SHA-1 的任何安全属性，包括抗碰撞性和抗第二原像攻击性。

这句话的分量比它看起来要重。SHA-1 之所以被淘汰，是因为它的抗碰撞性被攻破了，可以构造出两个不同输入得到相同摘要。但 WebSocket 握手根本不需要抗碰撞性：

  • 它要防的不是”有攻击者能构造出碰撞”，而是”有不理解协议的东西碰巧也返回了正确的 Accept”；它防的是误连，真正的安全性来自 TLS（wss://）和 Origin 校验；
  • 而这个校验之所以能成立，靠的是前面那个 GUID 的唯一性，一个不懂 WebSocket 的端点不会把 258EAFA5-E914-47DA-95CA-C5AB0DC85B11 当成自己的正常数据；
  • 所以攻击者就算能算出这个摘要也毫无意义，因为算法是公开的，摘要里没有任何 secret。

换句话说，SHA-1 在这里只是一个便宜的、所有语言都内置的一致性校验函数。

顺带一个值得知道的细节：RFC 8441（HTTP/2 上的 WebSocket）明确说明第 10.8 节不再适用，因为扩展 CONNECT 方案里 Sec-WebSocket-Key 和 Sec-WebSocket-Accept 这套机制被 :protocol 伪首部取代了。

校验失败的行为

规范用一句概括性的话说明了客户端的校验底线，大意是：如果 Sec-WebSocket-Accept 的值和期望值不符、这个头缺失、或者 HTTP 状态码不是 101，那么连接就不会被建立。

而官方逐条列出了客户端必须检查的项，任何一条不满足，客户端都必须让连接失败：

  • 状态码不是 101，就按普通 HTTP 处理；
  • 响应缺少 Upgrade 头，或者值不是 websocket（大小写不敏感）；
  • 响应缺少 Connection 头，或者不包含 Upgrade 令牌；
  • 响应缺少 Sec-WebSocket-Accept，或者值不等于上面算出来的结果；
  • 响应带上了一个客户端没请求过的扩展；
  • 响应带上了一个客户端没请求过的子协议。

最后两条经常被忽略。它们的实际含义是：服务端不能在客户端没同意的前提下擅自启用扩展或子协议。 比如客户端没有请求 permessage-deflate 压缩扩展，服务端就不能自己开——否则客户端解帧会直接错乱。

握手之后的连接状态

握手成功后，底层的 TCP 连接并不会重建，它只是换了一套语言。关键点在于，同一个 TCP socket，握手前说 HTTP，握手后说 WebSocket 帧。 这也是为什么 WebSocket 能复用 80/443 端口、能穿过大部分防火墙，因为它在握手阶段和一个普通 HTTP 请求没有区别。

规范把这个状态命名为”WebSocket 连接已建立（Established）“，并且把此后连接所处的状态称为 OPEN 状态。你在日志里看到这两个词（Established / OPEN），说的就是握手已经走完、双方可以开始发帧了。

按字段逐个拆。

FIN：最后一片标记

FIN 只有 1 个 bit，含义是”这是本消息的最后一个分片”。绝大多数情况下，一个消息就是一个帧，此时 FIN = 1。只有做分片时才会出现 FIN = 0 的中间帧。

规范还补了一句：第一个分片本身也可以是最后一个分片——也就是说，单帧消息本质上就是”只有一个分片的分片消息”，这两种情况在实现上可以统一处理。

RSV1 / RSV2 / RSV3：扩展位

三个保留位，默认必须是 0。如果收到非 0 值，而本次连接又没有协商出能解释这些位的扩展，接收方必须让连接失败。

规范对这三个位的要求是硬性的：除非某个已协商的扩展明确定义了非 0 值的含义，否则它们必须为 0；一旦收到非 0 值而又没有任何扩展能解释它，接收方必须判定连接失败。

这里就能看出 WebSocket 的扩展机制是怎么设计的：扩展就是给这些保留位赋予语义。最典型的例子是 permessage-deflate 压缩扩展，它用 RSV1 表示”本消息的载荷是压缩过的”。

Opcode：4 bit 的操作

规范定义的值如下：

值 含义 类别
%x0 continuation frame（续帧） 数据帧
%x1 text frame（文本帧） 数据帧
%x2 binary frame（二进制帧） 数据帧
%x3-%x7 保留给后续非控制帧 数据帧
%x8 connection close（关闭） 控制帧
%x9 ping 控制帧
%xA pong 控制帧
%xB-%xF 保留给后续控制帧 控制帧

规范对它的定义是：操作码决定载荷数据该如何解释；如果收到一个未知的操作码，接收方必须判定连接失败。 这一点在实现时要严格对待——不能”看不懂就忽略”，那会造成协议状态错乱。

这里有个很好记的规律：操作码最高位为 1 的是控制帧。 所以 0x8、0x9、0xA 的最高位都是 1，它们是控制帧；0x0、0x1、0x2 是数据帧。

MASK：掩码位

一个 bit，表示载荷是否被掩码。规则是不对称的，这一点后面单独讲：

  • 客户端发给服务端的帧，这一位必须是 1；
  • 服务端发给客户端的帧，这一位必须是 0。

Payload length：三种长度的紧凑编码

这是 WebSocket 帧里设计最巧妙的一个字段。它只有 7 个 bit，但要表达的长度可能很大，所以用了转义值的设计：

  • 值在 0-125 之间：这个值就是载荷长度；
  • 值等于 126：后面紧跟的 2 字节（16 位无符号整数）才是真正的载荷长度；
  • 值等于 127：后面紧跟的 8 字节（64 位无符号整数）才是真正的载荷长度；
  • 多字节长度一律按网络字节序（大端）表示。

关于 127 这种情形，规范还加了一条容易被忽略的约束：那 8 字节里最高位必须是 0。 也就是说实际能表达的最大长度是 2 的 63 次方减一，而不是无符号 64 位的满量程。这是一道防止长度字段被滥用的护栏。

规范还有两条硬约束，也就是必须用最少字节数编码。一个 124 字节的载荷不能被编码成 126, 0, 124 这种浪费形式。这条约束的存在是为了防止有人用它做流量放大或者绕过长度限制。

另外，载荷长度统计的是 Extension data + Application data 的总和，所以用了压缩扩展之后，压缩后它算的是压缩后的长度，但应用层拿到的是解压后的长度；所以限流要按应用层长度来限，不然压缩炸弹能直接绕过。

顺便给出长度分界点的实际含义，这在估算帧开销时很有用：

载荷长度 帧头开销（服务端 → 客户端） 帧头开销（客户端 → 服务端）
0 - 125 字节 2 字节 6 字节
126 - 65535 字节 4 字节 8 字节
≥ 65536 字节 10 字节 14 字节

对比一下 HTTP 每次都带几百字节的头部，WebSocket 在高频小消息场景下的开销优势是压倒性的。

掩码机制

  • 掩码密钥是一个 32 位随机值，由客户端选取；
  • 每一帧都必须重新生成，不能复用；
  • 必须来自强熵源，不能是伪随机可预测的；
  • 掩码使用的是异或（XOR）运算，而且不能改变载荷长度。

规范对掩码密钥的要求说得很重：这个密钥必须不可预测，必须来自强熵源，而且某一帧的密钥不能让服务端或代理轻易推断出下一帧的密钥。 它甚至解释了为什么——密钥的不可预测性，是阻止恶意应用”自行挑选线路上出现的字节”的关键。

载荷长度不包含掩码密钥的长度。 那 4 个字节的密钥属于帧头，不占载荷空间，所以掩码不会让数据变长，也不会影响按长度解析。

掩码的变换算法规范写成了一个逐字节的公式：第 i 个字节的变换结果，等于原始字节异或上”密钥里第 i 对 4 取模的那一个字节”。也就是密钥按 4 字节循环使用。

然后，掩码的目的不是保密。 密钥就写在同一个帧里，任何人都能解出来，它提供不了任何机密性。只不过是防止如下的情况发生：

  1. 攻击者先与一个自己控制的服务器建立连接，并在 HTTP 连接上执行 UPGRADE，也就是升级成 WebSocket；
  2. 然后，攻击者通过这个已升级的连接发送数据，而这些数据看起来像是一个针对某个已知资源的 GET 请求；
  3. 部署在中间的不合规代理无法区分这是 WebSocket 帧还是一个新的 HTTP 请求，于是把它当成真实请求转发出去；
  4. 响应被代理缓存——缓存就这样被投毒了。

这不是我编的假设场景，而是规范里记录的一次真实实验。规范说，在这个协议开发期间，有人做过一次实验，演示了一类针对代理的攻击，并且确实导致了部署在真实环境中的缓存代理被投毒。攻击的一般形式就是上面那四步。

这两句话解释了掩码设计的全部逻辑：

  • 掩码的作用是让攻击者无法控制”线路上实际出现的字节”。 他想让第 N 个字节等于某个特定值，就必须让”明文 XOR 随机密钥”的结果等于那个值，而密钥每帧都换且不可预测，这个构造就不可能成功；
  • 威胁模型只是”客户端发送的数据看起来像 HTTP 请求”，所以只需要对客户端到服务端这一个方向做掩码，服务端到客户端不需要。

规范里还有一句很实在的提醒，大意是：即便有了掩码保护，那些不合规的 HTTP 代理，仍然会被”不做掩码的客户端和服务器”投毒。 也就是说，掩码只能保护双方都合规的场景。如果一个不合规的客户端根本不做掩码，那它连的那个不合规代理仍然会被投毒——掩码保护的是整个生态，不是单个连接。

掩码有方向性要求

掩码的方向性在规范里是用强制级别规定的，可以整理成四条：

规则 违反的后果
客户端发给服务端的所有帧必须掩码（无论是否走 TLS） 服务端必须关闭连接，可发 1002 协议错误
服务端发给客户端的帧必须不掩码 客户端必须关闭连接
掩码密钥每帧必须重新随机 视为协议违规
掩码密钥必须来自强熵源 视为协议违规

注意第一条括号里的那句补充：掩码与是否运行在 TLS 之上无关。 有人以为用了 wss:// 就可以省掉掩码，实际上加密和掩码防护的是完全不同的东西，因为 TLS 防的是链路上的窃听者，掩码防的是不合规的中间代理被投毒。两者不能互相替代。

这也解释了为什么用 Java 原生 socket 手写 WebSocket 客户端时，最容易犯的错就是忘记掩码，一对接标准服务端就立刻被 1002 拒绝。

分片与重组代表一条消息可以拆成多个帧

WebSocket 的”消息（Message）“和”帧（Frame）“是两个不同层级的概念。一条应用层消息可以由多个帧拼成，这就是分片。

规范给出的定义是两条，大意如下：未分片的消息，就是单个帧，FIN 位为 1 且操作码不为 0；分片的消息，则先是一个 FIN 位为 0、操作码不为 0 的帧，后面跟着零个或多个 FIN 位为 0、操作码为 0 的帧，最后以一个 FIN 位为 1、操作码为 0 的帧收尾。

翻译成规则就是：

  1. 未分片消息：单个帧，FIN = 1，opcode 不是 0；
  2. 分片消息：第一片 FIN = 0 且 opcode 非 0（用真实类型），后面跟零到多个 FIN = 0 且 opcode 为 0 的续帧，最后以一个 FIN = 1 且 opcode 为 0 的帧结束。

接收方把所有片段的载荷依次拼接，直到遇到 FIN = 1，才算收到完整的一条消息。

规范里给的分片动机，大意是：分片最主要的目的，是允许在”消息刚开始发送时还不知道它有多大”的情况下把消息发出去，而不必先把整条消息缓冲起来。也就是支持流式产出，边生成边发，不用把整条消息堆在内存里。分片的次要用途还有多路复用，把大消息拆碎，让其他消息有机会插进去。

规范还列出了几条必须遵守的约束

约束 具体含义
分片顺序必须保持 一条消息的各个分片，必须按发送顺序交付给接收方
不同消息的分片不能交错 一条消息的分片不得插入另一条消息的分片之间，除非协商了能解释交错语义的扩展
所有分片类型必须一致 一条消息的所有分片类型都相同，由第一个分片的操作码决定
双方都必须支持接收分片和未分片消息 客户端和服务端都必须具备接收这两种形态消息的能力
分片大小任意 对于非控制帧，发送方可以把消息切成任意大小的分片
中间件不得改变控制帧的分片 控制帧不能分片，因此中间件不得试图改变控制帧的分片方式

其中第二条值得特别注意：它意味着在一条消息的分片序列中间，你不能插入另一条消息的分片。 所以说，用分片实现多路复用的可能性是存在的，但是受这条规则约束，实现起来并不简单。

关于控制帧的插入规则，规范说的是：控制帧可以插入到一条分片消息的中间，但控制帧本身不允许被分片；而且接收方必须具备处理”分片消息中间夹着控制帧”这种情况的能力。

还有关于控制帧的一些规则：

控制帧可以插在分片消息的中间，而且接收方必须能处理这种情况。

  • 这个设计的理由规范也写了，用的是 Ping 做例子。大意是：如果控制帧不能被插队，那么当它排在一条大消息后面时，一个 Ping 的延迟就会非常长。所以说，如果控制帧必须排在一条大消息的所有分片之后，那么 Ping 的延迟就会非常长。所以说规范允许它们”插队”，代价是接收方必须能正确处理这种交错。

所有控制帧的载荷长度都必须在 125 字节以内，并且都不允许分片。

  • 125 字节上限适用于所有控制帧（Close、Ping、Pong 三类都是控制帧），而且都不允许分片。

    125 这个数字不是随便取的：它正好让控制帧的长度字段停留在 7 位范围内（0-125），不需要扩展到 16 位或 64 位。这让控制帧永远是定长头部，可以被快速解析和插入。

控制帧：Close、Ping、Pong

WebSocket 定义了三种控制帧，它们是这个协议保持连接健康的全部手段。规范对控制帧的定位是：它们用来传递关于 WebSocket 连接本身的状态，而不是业务数据，并且它们可以插入到分片消息中间。

Close（opcode 0x8）：一次必须成对的握手

Close 帧的设计要点，规范说的是：Close 帧可以带一个 body（也就是帧里的 Application data 部分）来说明关闭原因；如果带了这个 body，那么它的前两个字节必须是一个网络字节序的 2 字节无符号整数，用来表示状态码。

  • 原因文本不保证人类可读，而且客户端不允许把它展示给最终用户，因为服务端可能在里面塞调试信息甚至内部数据；

关闭握手的流程是成对的。如果一个端点收到了 Close 帧，而它之前还没有发过 Close 帧，那么它必须回一个 Close 帧；当双方都完成了”发出”和”收到”Close 的动作之后，这个端点才认为 WebSocket 连接已关闭，并且必须关闭底层的 TCP 连接。服务端必须立即关闭底层 TCP 连接，而客户端应该等服务端来关。另外，应用在发出 Close 帧之后，不得再发送任何数据帧。

提炼成四条：

  1. 收到 Close 且尚未发过 Close，必须回一个 Close；
  2. 双方都完成收发的动作后，连接才算关闭，必须关闭底层 TCP 连接；
  3. 服务端必须立即关闭底层 TCP 连接；客户端应该等服务端先关（这样能避免客户端发出最后一个数据后，服务端还没来得及读就断了）；
  4. 发出 Close 后不能再发任何数据帧。

这个 服务端先关、客户端后关 的顺序设计很实用。它避免了那种经典的 客户端以为发完了就断开，服务端其实还有数据没读到 的竞态问题。

Ping（0x9）与 Pong（0xA）：活性探测

Ping/Pong 的语义很简单，规范的第一条是

  • 收到 Ping 帧之后，端点必须回一个 Pong 帧，除非它已经收到过 Close 帧；而且它应该在条件允许的情况下尽快回复。
  • 收到 Ping 必须回 Pong，除非已经收到了 Close 帧。 回复要尽快。已经进入关闭流程了就不用再回 Pong 了。

Pong 的内容必须与 Ping 一致，作为对某个 Ping 帧的响应而发出的 Pong 帧，它的 Application data 必须与它所回应的那个 Ping 帧的 body 完全相同。这样 Ping 的发送方可以通过载荷匹配来确认这是对我这个 Ping 的回应，而不是别人的。

规范还允许合并应答，这是一个优化。大意是：如果一个端点收到了 Ping，而它之前收到的那些 Ping 都还没回过 Pong，那么它可以选择只为最近处理的那个 Ping 发一个 Pong。如果对端连续发了好几个 Ping，你可以只回最后一个。 这在高频 Ping 的场景下能省掉不少无谓的往返。

最后这条我特别喜欢，因为它把”心跳”和”Ping”解耦了。规范说的是：Pong 帧可以被主动发送，不必有对应的 Ping；这种主动的 Pong 充当一种单向心跳，而且不期望对方回应。完全可以当心跳包用。

官方还说明了 Ping/Pong 的用途定位，大意是：Ping 帧既可以当作保活手段，也可以用来验证对端是否仍然有响应。

然而这两件事在实践中是不同的：保活是为了防止中间代理因为空闲而断连；探测响应是为了发现 TCP 连接看起来还在，但对端进程已经卡死 的情况（半开连接）。

浏览器侧的局限

这里有个实践中的现实问题必须说清楚：浏览器的 JavaScript WebSocket API 不暴露 Ping/Pong。 你在浏览器里拿不到发送 Ping 的能力，也监听不到收到的 Ping。

这带来的实际影响是：

  • 服务端主动发 Ping 是可行的：浏览器会自动回 Pong（这是协议层行为，不经过 JS），服务端据此判断客户端是否还活着；
  • 反过来不行：需要浏览器主动保活时，只能走应用层，发一条自定义的 JSON 心跳消息。

这个差异直接影响了后面的选型结论：WebSocket 虽然有心跳能力，但在浏览器侧你只能依赖服务端发起。 这也是为什么 STOMP 那种”应用层心跳”（发一个 EOL 空行）反而更实用，因为它在应用层，浏览器完全可以控制。

关闭状态码

关闭状态码是排查线上问题的重要线索，而且这里有两个很多人不知道的细节：哪些码不允许发送，以及哪些码其实不是 RFC 6455 定义的。

我把 RFC 6455 第 7.4.1 节定义的码值和 IANA 后补注册的码值分开列，这样不会混淆来源。

RFC 6455 定义的码：

状态码 名称 含义
1000 Normal Closure 正常关闭，建立连接的目的已经达成
1001 Going Away 端点”要走了”，比如服务端下线或浏览器离开页面
1002 Protocol Error 协议错误，端点因协议错误终止连接
1003 Unsupported Data 收到了无法接受的数据类型（比如只懂文本的端点收到了二进制）
1004 Reserved 保留，具体含义未来可能定义
1005 No Status Rcvd 不允许在帧里发送；用于表示”实际上没有状态码”
1006 Abnormal Closure 不允许在帧里发送；用于表示”未发送或接收 Close 帧就异常关闭”
1007 Invalid frame payload data 载荷数据与消息类型不符，比如文本消息里出现非 UTF-8 数据
1008 Policy Violation 收到的消息违反了策略，这是一个通用状态码
1009 Message Too Big 收到的消息太大，无法处理
1010 Mandatory Ext. 客户端专用：期望服务端协商一个或多个扩展，但服务端没有返回
1011 Internal Error 服务端专用：遇到未预期的情况，无法完成请求
1015 TLS Handshake 不允许在帧里发送；表示因 TLS 握手失败而关闭

关于 1010，规范有一句特别说明：这个状态码不会被服务端使用，因为服务端有更直接的做法，它可以干脆让握手失败。所以1010 是客户端专用的，因为服务端如果不同意扩展，它可以在握手阶段直接拒绝，不需要专门发一个 1010。这句话解释了”为什么这个码只有客户端会用”。

顺便说一下 1003 和 1007 的区别，这两个很容易混：1003 说的是”数据类型”不被接受（比如只懂文本的端点收到二进制帧），1007 说的是”数据内容和消息类型不一致”（比如一个文本帧里塞了非法的 UTF-8 字节）。一个是类型层面，一个是内容层面。

IANA 后补注册的码（不属于 RFC 6455）：

状态码 名称 含义
1012 Service Restart 服务重启
1013 Try Again Later 服务暂时过载，请稍后重试
1014 Bad Gateway 服务端作为网关或代理时，从上游收到了无效响应（类似 HTTP 502）

它们是通过 IANA 的 WebSocket Close Code Number Registry 后补注册的扩展码。

除这些已定义的码之外，规范还划了保留区段，我按区段说明它们的用途：

区段 能不能用
0-999 不使用
1000-2999 保留给本协议、其未来修订版，以及那些写在永久且公开可得的规范里的扩展来定义
3000-3999 保留给库、框架和应用使用，这些码直接向 IANA 注册
4000-4999 保留给私有用途，因此不能被注册；可以按双方事先约定来使用

所以说，如果你想给业务定义一个专属的关闭原因，用 4000-4999 区间最省事，因为不需要注册，比如 4001 表示”登录态失效”、4002 表示”被其他设备踢下线”。

最后是关键的使用约束：1005、1006、1015 这三个码不允许作为 Close 帧的状态码发送。

官方对它们用的是同一句措辞：端点不得把这三个值中的任何一个，作为状态码放进 Close 控制帧里发送。 它们的作用是在应用层表示”本地推导出的关闭原因”：

  • 1005：“我收到了 Close 帧，但里面没有状态码”。规范规定，如果 Close 控制帧里不含状态码，那么”WebSocket 连接关闭码”就视为 1005；
  • 1006：“连接被关闭了，而且我根本没有收到过 Close 帧”。规范规定，如果连接已关闭而端点没有收到 Close 控制帧（比如底层传输连接直接断了），那么关闭码就视为 1006；
  • 1015：“因为 TLS 握手失败而关闭”。

在 Spring 里，服务端主动关闭时可以指定状态码。Spring 的 ExceptionWebSocketHandlerDecorator 在处理未捕获异常时，就是用 1011 关闭会话的。Spring 文档对这一行为的描述是，这个装饰器会捕获所有从 WebSocketHandler 方法里逃逸出来的异常，并以 1011 状态码关闭会话，表示服务端错误。

这个默认行为很合理：出错了要让客户端明确知道 是服务端的问题，不是客户端自己发错了。如果你自己实现限流、鉴权失效等逻辑，也应该主动用合适的码关闭，而不是让连接莫名其妙地断掉。

WebSocket 在 HTTP/2 和 HTTP/3 上怎么办？

HTTP/2 因为多路复用的特性，不允许有”连接级”的头部字段和状态码，而 Upgrade、Connection、101 恰好都是连接级的——这与 HTTP/2 的设计前提直接冲突。所以 RFC 8441 另辟蹊径，用 HTTP/2 的扩展 CONNECT 方法（Extended CONNECT）来引导 WebSocket。

它的机制有几个要点。

  • 第一，用 :protocol 伪首部指定目标协议。 规范允许在 CONNECT 请求的 HEADERS 上加一个 :protocol 伪首部，用来指明这条隧道上准备说哪种协议。对 WebSocket 来说，这个值必须是 websocket。和 HTTP/1.1 的 Sec-WebSocket-Protocol 不同，它是单值的。
  • 第二，服务端必须先通告能力。 这就是 SETTINGS_ENABLE_CONNECT_PROTOCOL 设置项，它的取值必须是 0 或 1。规范说，客户端在收到值为 1 的这个设置之后，才可以在新建流时使用扩展 CONNECT。而且发送方不得在已经发过 1 之后，再发送值为 0 的同一个设置项。所以说，一旦开了就不能关，避免能力反复变化造成状态不一致。
  • 第三，握手校验机制被替换掉了。 规范明确说：使用扩展 CONNECT 来引导 WebSocket 的实现，不再处理 RFC 6455 里的 Sec-WebSocket-Key 和 Sec-WebSocket-Accept，因为这套功能已经被 :protocol 伪首部取代了。这很合理：HTTP/2 有自己严格的首部校验机制

同时 Connection、Upgrade、Host 这些头在 HTTP/2 上是不得包含的，而 Origin、Sec-WebSocket-Version、Sec-WebSocket-Protocol、Sec-WebSocket-Extensions 这些仍然沿用。

在 HTTP/3 上，RFC 9220 做了同样的适配。其实在 HTTP/2 单条流上跑 WebSocket”的机制，同样适用于 HTTP/3，只是与 HTTP 版本相关的细节需要单独规定。语义与 HTTP/2 完全一致，SETTINGS_ENABLE_CONNECT_PROTOCOL 的值同样是 0x08。RFC 9220 里还有一条值得知道的细节：如果服务端宣称支持扩展 CONNECT，但收到的请求里 :protocol 是个未知或不支持的值，那它应该回一个 501（Not Implemented）。

HTTP/2 上的 WebSocket 并没有解决 TCP 层队头阻塞，因为一条 WebSocket 会话仍然映射到一条 HTTP/2 流，而所有流都跑在同一条 TCP 连接上。它带来的好处是：

  • 省掉一次独立的 TCP/TLS 连接建立；
  • 让 WebSocket 流量和其他 HTTP 流量共享一条连接，更好地利用连接资源；
  • 在 HTTP/2 环境下不再受 HTTP/1.1 每域名 6 个连接的限制。

SSE 规范与 EventSource

如果说 WebSocket 是另起炉灶，那 SSE（Server-Sent Events，服务器发送事件）就是就地改造。它选择的路线是：不改变 HTTP 的传输方式，只在 HTTP 之上定义一套严格的消息格式和客户端 API。

MIME 类型与编码

SSE 的规范开篇就定死了两件事：事件流格式的 MIME 类型是 text/event-stream，而且这种格式的事件流必须始终以 UTF-8 编码。

  • MIME 类型必须是 text/event-stream；
  • 必须是 UTF-8 编码，没有其他选择。它还规定解码时用的是标准的 UTF-8 解码算法

响应必须是 200 且 Content-Type 正确

这一条是 SSE 服务端最基础的硬性要求，规范里的原意是：如果响应的状态码不是 200，或者响应的 Content-Type 不是 text/event-stream，就判定连接失败。这不是重试，而是失败

而这个机制恰好解释了一个非常好用的技巧，用 204 让浏览器停下来。如果服务端返回 204 No Content，浏览器就不会再重连，并且会把 readyState 置为 CLOSED。

这是 SSE 一个非常好用但常被忽略的能力。因为客户端会在连接关闭后重连；而服务端可以用 HTTP 204 No Content 这个响应码来告诉它不要再重连了。但是其实，任何非 200 响应都会让浏览器放弃重连。所以说，不要用 5xx 来表达”暂时不可用”。如果你在服务端限流时返回 503，浏览器不会重试，而是彻底放弃。如果你希望客户端重试，正确的做法是建立连接后立刻关闭，这会触发正常的重连流程。

重定向

规范里说：事件流请求可以像普通 HTTP 请求一样，用 HTTP 301 和 307 重定向。

301 和 307 重定向都是支持的，行为和普通 HTTP 请求一致。这里要留意 301 是永久重定向，浏览器可能缓存它；滚动发布时用 307 更安全。

其中，事件源的 origin 取的是重定向之后最终 URL 的 origin。规范明确说是重定向之后的 URL。如果你把 SSE 从 a.example.com 重定向到 b.example.com，那么客户端收到的事件 origin 就是 b.example.com，跨域校验也按这个来。

readyState 的三个状态

EventSource 的 readyState 有三种状态，它们的含义在规范里定义得很清楚：

常量 数值 含义
CONNECTING 0 连接尚未建立，或者曾经关闭、用户代理正在重连
OPEN 1 连接已打开，正在派发收到的消息
CLOSED 2 连接已关闭且不会重连（发生致命错误，或调用了 close()）

这里有个重要的实践价值：readyState 是区分临时抖动和请求真的寄了的唯一手段。

  • 如果是 0，说明浏览器正在自动重连，你什么都不用做；
  • 如果是 2，说明这次是真的不重试了，通常是因为服务端返回了 204，或者调用了 close()。

EventSource 还提供了 close() 方法，它的作用是中止所有为这个对象发起的 fetch 过程，并把 readyState 置为 CLOSED。注意它和 浏览器自己判定连接失败 的效果是一样的，都是进入 CLOSED，都不会再重连。

重连算法与 Last-Event-ID

SSE 规范里定义的重连状态是这样的：一个”重连时间”（单位毫秒），它初始必须是一个由实现决定的取值，很可能在几秒这个量级；还有一个最后事件 ID 字符串，它初始必须是空字符串。

注意两点：

  • 初始重连时间是实现自定义的，规范只给了个大概范围：大概几秒量级；
  • 初始的 last event ID 是空字符串。

而重连的完整步骤，规范是这么写的：

  1. 排队一个任务：如果 readyState 已经是 CLOSED 就中止；否则把 readyState 设为 CONNECTING，并派发一个 error 事件；
  2. 等待一个等于重连时间的延迟；
  3. 可选地再等一会儿。 如果上一次尝试失败了，用户代理可能会引入一个指数退避的延迟，以避免给一个可能已经过载的服务器雪上加霜；另一种情况是，如果操作系统报告当前没有网络连接，用户代理可能会等操作系统通告网络恢复之后再重试；
  4. 等前面那个任务执行完；
  5. 排队一个任务：如果 readyState 不是 CONNECTING 就返回；否则如果 last event ID string 非空，就把它以 UTF-8 编码后设置为请求头的 Last-Event-ID，然后重新发起 Fetch。

不要用 IP 地址关联连接和用户

想把多个事件源连接互相关联、或者把连接和之前提供的某个文档关联起来的作者，可能会发现依赖 IP 地址是行不通的，因为单个客户端可能有多个 IP 地址（它走了多个代理服务器），而单个 IP 地址也可能对应多个客户端（它们共用一个代理服务器）。更好的做法是在提供文档时给它带一个唯一标识符，然后在建立连接时把这个标识符作为 URL 的一部分传过去。

因为单个客户端可能有多个 IP（走了多级代理），单个 IP 也可能对应多个客户端（共享出口）。 所以：

  • 不要用 IP 做 SSE 会话的唯一标识；
  • 不要用 IP 做限流维度的唯一依据（会把同一个公司出口后面的所有用户当成一个人）；
  • 正确做法是在页面渲染时生成一个唯一标识，建立 SSE 连接时作为 URL 参数带上。

这个建议不仅对 SSE 成立，对 WebSocket 的会话管理同样成立，对其他的类似的会话管理也是这样。

MDN 的 EventSource 文档页也给出了数字 6，并且明确了它的作用域，大意是：这个限制是按”浏览器 + 域名”计的，也就是说你可以跨所有标签页对 www.example1.com 打开 6 条 SSE 连接，同时对 www.example2.com 再开 6 条，也就是这个配额是跨标签页共享的。所以：

  • 用户开 6 个标签页，每个标签页都建一个 SSE 连接，配额就满了；
  • 第 7 个标签页的 SSE 连接会被排队阻塞，页面看起来”卡住了”；
  • 更糟的是，这些被占用的连接会挤压该域名下其他普通 XHR 请求的配额，导致整个站点都变慢。

MDN 还给出了 HTTP/2 下的情况，使用 HTTP/2 时，同时打开的 HTTP 流数量上限由服务端和客户端协商决定，默认是 100。

所以说 HTTP/2 下不再有 6 连接的限制，取而代之的是”并发流的数量”，默认 100 且在服务端和客户端之间协商。这也是把 SSE 部署在 HTTP/2 网关后面的一个额外收益。

规避手段一般这样：

  1. 在同一个标签页内复用同一个 EventSource 全局实例（最简单也最有效，用 event 字段区分业务类型）；
  2. 用 SharedWorker 在所有标签页之间共享一个 EventSource（规范明示的方案）；
  3. 升到 HTTP/2（不改代码就能缓解）；
  4. 为每个连接使用不同域名（规范说这个机制”相对复杂”，一般不建议）。

一般情况下第一条是必须做的，因为绝不因为”页面上有三个模块需要实时数据”就开三条 SSE 连接。

HTTP 语义的保留

如果只能记住一条差异，我建议记住这条。

SSE 是一个普通 HTTP 响应。 这句话听起来平淡，但它的工程含义非常巨大：

  • 鉴权体系完全不用改。 你的 JWT 拦截器、Session Cookie、网关的认证过滤器，全都原样生效，因为这就是一个 GET 请求。
  • CORS 机制原样生效。 跨域时配置 Access-Control-Allow-Origin 就行，和普通接口一模一样。
  • HTTP 状态码语义可用。 401 拒绝连接、403 无权限、204 让客户端停止重连、307 重定向到另一个节点——这些在 SSE 里都是优雅且标准的表达方式。
  • 网关、日志、监控不用动。 访问日志里能看到这个请求，APM 能追踪它，压测工具能打它。

而 WebSocket 握手之后，这一切都消失了：

  • 握手完成后连接里流动的就不再是 HTTP 了，标准 HTTP 中间件看不到”请求”，只看到一堆字节；
  • 你的 Spring Security 过滤器链只在握手那一次执行，之后的消息不会再经过它——这就是为什么 Spring Security 需要专门提供 @EnableWebSocketSecurity 和 ChannelInterceptor 来做消息级授权；
  • 网关需要显式配置才能正确转发升级请求，配置错了会静默降级成普通 HTTP 导致连接失败；
  • APM 工具通常看不到 WebSocket 里的”逐条消息”，只能看到连接建立和关闭。

Spring Security 官方文档里有一句很关键的说明：Spring Security 只保护 clientInboundChannel，它并不试图保护 clientOutboundChannel。它给出的理由是性能，每一条入站消息通常对应多条出站消息；而它给出的建议是：与其去保护出站消息，不如把订阅这个动作保护好。

Spring Security 只管入站消息，不管出站消息。这就是 WebSocket 强大但昂贵的具体体现：你获得了双向能力，代价是要自己重建一整套在 HTTP 里的安全与治理能力。

重连与状态恢复

SSE 的自动重连 + Last-Event-ID 组合，本质上提供了一套消息可靠性原语。

考虑这个场景：用户正在看一个实时订单看板，网络抖动了 3 秒。

用 SSE 时：

  1. 浏览器检测到连接断开，readyState 变成 CONNECTING；
  2. 等待退避时间后自动重连，带上 Last-Event-ID: 10086；
  3. 服务端从 10086 之后的事件开始补发；
  4. 用户端看不到任何异常，数据也没有缺口。

用 WebSocket 时：

  1. 客户端收到 onclose（或者干脆因为网络中断，什么都没收到，只能靠心跳超时发现）；
  2. 你需要在 onclose 里实现退避重连（否则所有客户端会同时重连，打出一波流量尖峰）；
  3. 重连成功后，你需要在应用协议里加一个”同步”消息：客户端告诉服务端”我最后收到的消息序号是 10086”，服务端补发差额；
  4. 这套逻辑你得自己设计、自己实现、自己测试。

这个差异在业务上意味着什么？如果你做的是”通知提醒”、“行情推送”、“进度同步”，这类允许重连后补齐的场景，SSE 省掉的工作量是实打实的。而如果你做的是”聊天”、“实时协同”、“游戏操作”，这类每一帧都要求即时且不可重放的场景，那你需要的是 WebSocket 的低延迟双向通道。

选型方法

我在实践中总结出三个问题，按顺序问下去，基本能确定方向。

第一个问题：客户端需要频繁上行吗？

这是最关键的一刀。

  • 需要：聊天、协同编辑、在线游戏、实时协作白板、远程控制。这些场景的特征是”客户端产生的消息量和时间敏感度与下行相当”，用 SSE 模拟就要在下面再开一条 POST 通道，两条通道的时序无法保证，反而更复杂。选 WebSocket。
  • 不需要：通知、公告、行情展示、任务进度、日志滚动、状态看板。客户端最多偶尔发个”订阅某只股票”的控制指令，用普通 POST 就够了。选 SSE。

上行消息是否需要和下行消息共享顺序保证？如果需要（比如聊天里”我发了一条消息，紧接着收到别人的回复”，顺序必须正确），那么两条独立通道会带来麻烦，WebSocket 更合适；如果不需要，SSE + POST 完全可行。

第二个问题：消息频率和体量有多大？

Spring 官方认为：只有”低延迟 + 高频 + 大流量”三者叠加，才是 WebSocket 最合适的场合。

  • 低频：短轮询就够了，别上长连接。为了一条消息维持一个长连接，成本反而更高。
  • 中频：SSE 最划算。连接开销低、实现简单、有自动重连。
  • 高频大流量：WebSocket 更合适，因为它的帧头开销小（短消息只要 2 字节）、支持二进制（不用 base64 膨胀）、支持 permessage-deflate 压缩。

第三个问题：你的基础设施能承受多大的改造成本？

这是个现实问题，但往往被忽略。

SSE 需要改的：

  • nginx 关掉 proxy_buffering（或者应用返回 X-Accel-Buffering: no）；
  • 调大 proxy_read_timeout 并配合心跳；
  • 容器异步超时时间要设够。

WebSocket 需要改的：

  • 上面全部，再加上：nginx 配置 Upgrade 和 Connection 头转发（如果漏了，连接会直接降级失败）；
  • 负载均衡要支持 WebSocket（四层或七层都要配置）；
  • 鉴权要从 HTTP 过滤器体系迁移到握手 + 消息两层；
  • 监控要新增 WebSocket 会话指标；
  • 如果要做多实例广播，还得引入消息代理。

三个常见误区

最后澄清三个我在讨论中经常遇到的误区。

  • SSE 是过时技术，WebSocket 更先进。

    不是。它们是同一时期（2011 年前后）标准化的两套方案，解决不同问题。SSE 不是”WebSocket 的简化版”，它有自己的独门能力——自动重连和断点续传是 WebSocket 里没有对应物的。而且 SSE 在 HTTP/2 时代反而更有价值，因为多路复用让它彻底摆脱了连接数限制。

  • SSE 只能服务端单向，所以功能弱。

    单向是 SSE 的设计边界，不是缺陷。事实上，绝大多数实时推送需求本质上就是单向的，通知、告警、行情、进度、日志、大屏。强行用双向协议做单向需求，带来的只是额外的复杂度和安全负担。

    而且单向只针对推送通道。你完全可以在 SSE 之外用普通的 REST 接口做上行，这在很多场景下比在长连接里做上行更好：上行天然是请求响应语义，用 HTTP 表达最自然。

  • SSE 是纯文本，所以性能一定比 WebSocket 差。

    这个结论要分场景看：

    • 对于高频小消息，WebSocket 的 2 字节帧头确实优于 SSE 的约 10 字节事件开销，而且 SSE 的事件开销随 data 行数线性增长（每个换行都要加一个 data: 前缀）；
    • 对于低频消息，两者的开销都可以忽略，此时 SSE 的实现简单度和可靠性优势更重要；
    • 对于二进制数据，WebSocket 完胜，因为 SSE 必须 base64（体积膨胀约 33%）。

    所以正确的说法是：在高频场景下 WebSocket 的性能优势明显，在低频场景下这个差异可以忽略。 不要为了性能去选一个用不上的复杂度。

并发发送问题

官方说：当直接使用 WebSocketHandler API，而不是间接地通过 STOMP 消息机制使用它的时候，应用必须自行同步消息的发送，因为底层标准的 WebSocket 会话（JSR-356）不允许并发发送；一个可选做法是用 ConcurrentWebSocketSessionDecorator 把 WebSocketSession 包装起来。

这个限制带来的现象非常隐蔽：如果你有两个线程同时往同一个 session 发消息，可能会抛 IllegalStateException: The remote endpoint was in state [TEXT_FULL_WRITING]，也可能表现为消息内容交错损坏。而且它不是每次都必现，只在并发碰撞时出现，测试环境很难复现，上了生产才爆。

Spring 提供了 ConcurrentWebSocketSessionDecorator 来解决。它的作用是：包装一个 WebSocketSession，以保证同一时刻只有一个线程能发送消息；如果某次发送很慢，其他线程后续尝试发送更多消息时就无法获取刷新锁，这些消息会被缓冲起来；在这种情况下，配置的缓冲区大小上限和发送时间上限会被检查，一旦超限，会话会被关闭。

这两个参数的含义很关键：

  • sendTimeLimit：一次发送允许占用的最长时间。超时后 Spring 会关闭这个会话；
  • sendBufferSizeLimit：该会话允许积压的缓冲区上限。超了也会关闭会话。

另外这个装饰器还有一个 OverflowStrategy 参数可以选择溢出的处理方式，默认是 TERMINATE，也就是超限时抛异常并终止会话；另一个可选值是 DROP，表示丢弃最旧的消息而不是断开连接。对于”消息可以丢、但连接不能断”的场景，DROP 更合适。

为什么需要缓冲区上限？因为如果客户端网络很慢（或者干脆是个恶意客户端，故意不读数据），服务端往这个 session 发的消息会不断堆积在内存里，最终把 JVM 内存撑爆。这是一个典型的慢消费者攻击面。给每个会话设一个缓冲区上限，超过就断开，是标准的防护手法。

STOMP 路线下不需要手动做这件事，因为 Spring 的消息基础设施已经内置了 sendTimeLimit 和 sendBufferSizeLimit 配置。

原生 WebSocket 的局限：为什么企业项目需要 STOMP

写到这里，原生 WebSocket 的问题已经很清楚了。Spring 官方文档用了很长一段来解释 WebSocket 作为低层传输协议的定位，大意是：WebSocket 是一种低层传输协议，和 HTTP 不同，它不对消息内容规定任何语义。这意味着，除非客户端和服务端就消息语义达成一致，否则没有任何办法对消息进行路由或处理。

所以说，WebSocket 不规定消息内容的语义。 它只负责把字节从一端搬到另一端，至于这个字节是什么，协议一无所知，也无法路由。

对比 HTTP ，在 HTTP 和 REST 里，应用被建模成很多个 URL；要与应用交互，客户端就以请求响应的方式访问这些 URL；服务端根据 HTTP 的 URL、方法和头部把请求路由到合适的处理器。而在 WebSocket 里，通常只有一个 URL 用于初始连接，此后所有应用消息都在同一条 TCP 连接上流动，这指向了一种完全不同的、异步的、事件驱动的消息架构。

这段话点出了 WebSocket 架构上的本质变化：

HTTP / REST WebSocket
应用建模 很多个 URL 通常只有一个连接 URL
路由依据 URL + method + header 无（握手后所有消息走同一条连接）
交互方式 请求响应 异步事件驱动
状态 无状态（或 Session 承载） 有状态的连接会话

所以用原生 WebSocket 做业务时，你实际上要自己发明一套应用层协议：

  • 消息里要带一个指令类型字段来做路由（等价于 URL）；
  • 要自己实现”订阅”和”取消订阅”（等价于 broker 的订阅表）；
  • 要自己维护 哪个 session 订阅了哪个主题 的映射；
  • 要自己实现给某个用户的所有会话推送；
  • 要自己处理序列化、错误码、超时、心跳。

这就是 STOMP 存在的意义。Spring 官方文档列出了用 STOMP 作为子协议，好处如下：

  1. 不用自己发明一套消息协议和消息格式；
  2. 有现成的 STOMP 客户端可用（包括 Spring Framework 提供的 Java 客户端）；
  3. 可以选择使用消息代理（比如 RabbitMQ、ActiveMQ 等）来管理订阅和广播消息；
  4. 业务逻辑可以组织到任意多个 @Controller 里，按 STOMP 的 destination 头来路由消息，而不是像处理裸 WebSocket 消息那样，一条连接只能对应一个 WebSocketHandler。
  5. 可以用 Spring Security 基于 STOMP 的目的地和消息类型来做授权。

STOMP 协议速览

STOMP 是什么。Spring 文档对它的定位是：

  • 全称面向文本的简单消息协议，最初是为 Ruby、Python、Perl 这类脚本语言连接企业消息代理而设计的；
  • 它只覆盖常用消息模式的一个最小子集，不是一个完备的消息 API；
  • 可以跑在任何可靠的双向流式协议上，TCP 和 WebSocket 都行，这一点很重要，它意味着 STOMP 和 WebSocket 是解耦的；
  • 虽然是文本协议，但载荷可以是文本或二进制。

规范对每一部分的定义，我整理成中文如下：

  • 命令：帧的第一行，以行结束符收尾。这个行结束符是”可选的 CR + 必需的 LF”，也就是 \n 或 \r\n 都可以；
  • 头部：命令之后是零个或多个 <key>:<value> 形式的头部条目，每个条目也以行结束符收尾；
  • 空行：一个额外的行结束符，标记头部结束、Body 开始；
  • Body：消息内容；
  • NULL 字节（^@ 表示，ASCII 的 0x00）：帧结束符。这个 NULL 字节之后还可以跟多个行结束符。

拆解成五步：

  1. 命令：第一行，以 EOL 结束；
  2. 头部：零到多个 key:value，每行一个；
  3. 空行：一个额外的 EOL，标记头部结束、Body 开始；
  4. Body：消息内容；
  5. NULL 字节：帧结束符。

那个 NULL 字节是 STOMP 解析的关键。如果 Body 里含有 NULL 字节，必须带 content-length 头，否则接收方无法确定帧边界，它会把 Body 里的 NULL 当成结束符。这一条在传二进制内容时特别重要。

还有几条解析规则值得知道：

  • 只有 SEND、MESSAGE 和 ERROR 这三种帧可以带 Body，其他帧都不得带 Body；
  • 命令和头部的名字是区分大小写的；
  • 除了 CONNECT 和 CONNECTED 帧以外，其他帧里的头部如果含有 CR、LF 或冒号，必须做转义（用 C 风格的 \r、\n、\c、\\）；而未定义的转义序列（比如 \t）必须被视为致命的协议错误；
  • 在 STOMP 1.2 里，客户端和服务端都绝不允许对头部值做空格裁剪或补齐。

常用命令

命令 方向 作用

服务端不能发送”未经请求”的消息。 所有服务端消息都必须是对某个客户端订阅的响应，subscription 头必须匹配客户端订阅的 id。这条规则意味着：客户端必须先订阅，服务端才能推。实践中前端要先发 SUBSCRIBE，后面才能收到 MESSAGE。

关于 CONNECT 帧，规范规定了两项必需的头：

  • accept-version（客户端支持的 STOMP 版本列表）
  • host（客户端想连接的虚拟主机名）；
  • 可选的头包括 login、passcode 和 heart-beat。

destination 的语义

关于 destination，destination 的含义在 STOMP 规范里是被有意留成不透明的。它可以是任意字符串，其语义和语法完全由 STOMP 服务端自己定义。不过很常见的一种做法是把它写成类似路径的字符串，其中 /topic/.. 表示发布订阅（一对多），/queue/ 表示点对点（一对一）的消息交换。

这一点在 Spring 的 simple broker 上要注意，对于内置的简单 broker，/topic 和 /queue 这两个前缀没有任何特殊含义，它们只是为了区分”发布订阅”和”点对点”而约定的命名习惯。当你使用外部 broker 时，要去查那个 broker 的 STOMP 文档，了解它支持什么样的目的地和前缀。

心跳机制

STOMP 有协议级的心跳，它用一个 heart-beat 头同时表达”我能发多快”和”我希望你发多快”。具有如下规则

  • 这个头必须包含两个以逗号分隔的正整数；就是 heart-beat:<cx>,<cy>：cx是发送方能保证的最小发送间隔（0 表示不能发）；cy是发送方希望收到的间隔（0 表示不想收）。
  • 第一个数字表示”发送方自己能做到什么”（也就是它外发心跳的能力）：0 表示它不能发送心跳，否则表示它能保证的两次心跳之间的最小毫秒间隔
  • 第二个数字表示”发送方希望收到什么”（也就是它希望对方发来的心跳频率）：0 表示它不想收到心跳，否则表示它期望的两次心跳之间的毫秒间隔。

对于客户端到服务端方向的心跳，如果客户端的 cx 是 0（客户端不能发心跳），或者服务端的 sy 是 0（服务端不想收心跳），那就不会有心跳；否则心跳间隔就是 cx 和 sy 里的较大值。

也就是取双方声明的较大值：客户端说”我最快 10000ms 能发一次”，服务端说”我希望 20000ms 收一次”，那实际就是 20000ms 一次。很明显，不这样取值会有问题

心跳的发送方式也很有意思，在某个方向上，如果期望每 n 毫秒有一次心跳，那么发送方必须至少每 n 毫秒在连接上发送一次新数据；如果发送方没有真实的 STOMP 帧要发，它必须发送一个行结束符（EOL）；而如果接收方在一个至少 n 毫秒的时间窗口内没有收到任何新数据，它可以把这条连接视为已死。

如果没有真实的 STOMP 帧要发，就发一个 EOL（换行符）来充当心跳。也就是说，STOMP 的心跳就是一个空行。这样做的好处是接收方不需要区分心跳帧和数据帧，不增加解析复杂度，而且其实很明显，任何在连接上收到的新数据，都表示远端还活着。

最后一条实践提醒：缺少 heart-beat 头必须被当作 heart-beat:0,0 处理，也就是”不能发、也不想收”。

三条消息通道与消息流

理解 STOMP 的配置，必须先理解消息是怎么流的。Spring 明确列出了三条通道：

  • clientInboundChannel：用于传递从 WebSocket 客户端收到的消息；
  • clientOutboundChannel：用于把服务端的消息发送给 WebSocket 客户端；
  • brokerChannel：用于在服务端应用代码内部向消息 broker 发送消息。
通道 方向 用途
clientInboundChannel 客户端 → 服务端 接收 WebSocket 客户端发来的消息
brokerChannel 应用内部 → broker 服务端代码主动往 broker 发消息
clientOutboundChannel 服务端 → 客户端 把服务端消息写回 WebSocket 客户端

官方文档还给了一个完整的流程示例：

  1. 客户端连接到 http://localhost:8080/portfolio，一旦 WebSocket 连接建立，STOMP 帧就开始在上面流动；
  2. 客户端发一个 SUBSCRIBE 帧，destination 头是 /topic/greeting。收到并解码后，消息被送到 clientInboundChannel，然后被路由到消息 broker，由 broker 保存这个客户端订阅；
  3. 客户端发一个 SEND 帧到 /app/greeting。/app 这个前缀的作用是把它路由到注解控制器；前缀被剥掉之后，剩下的 /greeting 部分就映射到 GreetingController 里的 @MessageMapping 方法；
  4. GreetingController 的返回值被转成一个 Spring Message，载荷来自返回值，destination 头默认是 /topic/greeting（由入站 destination 把 /app 换成 /topic 得来）。这条消息被送到 brokerChannel，由消息 broker 处理；
  5. 消息 broker 找到所有匹配的订阅者，通过 clientOutboundChannel 给每一个发送一个 MESSAGE 帧，最后由这个通道把消息编码成 STOMP 帧，发到 WebSocket 连接上。

注意第 4 步里的那个自动转换规则，非常关键：@MessageMapping 方法的返回值，默认目的地是把入站目的地的 /app 换成 /topic。

这个隐式规则让代码很简洁，但也容易让人困惑”我的消息到底发到哪去了”。如果目的地不符合预期，就用 @SendTo 显式指定。

编写消息控制器

STOMP 的控制器写起来和 Spring MVC 非常像，这是它最大的易用性优势。

关于方法参数，官方文档给出了完整的支持列表，我整理成表：

方法参数 说明
Message 访问完整消息
MessageHeaders 访问消息头
MessageHeaderAccessor / SimpMessageHeaderAccessor / StompHeaderAccessor 通过类型化访问器访问消息头
@Payload 访问载荷，由配置的 MessageConverter 转换（比如从 JSON）
@Header 访问特定消息头的值，必要时用 Converter 做类型转换
@Headers 访问全部消息头，参数必须能赋给 java.util.Map
@DestinationVariable 访问从 destination 模板变量中提取的值，必要时做类型转换
java.security.Principal 反映 WebSocket HTTP 握手时登录的用户

这个注解@Payload并不是必须的，因为如果没有其他参数匹配上，它就默认被当作载荷处理。所以 public void handle(ChatMessage msg) 和 public void handle(@Payload ChatMessage msg) 是等价的。这减少了大量样板代码。而且载荷参数支持 @Valid 自动校验，和 Spring MVC 完全一致。

关于返回值的默认行为，官方也说明：@MessageMapping 方法的返回值默认会经由匹配的 MessageConverter 序列化成载荷，并作为 Message 发往 brokerChannel，再由 broker 广播给订阅者；这条出站消息的目的地，就是入站消息的目的地加上 /topic 前缀。

另外，@SendTo 和 @SendToUser 可以同时用在同一个方法上，而且都支持类级别，在类级别时作为该类内方法的默认值，但方法级别的注解会覆盖类级别的。@MessageMapping 方法还可以返回 ListenableFuture、CompletableFuture 或 CompletionStage，也就是支持异步处理。

关于 @SubscribeMapping 的取舍，它的行为差异是：

  • @MessageMapping 的返回值：发到 broker，由 broker 广播给所有匹配的订阅者；
  • @SubscribeMapping 的返回值：默认直接通过 clientOutboundChannel 发给发起订阅的那个客户端，不经过 broker，也不会把这个订阅存下来给后续广播用。

不要试图把 broker 和控制器映射到同一个目的地前缀，除非你确实想让两者独立处理消息（包括订阅）。因为入站消息是并行处理的，一条给定消息到底由 broker 还是控制器先处理，是没有任何保证的。

关于怎么知道订阅已经就绪？如果你希望在订阅被 broker 保存、可以开始接收广播时收到通知，客户端应该请求 receipt（如果服务端支持的话，simple broker 并不支持）。 换句话讲，simple broker 下你是没有订阅确认这个能力的；要么用带 receipt 能力的 Java STOMP 客户端，要么在服务端注册一个 ExecutorChannelInterceptor 到 brokerChannel，实现 afterMessageHandled，在消息（包括订阅）被处理完之后做后续动作。

关于用户目的地的转换机制，应用可以发送针对特定用户的消息，Spring 的 STOMP 支持识别以 /user/ 为前缀的目的地来实现这一点。比如客户端可能订阅 /user/queue/position-updates 这个目的地；UserDestinationMessageHandler 会处理它，并把它转换成一个对该用户会话唯一的 destination（例如 /queue/position-updates-user123）。这样做的好处是，你可以订阅一个通用命名的目的地，同时又保证不会和其他订阅了同一目的地的用户发生冲突，让每个用户都能收到属于自己的那份更新。

有一个方向上的区别：订阅侧写的是 /user/...（不带用户名），而发送侧写的是 /user/{username}/...（带用户名），后者会被解析成该用户的一个或多个会话目的地。

必须正确配置 broker 前缀和应用前缀，否则 broker 会去处理本该由 UserDestinationMessageHandler 处理的 /user 前缀消息。 这就是为什么在配置里要把 enableSimpleBroker("/topic", "/queue") 和 setApplicationDestinationPrefixes("/app") 配清楚——不要让 /user 落进 broker 的前缀范围。

关于多会话的行为，默认情况下，如果同一个用户有多个会话（多标签页、多设备），消息会发给所有会话。 如果只想发给”当前这个发消息的会话”，用 @SendToUser(broadcast = false)。

还有一条提醒是关于未登录用户的，未认证的用户也能订阅 user destination，此时 @SendToUser 的行为等同于 broadcast=false。这说明 user destination 本身不是一道安全边界，别指望用它来做隔离——真正的隔离要靠 Spring Security 的授权规则。

线程池与性能调优

STOMP 的性能调优，核心是配置背撑三条通道的线程池，以及几个与消息发送相关的保护参数。

关于 clientInboundChannel 和 clientOutboundChannel 的默认线程数，存在三种说法：

来源 说法
Spring 参考文档 可用处理器数量的 2 倍
WebSocketMessageBrokerConfigurer Javadoc 大小为 1 的线程池
Spring Framework 7.0.9 源码 corePoolSize = 0、maxPoolSize = 1

很明显三者冲突了。源码和 Javadoc 一致，参考文档说法不同。但纠结默认值没有意义，无论默认是 1 还是 2×CPU，对生产级消息推送服务都远远不够，必须显式配置。这里一般是把默认值当成极小/未定义，不依赖它，直接设置成业务需要的值

调优方向取决于工作负载类型，如果注解方法里的处理主要是 CPU 密集型的，clientInboundChannel 的线程数应当保持在处理器数量附近；如果这些工作更偏 IO 密集、需要阻塞或等待数据库或其他外部系统，那么线程池大小大概就需要增加。

  • CPU 密集：clientInboundChannel 线程数保持在 CPU 核心数附近；
  • IO 密集（查库、调远程服务）：要适当增加线程数。

而且注意到，如果队列容量是默认的 Integer.MAX_VALUE，那么线程数永远不会超过核心线程数，因为所有超出核心数的任务都被塞进队列里排队了，永远触发不了”队列满了才扩容到 maxPoolSize”的条件。

出站线程池的调优逻辑和入站不同，出站线程池的负载取决于客户端网络状况，这是应用无法控制的。所以 Spring 额外提供了两个保护参数。sendTimeLimit 和 sendBufferSizeLimit。 sendTimeLimit 控制”一次发送最多允许多久”，sendBufferSizeLimit 控制”最多能积压多少数据”。超过任一限制，该会话会被关闭。

同一时刻只有一个线程能往某个客户端发送，其他消息会被缓冲。

配置项 默认值 说明
messageSizeLimit 64KB 不是单个 WebSocket 消息的大小，而是在 WebSocket 服务器层之上重组后的 STOMP 消息大小
sendTimeLimit 10 秒 入参必须大于 0，否则被忽略
sendBufferSizeLimit 512KB 小于等于 0 会让缓冲实际上被禁用
timeToFirstMessage 60 秒 超过这个时间没收到第一条消息，视为代理或网络异常并关闭

关于 sendTimeLimit，会话的时间上限只在”尝试发送更多消息”时才会被检查；所以如果只发了一条消息而它卡住了，那么除非之后再发一条消息、或者底层物理 socket 自己超时，否则这个会话不会超时。也就是说，如果只发了一条消息而且它卡住了，这个会话不会超时。

关于 messageSizeLimit，理论上，一条 WebSocket 消息的大小几乎可以不受限制。但在实践中，WebSocket 服务器会施加限制，例如 Tomcat 上是 8K，Jetty 上是 64K。出于这个原因，像 stomp-js/stompjs 这样的 STOMP 客户端会在 16K 的边界处切分较大的 STOMP 消息，把它们作为多条 WebSocket 消息发送，而这要求服务端进行缓冲和重新组装。

所以说，Spring 会自动调整 WebSocket 消息大小上限，保证至少能承载 16K 的 WebSocket 消息。 所以你可以放心地把 messageSizeLimit 设成业务需要的大小，不用去关心底层容器的限制。

监控：WebSocketMessageBrokerStats

Spring 在启用 @EnableWebSocketMessageBroker 时会自动注册一个统计 bean，这个能力在排查线上问题时非常有用。它的行为是：在使用 @EnableWebSocketMessageBroker 时，一些关键基础设施组件会自动收集统计信息和计数器；配置还会声明一个 WebSocketMessageBrokerStats 类型的 bean，把所有这些信息集中到一处，并默认以 INFO 级别每 30 分钟记录一次日志；这个 bean 可以通过 Spring 的 MBeanExporter 导出到 JMX，以便在运行时查看。

它收集的信息，官方文档列出的内容包括：

  • Client WebSocket Sessions：
    • Current：当前有多少客户端会话，还按 WebSocket 与 SockJS 的 HTTP streaming/polling 分别统计；
    • Total：累计建立过多少会话；
    • Abnormally Closed：
      • Connect Failures：会话建立后 60 秒内没收到任何消息就关闭的——官方说这通常意味着代理或网络有问题；
      • Send Limit Exceeded：因为超过发送超时或发送缓冲区上限而被关闭的会话，官方说这可能发生在慢客户端身上；
      • Transport Errors：传输错误导致的关闭，比如读写 WebSocket 连接失败、或 HTTP 请求/响应失败；
    • STOMP Frames：处理过的 CONNECT、CONNECTED、DISCONNECT 帧总数。
  • STOMP Broker Relay（接外部 broker 时）：
    • TCP Connections：代表客户端 WebSocket 会话建立的到 broker 的 TCP 连接数，应该等于客户端会话数 + 1（那个额外的 1 是应用内部发消息用的共享”系统”连接）；
    • STOMP Frames：转发给 broker 和从 broker 收到的各类帧总数。

另外它还会带上通道线程池的统计，以及 SockJS 任务调度器的统计。

这三个计数器（Connect Failures、Send Limit Exceeded、Transport Errors）是在生产环境排查 WebSocket 问题的第一手资料。

  • Connect Failures 突增 → 去查 nginx 的 proxy_read_timeout、查负载均衡的空闲超时；
  • Send Limit Exceeded 突增 → 说明有一批客户端网络很差（移动端弱网？），要调整 sendBufferSizeLimit 或者做消息降采样；
  • Transport Errors 突增 → 一般是网络层问题或者容器资源耗尽。

我在项目里会把它接到 Micrometer 上做告警，而不是等 30 分钟一次的日志。

内存与资源管理清单

SSE 在 MVC 下最容易出的问题是连接泄漏，症状是内存缓慢增长、最后 OOM 或者被连接数打满。下面是我总结的必查清单：

  1. 有没有设 onCompletion / onTimeout / onError 三个回调？ 它们是释放资源的唯一入口。少一个都会泄漏。
  2. 超时后有没有主动调用 complete()？ onTimeout 触发时容器只是通知你超时了，不会自动清理 emitter。
  3. 心跳有没有在跑？ 没有心跳，客户端断开的连接永远不会被发现和清理。
  4. 超时时间是否合理？ 太长会导致”僵尸连接”堆积；太短会导致客户端频繁重连。 我的经验值是：超时时间设为前端期望单次连接时长的 1.5 到 2 倍。比如前端希望连接保持 30 分钟然后主动重连，那服务端超时可以设 45-60 分钟。
  5. 连接池有没有上限？ 单个用户的连接数、单个频道的订阅者数量都要有上限，否则一个恶意用户开一万个连接就能打垮服务。
  6. 推送失败后有没有移除？ send 抛异常时一定要把 emitter 从集合里摘掉，否则下次推送还会去试这个死连接。

Spring WebFlux：反应式 SSE

如果你的项目是 WebFlux，或者连接数会非常大，那响应式方案是更好的选择。Spring 也提供了 ServerSentEvent 这个类型来表达 SSE 事件的各个字段。

ServerSentEvent 是用于 Spring 反应式 Web 支持的 Server-Sent Event 表示；Flux<ServerSentEvent> 或 Observable<ServerSentEvent> 是 Spring MVC 的 SseEmitter 在反应式侧的等价物。

它的 builder 方法对应的字段和 MVC 侧一样：id()、event()、retry()、comment()、data()。关于 retry，它的入参类型是 Duration，而不是毫秒数

WebFlux 侧关于返回值，Flux<ServerSentEvent>、Observable<ServerSentEvent> 或其他响应式类型，都会发出 Server-Sent Events；如果只需要写数据，ServerSentEvent 这个包装类型可以省略，但此时必须通过 produces 属性请求或在映射里声明 text/event-stream。

也就是说，如果你不关心 id / event / retry 这些字段，直接返回 Flux<MyData> 也可以，只是produces 千万不能忘。

一个提醒：Flux 的事件流是有背压语义的。 如果客户端消费不过来，反应式流会施加背压，而不是像 MVC 那样无脑往缓冲区里堆。这在保护服务端内存方面是个优势，但也要注意：某些背压策略下，慢客户端会导致事件堆积在内存里（比如用了 onBackpressureBuffer），这时仍然需要设置缓冲区上限和溢出策略。

WebFlux 的方案还有一个隐性优势：它不需要为每个连接分配一个写线程。所以：

Spring MVC + SseEmitter WebFlux + Flux
每连接的线程开销 写入时占用一个线程 无额外线程（非阻塞 IO）
背压支持 有（通过 reactive types），但写入仍阻塞 原生支持
万级连接 需要仔细规划线程池 相对轻松
迁移成本 低（存量 MVC 项目） 高（需要整个栈反应式）

最后，WebFlux 是一个全栈选择，不是局部优化。 如果你只在 SSE 这一个接口上用 WebFlux，而其他接口还是阻塞式的 MVC，那你会失去 WebFlux 的大部分收益，还引入了两套编程模型的复杂度。要上就上全套。

纯 HTTP 手写流

有时候框架抽象反而碍事，比如你想做多路复用（一个 SSE 连接推多个频道）、或者想完全自己控制输出格式。这时可以直接操作 HttpServletResponse。

手写流的五个关键点，正好对应我在讲 SSE 规范时提到的要求：

  1. Content-Type 必须是 text/event-stream；
  2. 编码必须是 UTF-8；
  3. 消息以空行结尾（两个连续换行）；
  4. 多行内容拆成多个 data: 字段；
  5. 每次写完必须 flush()。

第 5 点在手写方案里尤其重要。很多人写完之后发现”服务端明明发了，客户端要等好久才收到”，就是因为没有 flush——数据卡在 PrintWriter 或者容器缓冲区里了。

关于 X-Accel-Buffering: no，nginx 官方文档确认了这个头的存在和作用，缓冲也可以通过 X-Accel-Buffering 响应头字段传入 yes 或 no 来开关；这个能力可以用 proxy_ignore_headers 指令禁用。

这个头的价值在于，你可以在应用层控制 nginx 的缓冲行为，而不用去改 nginx 配置。对于 SSE 这种”只有某些接口需要关缓冲”的场景，这比全局关掉 proxy_buffering 更精细。

安全相关

功能和性能的问题通常能在测试环境暴露，但安全问题的特点是：它在开发阶段完全正常，上线后才被利用。

这一部分主要基于 Spring Security 官方 WebSocket 安全文档。

同源策略对 WebSocket 不生效

浏览器不会对 WebSocket 连接执行同源策略。

文档给了一个非常具体的攻击场景来说明后果：

设想如下场景：一个用户访问 bank.com 并登录了自己的账户。然后同一个用户在浏览器里又打开一个标签页，访问 evil.com。同源策略保证了 evil.com 无法读取或写入 bank.com 的数据。

但是对 WebSocket 来说，同源策略不适用。事实上，除非 bank.com 明确禁止，否则 evil.com 可以代表这个用户读写数据。这意味着用户能通过 WebSocket 做的任何事情（比如转账），evil.com 都能代表他去做。

整理成攻击步骤：

  1. 用户登录了 bank.com，浏览器里有了登录态的 Cookie；
  2. 用户在另一个标签页打开了 evil.com；
  3. evil.com 的脚本发起一个到 bank.com 的 WebSocket 连接；
  4. 因为这个连接会自动携带 bank.com 的 Cookie，服务端认为这是合法用户；
  5. 同源策略不管 WebSocket，所以这个连接被建立；
  6. 于是 evil.com 就可以以用户身份通过 WebSocket 做任何事，包括转账。

文档把 SockJS 也纳入了警告范围，SockJS 因为要模拟 WebSocket，同样绕过了同源策略，所以用 SockJS 也必须显式防护。

Origin 校验与 Spring 的默认行为

好消息是，Spring 从 4.1.5 起就默认只接受同源请求了。Spring 的 WebSocket 和 SockJS 支持就把访问限制在当前域名内了；而 Spring Security 在此基础上又增加了一层保护，形成纵深防御。

前面已经讲过三种配置模式（只允许同源、允许指定列表、允许全部）：

  • 默认只允许同源，这是安全的默认值，不要轻易改成 *；
  • 用 setAllowedOriginPatterns 而不是 setAllowedOrigins，前者支持通配模式且是 Spring 推荐的方式；
  • Origin 头可以被非浏览器客户端伪造，所以它只防浏览器侧的攻击（CSRF 方向），不能替代认证。

Spring Security 会在此基础上再加一层，形成纵深防御。这就是官方说的 defense in depth。

消息级授权

Origin 校验只保护了”握手这一次”。握手成功之后，连接里流动的所有 STOMP 消息都不再经过 Web 安全过滤器链了。

关于 @EnableWebSocketSecurity 这个注解的两个隐含行为：

  1. 任何入站的 CONNECT 消息都需要一个合法的 CSRF token，以此来强制同源策略。

    如果你用 @EnableWebSocketSecurity，客户端必须正确传 CSRF token，否则连 CONNECT 都会失败。

  2. 对于任何入站请求，SecurityContextHolder 都会被填充用户信息，放在 simpUser 头属性里。

区分 SUBSCRIBE 和 MESSAGE

客户端只能请求，不能广播。广播是服务端的特权。

设想一个聊天应用：

  • 系统可以通过 /topic/system/notifications 这个目的地，向所有用户发送通知类 MESSAGE；
  • 客户端可以通过 SUBSCRIBE 到 /topic/system/notifications 来接收通知。

我们当然希望客户端能够 SUBSCRIBE 到 /topic/system/notifications，但我们不希望允许它们向这个目的地发送 MESSAGE。因为如果我们允许向 /topic/system/notifications 发送 MESSAGE，客户端就能直接往这个端点发消息，从而冒充系统。

如果允许客户端往广播目的地发消息，客户端就能冒充系统。

总的来说，应用的常见做法是：拒绝任何发往以 broker 前缀（/topic/ 或 /queue/）开头的目的地的 MESSAGE，客户端只能往 /app/** 发，由服务端决定要不要广播出去。

理解 destination 转换，才能写对规则

  • 用户可以通过向 /app/chat 发消息来把消息发给某个特定用户；
  • 应用看到这条消息，确保 from 属性被指定为当前用户（我们不能信任客户端）；
  • 然后应用通过 SimpMessageSendingOperations.convertAndSendToUser("toUser", "/queue/messages", message) 把消息发给接收者；
  • 这条消息的目的地会被转换成 /queue/user/messages-<sessionid>。

注意最后一步的转换：

在这个聊天应用里，我们想让客户端监听 /user/queue，它会被转换成 /queue/user/messages-<sessionid>。但是，我们绝不能让客户端有能力监听 /queue/*，因为那会让客户端看到所有用户的消息。

所以说，客户端订阅 /user/queue/messages 是安全的，但你必须禁止它订阅 /queue/*。因为 /queue/* 是转换后的真实目的地空间，里面装着所有用户的消息。如果你开放了 /queue/** 的订阅权限，任何一个客户端都能订阅到别人的私信。

授权规则要写在”客户端声明的目的地”上（/user/...），而不是”转换后的真实目的地”上（/queue/...），并且必须显式拒绝客户端直接访问转换后的空间。

Token 认证：从 STOMP 头里取凭证

前面提到，浏览器原生 WebSocket 不支持自定义请求头，但 STOMP 的 CONNECT 帧可以带头部。所以企业项目里标准的做法是把 JWT 放在 STOMP 的 CONNECT 头里。

STOMP 协议确实在 CONNECT 帧上提供了 login 和 passcode 这两个头。它们最初是为 STOMP over TCP 设计的，在那个场景下也是必需的。但对于 STOMP over WebSocket，Spring 默认会忽略 STOMP 协议层面的认证头，并假定用户已经在 HTTP 传输层完成了认证。

注意这个默认行为，Spring 默认忽略 STOMP 层的认证头，它假设你已经在 HTTP 传输层完成认证了。

所以有两条路线。

依赖 HTTP 层认证

对于 WebSocket 握手请求、或者 SockJS 的 HTTP 传输请求来说，通常已经存在一个已认证用户，可以通过 HttpServletRequest#getUserPrincipal() 拿到。Spring 会自动把这个用户与该用户创建的 WebSocket 或 SockJS 会话关联起来，并进而通过一个 user 头，关联到这条会话上传输的所有 STOMP 消息。简而言之，一个典型的 Web 应用除了它原本为安全所做的事之外，不需要做任何额外的事。

如果你的应用用 Cookie + Session 认证，那基本上什么都不用做：用户在 HTTP 层认证 → Session 里存着安全上下文 → WebSocket 握手时 Spring 自动关联用户 → 之后每条 STOMP 消息都会自动带上用户信息。

这就是用 WebSocket 时，能用 Cookie/Session 就用，别硬上 JWT。

从 STOMP CONNECT 头里取 token（前后端分离）

如果架构是前后端分离 + JWT，Session 不可用，那就需要自定义一个 ChannelInterceptor。

首先，RFC 6455 并没有规定服务端在 WebSocket 握手期间认证客户端的具体方式；而浏览器客户端只能用标准的认证头（比如 HTTP Basic）或 Cookie，不能发自定义头；SockJS 的 JavaScript 客户端同样不能在传输请求里发 HTTP 头。虽然 token 也可以放在查询参数里，但那样 token 可能会随着 URL 一起被无意中记录到服务端日志里

所以官方推荐的两步方案是：客户端在 connect 时把认证头放进 STOMP 头里，服务端用一个 ChannelInterceptor 处理它。而且官方特别强调，只需要在 CONNECT 这条消息上做认证并设置 user 头，Spring 会记住这个用户，并把它关联到同一会话后续的所有 STOMP 消息上。

这个拦截器做了三件事：

  1. 只在 CONNECT 帧做认证，因为认证只需要做一次；
  2. accessor.setUser(auth) 把认证结果绑定到 STOMP 会话上，之后同一个会话里的所有消息都会带上这个用户（这就是为什么 @MessageMapping 方法里能直接注入 Principal）；
  3. 认证失败抛 MessagingException，连接会被拒绝。

CSRF：为什么 SockJS 特别麻烦

默认情况下，Spring Security 要求所有 CONNECT 消息都带 CSRF token。这确保了只有能够访问该 CSRF token 的站点才能建立连接。而由于只有同源站点才能访问到这个 CSRF token，外部域名就不被允许建立连接。

只有同源页面才能拿到 CSRF token，所以要求携带 CSRF token 就等价于强制同源。

SSE 的安全考量

SSE 的安全模型和普通 HTTP 接口基本一致，所以反而简单。

  • SSE 受 CORS 约束。

    因为 SSE 就是一个普通 GET 请求，浏览器的 CORS 机制正常生效。跨域时需要服务端返回正确的 Access-Control-Allow-Origin。EventSource 的 withCredentials: true 会让请求携带 Cookie，此时服务端不能用 Access-Control-Allow-Origin: *（CORS 规范禁止）。

  • token 不要放在 URL 里。

    这是 SSE 最常见的错误。因为EventSource 的构造函数只接受 URL，没法加自定义头（和原生 WebSocket 一样的问题）；于是很多人把 token 拼在 query string 里；但 URL 会被记录到 nginx access log、浏览器历史、Referer 头、APM 系统里，token 就泄漏了。

    正确做法有三种，按推荐顺序：

    1. 用 Cookie 认证（如果架构允许）：浏览器自动携带，URL 干净；

    2. 用一个短期的、一次性的 stream ticket：先通过正常接口（带 Authorization 头）换一个只能用一次的 ticket，然后用 ticket 建立 SSE 连接。ticket 有效期设得很短（比如 30 秒），即使泄漏了危害也有限；

    3. 如果非要把 token 放 URL，至少确保访问日志做了脱敏。

  • SSE 连接要有认证续期机制。

    SSE 连接可能保持几十分钟，而 token 可能 15 分钟就过期了。由于 SSE 连接建立后不再有”重新鉴权”的机会，你需要：

    • 让服务端定期检查会话有效性（比如每 5 分钟检查一次），失效就 complete() 掉连接；
    • 或者让前端在 token 即将过期时主动重连（关闭旧连接、用新 token 建新连接）。

  • 注意 Last-Event-ID 越权。

    如果你的 SSE 事件 ID 是全局递增的，那么客户端可以伪造一个很小的 Last-Event-ID 来要求服务端补发历史消息。必须校验这个用户是否有权访问这些历史事件。 正确的设计是，Last-Event-ID 只在”该用户自己的消息流”里做游标，服务端补发时要用 userId 作为过滤条件，而不是只按 ID 范围查。

网关配置

本地开发时一切正常，部署到带 nginx 的环境后就各种奇怪现象，这几乎是每个实时推送项目的必经之路。

WebSocket：必须显式转发两个逐跳头部

nginx 官方文档专门有一页讲 WebSocket proxying，大意是：Upgrade 是逐跳（hop-by-hop）头部，nginx 默认不会把它从客户端传给后端。 同样被默认丢弃的还有 Connection。如果这两个头传不过去，后端就看不到 客户端想升级协议 这个意图，握手会直接失败或者退化成普通 HTTP 请求。

从 1.3.13 版本起，如果被代理的服务器返回了 101（Switching Protocols）状态码，并且客户端在请求里通过 Upgrade 头要求了协议切换，那么 nginx 会启用一种特殊的运行模式，在客户端和被代理服务器之间建立一条隧道。

nginx 官方给的配置是这样的：

  • proxy_http_version ：它的默认值从 1.29.7 起变成了 1.1；在 1.29.7 之前，默认值用的是 1.0。

也就是说：

  • nginx 1.29.7 及以上：默认已经是 HTTP/1.1，proxy_http_version 1.1; 可以不写；
  • nginx 1.29.7 以下：默认是 HTTP/1.0，必须显式写 proxy_http_version 1.1;，因为 HTTP/1.0 不支持协议升级语义。

建议是不管什么版本都写上这一行。 它在新版本上没有副作用，却能让配置在任意版本上都正确

这样同一个 location 既能处理 WebSocket 升级，有 Upgrade 头时 Connection: upgrade，也能处理普通 HTTP 请求，没有时 Connection: close。

nginx 默认 60 秒内没有任何数据传输就关闭连接。这就是为什么”连接总是一分钟左右断一次”成了 WebSocket 部署的经典问题。官方给了两个解决方向：调大 proxy_read_timeout，或者让服务端定期发 Ping 帧来重置超时。

一般是两个都做：把 proxy_read_timeout 调到 300-600 秒，同时服务端按 10-30 秒间隔发心跳。只调大超时不解决”连接已经死了但双方都不知道”的问题；只发心跳则在网络真正卡住时会被提前掐掉。

SSE 的问题在缓冲，不在升级

SSE 不需要转发任何头部，它就是一个普通 GET，所以配置反而更简单，但有一个独特的坑：缓冲。

proxy_buffering 的默认值是 on。

开启缓冲时，nginx 会 尽快把响应从后端读出来 并攒在缓冲区里；关闭时才会 收到什么立刻转发什么。

你辛辛苦苦写的事件流，被 nginx 攒在缓冲区里，攒够一批才发给客户端。用户看到的现象是”消息延迟几秒到几十秒才出现”或者”几条消息同时弹出来”。

两种关闭方式：

  • 改 nginx 配置

  • 应用层返回响应头（推荐）

    缓冲也可以通过 X-Accel-Buffering 响应头字段传入 yes 或 no 来开关；这个能力可以用 proxy_ignore_headers 指令禁用。所以服务端只要在 SSE 响应里加一个头就行：

方式二的优点是不用动运维配置，而且粒度精确，只有 SSE 接口关缓冲，其他接口保持不变。对于”公司网关统一管控、改配置要走审批”的场景，这是唯一可行的方案。

关于 proxy_read_timeout，它定义的是从被代理服务器读取响应的超时。这个超时只设置在两次连续读操作之间，而不是整个响应的传输过程。如果被代理服务器在这段时间内没有传输任何东西，连接就会被关闭。这个超时只作用在”两次连续读操作之间”，而不是整个响应的总时长。

这句话非常关键，它说明了为什么 SSE 只要心跳足够频繁，就不需要把超时设得特别大。每一次心跳都是一次读操作，都会重置计时器。默认 60 秒配合 15 秒心跳已经完全够用了。

反过来说，如果你的 SSE 没有心跳，那不管 proxy_read_timeout 设得多大，连接都撑不住，因为 60 秒（或你设的值）内没有任何数据传输，连接就会被关闭。这和 WebSocket 的情形完全一样。

多实例部署：会话粘不住怎么办

单机部署时一切正常，一旦水平扩容到多实例，实时推送就会出一个诡异的现象：消息只推到了恰好连在同一台机器上的那部分用户。

原因很直接，消息的生产者（比如处理支付回调的实例 A）和消费者（比如连在实例 B 上的用户）不在同一台机器上，而实例 A 的 SimpMessagingTemplate 只能找到自己内存里维护的订阅关系。

Spring 官方认为。简单 broker 很适合入门，但它只支持 STOMP 命令的一个子集（它不支持 ack、receipt 以及其他一些特性），依赖一个简单的消息发送循环，而且不适合做集群。

另一处是：simple broker 无法用于多实例。用上完整功能的消息代理后，每个应用实例都连到 broker 上，一个实例广播的消息就能通过 broker 传到其他实例的客户端。

有四种常见解法，我按推荐度排序。

方案一：STOMP broker relay（官方方案）

把 simple broker 换成外部 STOMP broker（RabbitMQ、ActiveMQ 等）：

STOMP broker relay 就是一个 MessageHandler，它通过把消息转发给外部消息 broker 来处理消息；为了做到这一点，它会与 broker 建立 TCP 连接，把所有消息转发给它，然后再把从它那里收到的所有消息，通过各客户端的 WebSocket 会话转发下去。本质上，它扮演的是一个双向转发的”中继”角色。

broker relay 本身就是一个 MessageHandler，它和后端建立 TCP 连接，把所有消息转发给 broker，再把从 broker 收到的消息通过 WebSocket 会话转发给客户端。本质上它就是一个双向转发的”中继器”。

关键是两个 broadcast 配置。在多应用服务器的场景下，一个用户目的地可能无法被解析，因为这个用户连在另一台服务器上。在这种情况下，你可以配置一个目的地，把无法解析的消息广播出去，让其他服务器有机会尝试解析。这可以通过 Java 配置里的 userDestinationBroadcast 属性、或者 XML 里 message-broker 元素的 user-destination-broadcast 属性来设置。配置 userDestinationBroadcast 后，无法解析的消息会被广播出去，让其他实例有机会处理。

关于 userRegistryBroadcast，把本地用户注册表的内容广播出去，并监听来自其他服务器的这类广播。在多应用服务器场景下，这使得每个服务器的用户注册表都能感知到连接在其他服务器上的用户。

这两个属性都挂在 StompBrokerRelayRegistration 上，而且默认都是不设置的。其中 userDestinationBroadcast 在 用户私有消息（/user/**）+ 多实例 这个组合场景下是必须配置的，否则会出现有时能收到私信、有时收不到的随机故障。排查这类问题极其痛苦，因为它是概率性的。

broker relay 需要 reactor-netty 和 netty-all 来做 TCP 连接管理，这两个依赖容易漏。为了做 TCP 连接管理，需要在你的项目里加上 io.projectreactor.netty:reactor-netty 和 io.netty:netty-all 这两个依赖。

关于消息大小还有一个细节值得注意：STOMP broker relay 走的是 TCP，不受 WebSocket 帧大小的限制，所以大消息的问题会小一些。但 broker 本身可能有自己的大小限制，要去查对应 broker 的文档。

最后提醒一下外部 broker 的队列清理问题。用户会话结束后，那些为每个用户动态创建的队列必须被清理掉，否则队列会无限增长。这是接外部 broker 时最容易忽略的运维问题。

方案三：网关会话粘滞

用一致性哈希或 IP 哈希把同一个用户的连接都路由到同一个实例：

但我不推荐这个方案，原因有三个：

  1. ip_hash 在客户端 IP 变化（移动网络切换、多级代理）时就会失效，用户连接被路由到别的实例；
  2. 扩容/缩容时哈希环变化，大量用户会被重新分配，导致连接风暴；
  3. 它只解决了 同一用户连在同一实例，没解决 业务事件在另一实例产生。支付回调可能落在实例 A，而这个用户连在实例 B，消息照样推不过去。

粘滞只能作为辅助手段，不能作为多实例推送的主方案。 真正的问题不在连接路由，而在消息如何跨实例传递。

方案四：消息队列 / 事件总线

如果系统本来就有 Kafka、RocketMQ 之类的消息队列，直接用它们做跨实例广播是最自然的。所有实例订阅同一个 topic，收到消息后各自推给自己本地的 WebSocket 会话。

这个方案的优点是基础设施已经存在，不增加新组件；缺点是需要自己实现”消息到会话”的路由逻辑，而且要注意消费组的选择，必须是”广播模式”（每个实例都收到），而不是”集群模式”（只有一个实例收到）。

在 Kafka 里对应的概念是每个实例用不同的 consumer group；在 RocketMQ 里是 BROADCASTING 模式。这个区别很关键，配错了就会变成”只有一个实例收到消息”，表现和没配一样。

监控与可观测性

实时推送的监控，难点在于常规的 HTTP 监控指标在这里是失效的：一个保持了 30 分钟的 WebSocket 连接，在 APM 里可能只显示为一个耗时 30 分钟的请求，看不出任何有用信息。

WebSocket 侧要采集的指标

STOMP 路线的最大优势之一，就是 Spring 已经内建了统计能力。前面讲过 WebSocketMessageBrokerStats，这里给出落地成 Micrometer 指标的写法：

五个指标：

指标 含义 异常时的排查方向
ws.connections.active 当前活跃连接数 突然归零说明大面积断连；持续上涨要查是否是连接泄漏
ws.disconnect.total{code="1006"} 异常断开次数 突增说明网络或代理在掐连接
ws.disconnect.total{code="1011"} 服务端错误断开 突增说明业务代码在抛异常
Connect Failures 会话建立后 60 秒内没收到任何消息就关闭 突增说明代理或网关配置有问题
Send Limit Exceeded 超过发送超时或缓冲上限被关闭 突增说明有大量慢客户端（弱网用户）

后两个可以直接从 WebSocketMessageBrokerStats 里取。Spring 文档对它们的定义，大意是：

  • Connect Failures：那些已经建立、但在 60 秒内没有收到任何消息就被关闭的会话。这通常是代理或网络问题的征兆。
  • Send Limit Exceeded：那些因为超过配置的发送超时或发送缓冲区限制而被关闭的会话，这种情况可能发生在慢客户端身上。

这两个计数器是 Spring 帮我们做好的诊断，直接接出来告警就能省掉大量排查时间。60 秒这个数字也正好对应 timeToFirstMessage 的默认值，所以它是可调的，如果你的客户端建立连接后确实要等很久才发第一条消息，记得把 timeToFirstMessage 调大，否则会误杀。

限流与容量规划

实时推送的连接数和消息量都容易失控，必须提前规划。

连接数维度的限流，三个层次都要限：

三个层次的作用不同：

  • 单用户限制防的是”正常用户的异常行为”（开了 20 个标签页、或者前端代码 bug 导致重复建连）；
  • 单 IP 限制防的是”单机攻击”（一个脚本从一台机器发起上万连接）。注意这个值不能设太小，因为企业出口 NAT 后面可能有几百个真实用户共享一个 IP；
  • 单实例限制是最重要的保护，防止实例被打满导致所有用户都受影响。达到上限后应该拒绝新连接而不是让内存耗尽。

而且对 服务端往客户端推 这个方向也要限流，因为客户端可以故意不读数据来制造积压：

  • 单连接发送速率限制：比如每连接每秒最多 50 条消息，超出的丢弃或降采样；
  • 单连接缓冲上限：STOMP 用 sendBufferSizeLimit，SSE 要自己统计未确认的字节数；
  • 消息大小上限：STOMP 用 setMessageSizeLimit，SSE 要在序列化后检查长度。

一个实用的做法是降采样而不是丢弃，对于高频的行情类推送，超过阈值时把多条消息合并成一条 批量更新 再发，客户端体验反而更好。

技术选型总结

把整篇文章的结论收敛成一张决策表：

业务场景 推荐方案 理由
站内通知、公告、系统消息 SSE 单向、低频、需要可靠重连与断点续传
订单/任务状态跟踪 SSE 状态变更次数少，SSE 的自动重连正好匹配
大屏看板、监控指标 SSE（HTTP/2 下）或 WebSocket 高频时 WebSocket 帧开销更低
实时聊天、IM WebSocket + STOMP 双向、需要用户寻址与订阅管理
协同编辑、白板 WebSocket + STOMP 高频双向，延迟敏感
在线游戏、实时互动 WebSocket（原生） 需要完全自定义协议与最低延迟
行情推送（高频） WebSocket + STOMP 高频大流量，需二进制与压缩支持
进度条、长任务反馈 SSE 单向、可断点续传、实现简单
需要向特定用户精准推送 WebSocket + STOMP /user/** 目的地是内建能力
团队网关改不动、只允许标准 HTTP SSE 就是一个 GET，无需改网关升级配置

如果只能记一句话，我会这么说：

先问自己”客户端要不要频繁上行”。不要，就优先 SSE，因为它便宜、可靠、几乎不需要改基础设施；要，就上 WebSocket + STOMP，并且从第一天就把安全、监控和多实例广播这三件事规划进去，因为它们都不是可以事后补的东西。
