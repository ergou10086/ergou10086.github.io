集群和分布式的区别

集群 Cluster 是多个相同节点协作处理同一任务以提高并发和可用性，分布式是将业务拆分为多个独立子系统在不同节点协作完成整体任务。

集群指将相同的系统或服务部署在多个节点上，通过负载均衡共同处理同一业务，关注节点的冗余和并发能力，以提升系统的并发能力和高可用性。集群节点功能一致，节点间通常不需要复杂通信协调，主要解决 量 的问题，如高并发访问或单点故障容错

分布式（Distributed）则是将一个大业务拆分为多个独立的子业务或子系统，分别部署在不同节点上，各节点协作完成整体任务。分布式系统强调节点间的通信与协调，每个节点可能承担不同功能，解决系统复杂性和迭代扩展问题，即“质”的问题

所以说，在redis中，需要单独的看待。

Redis 3.0后便多了一个 REDIS CLUSTER 配置，即Redis集群，他可以突破3.0之前只能一主多从的限制，实现多主多从，这种集群没有中心节点，可水平扩展，据官方文档称可以线性扩展到上万个节点，当前配置性能和高可用都优与哨兵模式，且配置非常简单

Redis 集群

Redis三大集群模式

Redis集群是一种通过将多个 Redis 节点连接在一起以实现高可用性、数据分片和负载均衡的技术。它允许 Redis 在不同节点上同时提供服务，提高整体性能和可靠性。

根据搭建的方式和集群的特性，Redis集群主要有三种模式：主从复制模式（Master-Slave）、哨兵模式（Sentinel）和Cluster模式

主从复制

主从复制是Redis的一种基本集群模式，它通过将一个Redis节点（主节点）的数据复制到一个或多个其他Redis节点（从节点）来实现数据的冗余和备份。

主节点负责处理客户端的写操作，同时从节点会实时同步主节点的数据。客户端可以从从节点读取数据，实现读写分离，提高系统性能。

主从复制的优缺点

优点：

  1. 配置简单，易于实现。
  2. 实现数据冗余，提高数据可靠性。
  3. 读写分离，提高系统性能。

缺点：

  1. 主节点故障时，需要手动切换到从节点，故障恢复时间较长。
  2. 主节点承担所有写操作，可能成为性能瓶颈。
  3. 无法实现数据分片，受单节点内存限制

所以说，一般情况下，主从复制模式适用于数据备份和容灾恢复，或者在线升级和扩展

总之，主从复制模式适合数据备份、读写分离和在线升级等场景，但在主节点故障时需要手动切换，不能自动实现故障转移。如果对高可用性要求较高，可以考虑使用哨兵模式或Cluster模式。

哨兵模式

哨兵模式就是所谓的 Sentinel 模式，哨兵模式是在主从复制基础上加入了哨兵节点，实现了自动故障转移。

哨兵节点是一种特殊的 Redis 节点，它会监控主节点和从节点的运行状态。当主节点发生故障时，哨兵节点会自动从从节点中选举出一个新的主节点，并通知其他从节点和客户端，实现故障转移。

Cluster模式

一般我们认为前两种模式是集群模式，Cluster 才是真正的分布式方案。它把数据分片到多个主节点上，每个主节点只负责一部分数据，从而同时解决容量和写吞吐的扩展问题。在 Cluster 中，每个主节点可以带从节点，故障时从节点自动升主，兼顾了高可用。

Cluster 模式是 Redis 的一种高级集群模式，它通过数据分片和分布式存储实现了负载均衡和高可用性。在 Cluster 模式下，Redis 将所有的键值对数据分散在多个节点上。每个节点负责一部分数据，称为槽位。通过对数据的分片，Cluster 模式可以突破单节点的内存限制，实现更大规模的数据存储。

Redis Cluster 将数据分为16384个槽位，每个节点负责管理一部分槽位。当客户端向 Redis Cluster 发送请求时，Cluster会根据键的哈希值将请求路由到相应的节点。具体来说，Redis Cluster 使用CRC16算法计算键的哈希值，然后对16384取模，得到槽位编号。

深入 Cluster

Redis Cluster 的核心设计围绕 去中心化 与 数据分片 展开，它没有使用一致性哈希，而是通过哈希槽来管理数据分布，并依靠客户端重定向机制实现透明访问。

哈希槽

Redis Cluster 中的哈希槽，本质上是介于 键 和 节点 之间的一层虚拟分片单元。它的核心作用是将整个键空间划分为固定数量的槽位，再把这些槽位分配给不同的主节点，从而实现数据的分布式存储与灵活扩缩容。

Redis Cluster 将整个键空间划分为 16384 个虚拟哈希槽（编号 0~16383）。每个键通过 CRC16(key) % 16384 计算归属槽位，集群中的每个主节点负责维护其中一部分槽。

计算方式如下

也就是说，先对键名进行 CRC16 校验和计算，再对 16384 取模，得到的余数就是该键所在的槽编号。集群中的每个主节点负责维护一部分槽位，键最终就存储在那个拥有对应槽位的主节点上。

理论上 CRC16 能产生 65536 个值，但 Redis 作者选择了 16384（即 2^14），主要基于两点

  • 集群节点间需要定期发送心跳包，其中包含槽位分配信息的 bitmap。若槽数为 65536，消息头会达到约 8KB；而 16384 个槽时仅约 2KB，能显著节省带宽。
  • Redis Cluster 的主节点数量通常不建议超过 1000 个。在千节点规模下，16384 个槽已经足够精细地分配数据，没有必要使用更大的数字。

相比一致性哈希，哈希槽的设计让运维操作更加可控：

  • 扩缩容直观：新增节点时，只需从现有节点匀出一部分槽迁移给新节点；移除节点时，将该节点的槽全部迁走即可。槽的迁移粒度是固定的，管理起来很清晰。
  • 手动控制分布：如果某些节点的硬件配置更好，你可以手动给它们分配更多槽，而不像一致性哈希那样较难干预数据分布。

默认情况下，每个键独立计算槽位。但如果你需要让多个键落在同一个槽里，可以使用哈希标签。

如果键名中包含 {...}，Redis 只会用花括号内的内容来计算槽位。例如 {user:1000}.name 和 {user:1000}.surname 会落在同一个槽，因为哈希计算只针对 user:1000 进行。

槽的归属可以动态改变，迁移过程中客户端可能会遇到两种重定向：

  • ASK 重定向：发生在槽迁移进行中。如果客户端请求的键已经不在源节点，源节点会返回 ASK，告诉客户端 这个键可能已经迁到目标节点了，你去那边试一下，但暂时不要更新你本地的槽映射表。客户端需要先向目标节点发送 ASKING 命令，才能执行后续请求。
  • MOVED 重定向：表示槽的归属已经永久变更。客户端收到 MOVED 后，应更新本地的 槽-节点 映射缓存，后续该槽的请求直接发往新节点。

客户端路由

Redis Cluster 的客户端路由核心在于客户端本地缓存一份 槽-节点 映射表，并自行计算键的归属槽，直接向正确节点发起请求，从而避免每次请求都经过服务端转发。

这是一个具备集群感知能力的客户端，其典型路由流程如下：

  • 初始化拓扑：客户端启动时连接集群中任意一个节点，发送 CLUSTER SLOTS（或 CLUSTER NODES）命令，获取完整的哈希槽分配表及对应的主从节点地址，并在本地缓存这份映射。
  • 计算并直达：当需要操作某个键时，客户端在本地用 CRC16(key) mod 16384 算出槽号，查缓存映射表找到负责该槽的节点，直接向该节点发送命令。理想情况下，一次网络往返即可完成。
  • 处理重定向：当集群拓扑发生变化时，客户端缓存的映射可能过时。此时目标节点会返回重定向错误：
    • MOVED：表示槽的归属已永久变更。客户端收到后，应触发一次拓扑刷新，更新本地映射，并将请求发往新节点。
    • ASK：表示槽正在迁移中，键可能已临时转移到目标节点。客户端需先向目标节点发送 ASKING 命令，再执行原请求，但不应因此更新本地槽映射，因为没迁移完

这时候，务必使用支持集群模式的客户端，如 Jedis，并确保其具备本地槽缓存与重定向处理能力。

集群规模与防脑裂

防脑裂机制是防止在节点失联时因错误选举而产生双主节点。

Redis Cluster 的故障转移依赖多数主节点投票。因此，集群必须拥有至少 3 个主节点，官方推荐的最小生产规模是 3 主 + 3 从，共 6 个节点，以确保任一主节点故障时，剩余主节点仍能构成多数并完成故障转移。

而 Redis Cluster 的主节点数量通常建议控制在 1000 个以内。这主要受限于 Gossip 协议的心跳开销：节点数越多，集群总线上的状态交换消息量增长越快，网络与 CPU 负担相应加重。

脑裂（Split-Brain）指因网络分区导致集群分裂，出现两个独立运作的 主节点 子集，各自接受写入，最终造成数据冲突或丢失。Redis Cluster 通过以下机制防范：

  • 一个主节点被标记为 PFAIL（疑似下线）后，需要集群中多数主节点也同意将其标记为 FAIL，故障转移才会启动。选举新主节点时，同样需要获得多数主节点的投票。这意味着，被隔离在少数派分区中的主节点无法被替换，因为少数派凑不够票数来发起选举，从而避免了双主的产生。
  • Redis 提供了 min-replicas-to-write 与 min-replicas-max-lag 参数，用于在主节点层面进行最后一道防护。当主节点发现自己可连接的合格从节点数量不足，或从节点复制延迟过大时，会主动拒绝写入。这样，一个因网络分区而与所有从节点失联的旧主节点，即使仍在运行，也无法继续接受写请求，从而大幅降低脑裂导致数据分叉的风险。
  • 合理配置 cluster-node-timeout，该参数决定节点多久无响应后被标记为 PFAIL。
  • 将主从节点分散部署在不同的物理机、机架或可用区，避免单一物理故障同时影响一个主节点及其所有从节点，从物理层面降低脑裂发生的概率。

分布式带来的新约束

在 Cluster 中，所有涉及多个键的命令，都要求这些键必须落在同一个哈希槽内。如果客户端尝试操作分属不同槽的键，服务端会直接返回 CROSSSLOT 错误。

单机 Redis 里随意使用的多键命令和事务，在 Cluster 中会受到严格限制。这是实际开发中最容易踩坑的地方。

这一限制直接波及了开发中最常用的两个特性：

  • 事务（MULTI/EXEC）：事务内的所有命令涉及的键必须同槽，否则整个事务无法执行。同时，WATCH 命令也只能监视同一槽内的键，跨槽监视会导致乐观锁机制失效。
  • Lua 脚本：脚本中通过 KEYS 数组传入的所有键，也必须属于同一槽。此外，脚本内严禁使用动态生成的键名（必须用 KEYS[1] 这样的显式声明），否则会报错。

所以说，这里需要使用上面提到的哈希标签（Hash Tag）。在键名中加入 {...}，Redis 只会对花括号内的内容计算哈希。例如，将 user:1001:name 和 user:1001:age 改为 {user:1001}:name 和 {user:1001}:age，即可强制它们落入同一槽，从而支持事务或批量操作。但需警惕，过度使用可能引发数据倾斜

单机 Redis 支持通过 SELECT 命令切换 16 个逻辑数据库（0-15）。但在 Cluster 模式下，SELECT 命令被完全禁用，集群只支持数据库 0。这是因为在分布式分片架构下，维护多数据库的原子操作会带来不必要的复杂性。因此，依赖多数据库隔离业务的旧代码，在迁移到 Cluster 时必须改造，改用键名前缀等方式来区分不同业务的数据。

因此，许多在单机下能返回全局信息的命令，在 Cluster 中语义发生了变化，通常只作用于当前连接所在的单个节点

Cluster 下的 Pipeline 行为与单机不同。由于命令必须发往正确的节点，一个 Pipeline 批次通常只能针对同一个节点。如果客户端试图在一个 Pipeline 中混合发往不同节点或包含跨槽键的命令，现代客户端（如 Jedis）会直接抛出异常或拒绝执行。这要求开发者在构建批量操作时，需要先按“目标节点”或“哈希槽”对命令进行分组，再分别打包发送。

所以说，Redis Cluster 的分布式约束本质上是将 全局原子性 和 全局视图 的成本转移给了应用层**。在设计阶段就需要有意识地通过哈希标签规划键的分布，并避免依赖跨节点的多键事务与全局遍历命令。如果你的业务场景强依赖跨键的复杂原子操作或全局遍历，那么 Cluster 可能并非最优选，或者需要引入应用层的协调逻辑来弥补这些限制。

主节点故障时，客户端如何恢复

实验继续保持 Java API 进程运行，先为 sku-recovery 成功预占一件库存，再停止该 SKU 所在的主节点 7301。

本次新主节点为 7305，客户端约 5.58 秒恢复；恢复过程中记录到 4 次暂时失败，没有把故障切换描述为完全无中断。接口遇到 Redis 暂时不可用时返回 503，调用方保留原 requestId 重试。

用故障前的 requestId 再次调用，得到 DUPLICATE 和原来的 orderId，库存保持为 4；再用新的 requestId 下单，库存变为 3，订单总数为 2。整个过程中 Java API 没有重启。

实验在故障前通过同连接写入并执行 WAIT，确认这次演示数据已复制到副本；这不等于 Redis 在所有故障下都具备强一致性或零丢失保证。

业务代码没有按端口硬编码路由，而是把同 SKU 的原子操作留在同槽，由 Cluster 客户端处理不同 SKU 的分片访问。单个热门 SKU 仍然落在一个主节点上，Cluster 不会自动把这个 SKU 的一个库存键拆到多个节点。

这个案例是可运行的库存预占原型：订单预占记录暂存在 Redis，还没有支付、订单数据库、超时回补和幂等记录清理。真实项目需要结合业务数据库确认正式订单，并处理异步复制、超时重试与库存补偿。
