前言

前几篇讲的都是服务端的相关内容，包括怎么启动、怎么处理连接、怎么拆包、怎么设计协议。这一篇就涉及到客户端的相关内容，问题立刻变得不一样。

服务端关心的是 同时接住很多连接，客户端关心的是 这一条连接出现了问题该怎么办。网络抖动、服务端重启、DNS 变化、空闲超时、握手失败，这些在服务端只是某条连接的生命周期结束，在客户端却必须变成可恢复的状态。

本篇按客户端可靠性的顺序往下走：先用 Bootstrap 把连接建立起来，处理同步/异步与超时；再讨论心跳和空闲检测，判断连接是不是还活着；然后设计断线重连，包括退避、抖动、重新鉴权和会话恢复；最后落到两个常见的应用层协议，WebSocket 和 HTTP/HTTPS，以及连接池的基本概念。

客户端连接

Bootstrap 客户端

ServerBootstrap 和 Bootstrap 虽然都继承自 AbstractBootstrap，但设计目标完全不同。

服务端需要 接受连接 和 处理连接 两个阶段，所以必须有两个 EventLoopGroup，分别是 boss/worker。而客户端只作为发起方，只负责 建立连接并处理该连接上的 I/O，所以一个 EventLoopGroup 就够了。

所以说，服务端用 ServerBootstrap，客户端用 Bootstrap。两者的配置方式很像，差别在于客户端只需要一个 EventLoopGroup：

connect() 返回 ChannelFuture，ChannelFuture 继承自 Netty 的 Future<Void>，它同时承载两类信息

  • 连接操作的状态：连接失败时，cause() 里是失败原因；连接成功时，channel() 是可用的 Channel。
  • 关联的 Channel：即使连接失败，channel() 仍然返回一个非 null 的 Channel 对象

客户端的线程模型

一个 Channel 从生到死，所有入站事件都由同一条 EventLoop 线程驱动；出站操作可以从任意线程发起，但真正落地仍然回到那条 EventLoop 线程。

所以说，客户端和服务端用的是同一套 EventLoop / Pipeline 机制，只是角色不同。Bootstrap 的 EventLoopGroup 里通常有 1–2 个 EventLoop，客户端的所有 Channel 共享这几条线程：

  • connect() 可以由 main 线程调用，结果回到 EventLoop 线程；
    • Bootstrap.connect() 本身不阻塞。它做的事情是，创建 NioSocketChannel，将其注册到选出的 EventLoop，然后向该 EventLoop 提交一个连接任务。真正的 SocketChannel.connect() 系统调用是在 EventLoop 线程里执行的。
    • 因此：
      • 调用 connect() 的线程（通常是 main 线程或业务线程）拿到的是一个 ChannelFuture，立即返回。
      • 连接的实际发起和完成发生在 EventLoop 线程上。
      • 如果连接成功，channelActive 回调也在 EventLoop 线程上触发。
  • channelActive、channelRead、channelInactive 在 Channel 绑定的 EventLoop 线程执行；
  • 多个服务端连接如果落在同一个 EventLoop，一个连接的慢 Handler 会拖住其他连接；
    • 一条 EventLoop 线程上的所有 Channel 共享这条线程的时间片。所以说，EventLoop 应该永远不被阻塞，必须保持随时响应事件的能力
  • 重连时复用同一个 EventLoopGroup，不要每次重连都新建 group，否则线程会越积越多。

客户端 Handler 同样要遵守 Callback 不阻塞 的规则。鉴权、数据库查询、同步 HTTP 调用都要移出 EventLoop；客户端的心跳和重连状态更新本身很轻，可以直接在 EventLoop 里做，但是在哪里触发呢？

  • channelActive：连接成功，启动心跳定时器，状态置为“已连接”。
  • channelInactive：连接断开，取消心跳定时器

客户端只有一个 EventLoopGroup，里面每个 NioEventLoop 是一条线程。默认线程数是 CPU 核数 × 2，但客户端场景下这通常没有必要 。如果客户端只连接一个服务端节点，设置 1 条线程完全足够。

connect().sync() 与异步 connect

上面我们知道，connect() 是异步非阻塞的，main 线程调用后立即返回一个 ChannelFuture，真正的连接建立由 NIO 线程完成 。

连接超时与失败原因

CONNECT_TIMEOUT_MILLIS 控制连接超时。连接一个没有服务监听的端口，通常会很快收到 ConnectException: Connection refused；连接一个丢包地址，才会走到超时，得到 ConnectTimeoutException。

AsyncConnectDemo 把四种情况放在一起：同步成功、异步成功、连接未监听端口失败、PromiseCombiner 组合两个 Future。日志里能看到失败 cause 的类型，以及监听器所在的线程。

connect() 失败之后，Channel 可能已经注册到 EventLoop，但不会进入 active 状态。重连时不要复用这个失败的 Channel，因为这是一个死的 Channel，重新 connect() 生成一个新的。

Future 组合与超时控制

一个连接建立往往不是单个操作：先 connect，再鉴权，再发第一条请求。

如果每一步都用回调嵌套，代码会变成一层套一层的回调地狱，Netty 提供了 PromiseCombiner 把多个 Future 异步操作组合成一个

它的用法很简单，把想等的几个 Future 都加进去，最后给一个总的结果。所有步骤都成功，总结果才算成功；任何一个失败，总结果就失败。

  • PromiseCombiner 只负责等全部完成，它不管超时。如果连接卡住了或者鉴权迟迟没响应，它就会一直等下去。所以实际使用时需要自己加一个定时器，超时了主动把总结果标记为失败

更常见的做法是把鉴权也当成一条普通消息，在 channelActive 里发出去，然后等服务器回包。收到鉴权成功的回包后，再把连接状态标记为 可用，之后才允许发业务请求。

连接失败时，要记得关闭 Bootstrap 的 EventLoopGroup。客户端通常有一个独立的 group，如果进程不退出，group.shutdownGracefully() 要在关闭流程里调用，否则线程会一直挂着。

心跳与空闲检测

为什么需要应用层心跳

在 Netty 中，客户端和服务端通过 TCP 建立连接后，只要双方没有主动关闭连接，也没有检测到明确的网络异常，连接通常就会保持在 ESTABLISHED 状态。

虽然这很防御，但是 TCP 连接处于 ESTABLISHED，连接一定能够正常通信吗。很明显不行，原因很多。这些情况下，客户端可能并不会立即收到连接关闭通知，Channel.isActive() 也可能暂时仍然返回 true。

这是因为 TCP 是面向连接的协议，但它并不会持续主动验证应用程序是否具备处理消息的能力。因此，对于需要长期保持连接的系统，必须考虑如何及时发现已经不可用的连接。

TCP 本身提供 SO_KEEPALIVE 机制，在 Netty 中可以通过以下方式启用：

TCP KeepAlive 会在连接满足操作系统规定的空闲条件后，尝试通过 TCP 探测报文判断对端是否仍然能够响应。

但是有两个问题

  • 默认检测周期通常较长：例如，Linux 常见默认配置中，TCP KeepAlive 要在连接空闲约 2 小时后才开始探测。对于 RPC、即时通信或者设备长连接服务而言，这样的故障发现时间无法接受。
  • 它无法验证应用层的处理能力：TCP KeepAlive 的响应主要由操作系统 TCP 协议栈完成。因此即使服务端业务线程池已经耗尽、应用程序发生死锁，只要操作系统仍然可以正常处理 TCP 探测，连接就可能被认为是存活的。因此，应用层通常需要另外设计心跳机制。

最常见的心跳协议采用请求与应答模式

基本流程如下：

  1. 客户端在指定条件下向服务端发送 PING。
  2. 服务端收到 PING 后，返回对应的 PONG。
  3. 客户端收到有效的 PONG，说明本次心跳成功。
  4. 如果在规定时间内没有收到对应的 PONG，则记录一次心跳失败。
  5. 连续失败达到阈值时，客户端主动关闭旧连接，交给重连机制重新建立连接。

其中，PING 通常携带序列号 seq，服务端返回的 PONG 应包含相同的序列号，以便客户端区分不同心跳请求。

关键的是，心跳只能说明，所经过的处理链路在规定时间内能够响应，也就是说，心跳是保活，而不是保可用。因此，心跳检测和应用健康检查属于两个不同层次的机制。

IdleStateHandler 及其原理

Netty 提供 IdleStateHandler，用于监测一个 Channel 在指定时间内是否发生读写活动。它本身不负责发送 PING、验证 PONG，也不会在发生空闲时自动关闭连接。

它的主要职责可以概括为：记录读写活动 → 判断是否超过空闲阈值 → 触发 IdleStateEvent → 由其他 Handler 决定如何处理。

IdleStateHandler 继承 ChannelDuplexHandler，因此能够同时参与入站和出站处理。

如何利用 IdleStateHandler 实现基础心跳？

最基本的方案是由客户端主动探测，服务端被动响应。

  • 接收客户端发送的 PING。返回对应的 PONG。
  • 根据需要，来监控客户端是否长时间没有发送数据。

  • 服务端一直有数据推送，客户端的 readerIdle 不会触发；但 writerIdle 仍可能触发，因为客户端一直没写；
  • allIdle 只在读写都停的时候触发，适合完全没动静的检测；
  • 事件触发后不会自动关闭连接，关闭动作要业务 Handler 自己做。

因为 Netty 就是在现有任务运行时通过重新计算剩余时间来调整下一次调度，而 Netty 认为没有必要在每次读写事件中反复取消和创建任务。

所以说，整套机制应该这样理解：读写活动更新时间戳，定时任务负责计算剩余空闲时间并触发事件

Ping/Pong 的设计

应用层 PING/PONG 可以自己定义消息类型，也可以直接用 WebSocket 的 Ping/Pong 帧。关键是

  • PING 要有唯一序号或时间戳，PONG 原样带回，才能算 RTT 和判断是否丢包；
  • 连续 N 个周期没收到 PONG，才判定断线，不要一次超时就重连；
  • 心跳消息不要走业务线程池，轻量处理即可；
  • 心跳间隔要小于服务端/中间设备的空闲超时，否则连接会被中间层先断开。

而且，完善的心跳协议至少需要维护：

状态 作用
sequence 为每次 PING 分配唯一序号
pendingSequence 记录当前等待 PONG 的心跳请求
sentTime 记录 PING 发送时间，用于计算 RTT
pongTimeout 限制等待 PONG 的最长时间
consecutiveFailures 记录连续心跳失败次数
maxFailures 超过阈值后主动关闭连接
  • 心跳间隔 是多久尝试发送一次 PING。
  • 心跳响应超时是发送一次 PING 后，最多等待多久才认为本次探测失败。

相对明显的一个心跳状态机

  • 触发 WRITER_IDLE 时，如果没有等待中的心跳，发送新的 PING。
  • 发送成功后，启动对应的 PONG 等待任务。
  • 如果收到匹配序号的 PONG，取消等待任务，将连续失败次数清零。
  • 如果超时仍未收到对应 PONG，记录一次失败，进行下一轮心跳。
  • 连续失败达到阈值时，关闭当前 Channel。

这种方式既避免了 PING 无限积压，也能准确区分网络读写空闲与心跳响应失败。

HeartbeatDemo 用 IdleStateHandler 发 PING，服务端前两次回 PONG，之后静默；客户端的 ReadTimeoutHandler 在等待超时后关闭连接，日志能区分 writerIdle 发 PING、readerIdle 与 ReadTimeoutException。

连接状态机

在 Netty 中，客户端一般通过 Bootstrap.connect() 与服务端建立 TCP 连接

但 TCP 连接并不是永久有效的。在长连接运行过程中，不小心可能就断了，此时如果客户端没有实现重连机制，连接断开后就只能等待业务代码重新发起连接，或者重启客户端进程。因此，长期运行的 Netty 客户端通常需要具备断线重连的能力。

指数退避与抖动

固定间隔重连在服务端宕机时会造成重连风暴，这和我们 Redis 防御缓存雪崩是一个道理。

服务端发生故障后，所有客户端在几乎相同的时间断开连接。如果客户端全部采用当时重连，那这样服务端本来就处于故障状态，却还需要不断处理大量 TCP 连接请求，死了。这种大规模客户端同时重试所引起的负载冲击，通常称为重连风暴

选择上：

  • 已经在 Spring MVC/WebFlux 里、只需要业务级 WebSocket：Spring 的封装更省事；
  • 需要自定义握手、二进制协议、精细的线程/背压控制：Netty 更合适；

keep-alive

HTTP/1.1 默认 keep-alive：一个 TCP 连接可以连续发多个请求/响应。HttpServerCodec 和 HttpObjectAggregator 都支持这种复用；业务只需要正确设置 Content-Length 或 Transfer-Encoding: chunked。

HttpDemo 的 client 在同一个 Channel 上连续发 /hello、/、/missing 三个请求，日志里能看到三个响应复用同一条连接；server 端打印每个请求的 URI 和 keep-alive 状态。

响应头与连接关闭

HTTP/1.1 的 keep-alive 依赖两个头：

  • Content-Length：告诉对端响应体有多长，连接才能在不关闭的情况下知道响应结束；
  • Connection: close：明确告诉对端这次响应后关闭连接。

如果服务端返回 Content-Length，客户端会按长度读完当前响应，然后继续在同一连接上读下一个响应；如果返回 Transfer-Encoding: chunked，客户端按 chunk 边界读到 0 长度块结束。两种方式都不能省略，否则连接复用会错位。

FullHttpResponse 适合响应体不大、能一次性放进内存的场景。大文件、流式响应不要用 FullHttpResponse，改用 HttpResponse + HttpContent 分块写，并正确设置 Transfer-Encoding。

HTTP 客户端的请求关联

一个连接上连续发多个请求时，响应不一定按请求顺序回来（HTTP/1.1 有 pipelining，但 Netty 的 HttpClientCodec 默认不开启）。如果业务并发发请求，要靠请求 ID 或响应顺序来关联。HttpDemo 是串行发请求，顺序最简单；真实客户端通常每个请求带唯一 ID，或者一个连接同时只处理一个请求。

ALPN

ALPN 是 TLS 的扩展，用来在握手阶段协商应用层协议（HTTP/1.1、HTTP/2）。JDK 9+ 支持 ALPN，Netty 通过 ApplicationProtocolConfig 配置。SslHandler 握手完成后可以用 applicationProtocol() 读取协商结果。

只做 HTTPS 时 ALPN 可以省略；如果要上 HTTP/2，ALPN 是必需的，因为 HTTP/2 和 HTTP/1.1 共用同一个端口，必须先协商协议。

TLS 握手流程

HTTPS 建立连接比 HTTP 多几步：

  1. TCP 连接建立；
  2. 客户端发 ClientHello，带支持的 TLS 版本、加密套件、ALPN 协议列表；
  3. 服务端回 ServerHello、Certificate，选定 TLS 版本和套件；
  4. 客户端校验证书，生成会话密钥；
  5. 双方交换 Finished，握手完成；
  6. 之后 HTTP 数据都在 TLS 记录层里加密传输。

在 Netty 里，第 2–5 步由 SslHandler 完成。SslHandler 的 handshakeFuture() 完成才代表 TLS 可用，channelActive 不代表 TLS 已经握手成功。业务如果要在连接建立后立刻发 HTTP 请求，应该等 handshakeFuture()，而不是等 channelActive：

连接池

Netty 本身不提供开箱即用的 HTTP 连接池

连接池解决的问题是复用已经建立的连接，避免每次请求都 TCP 握手、TLS 握手。HTTP/1.1 的连接池通常是 每个请求独占一个连接，用完归还；HTTP/2 则支持在一条连接上多路复用多个请求，每个请求有独立的 stream id。

Netty 本身不提供开箱即用的 HTTP 连接池，需要自己维护可用 Channel 队列、请求与响应的关联、超时和健康检查。常见做法是：

  • 维护一组 Channel，请求时借出，响应完成后归还；
  • 用请求 ID 关联 response，避免响应串线；
  • 对空闲连接做心跳或定期探活；
  • 设置最大连接数、最大等待时间、连接最大生命周期。

连接池不是越大约好。连接数过多会占用文件描述符和服务端资源；连接复用又会带来“一个慢请求占住连接”的问题。HTTP/2 的多路复用缓解了后者，但也引入了 stream 级别的流控和头部阻塞问题。

连接池与 ChannelGroup 的区别

ChannelGroup 连接池
管理对象 已建立的连接 可复用的连接
核心操作 广播、批量关闭、统计 借出、归还、健康检查
生命周期 连接关闭自动移除 需要自己维护空闲/占用状态
适用 服务端在线连接、客户端多连接 HTTP 客户端、RPC 客户端

ChannelGroup 可以作为连接池的底层容器，但连接池还需要请求关联、超时、空闲回收这些逻辑。把两者混为一谈，最后往往会出现“响应串线”或“连接被重复借出”的问题。

连接池的代价

  • 连接复用意味着请求之间可能相互影响，一个慢请求会占住连接；
  • 空闲连接需要心跳或定期探活，否则拿到的是半死连接；
  • 服务端主动关闭连接时，客户端池子里可能还留着失效连接，首次使用会失败，需要重试；
  • 连接最大生命周期和最大空闲时间要配合服务端的 keep-alive 设置。

如果请求量不大、对延迟不敏感，短连接反而更简单。连接池不是默认选项，而是有明确复用收益时的优化。

把这一篇串起来

客户端可靠连接可以按下面的顺序落地：

  1. 用 Bootstrap 建立连接，CONNECT_TIMEOUT_MILLIS 必设；启动/测试可以用 sync()，业务用监听器；
  2. 连接成功后做鉴权、恢复会话、启动心跳；
  3. 用 IdleStateHandler 发 PING，用 ReadTimeoutHandler 兜底，连续多个周期失败才判定断线；
  4. 断线进入状态机，指数退避 + 抖动重连，避免重连风暴；
  5. 重连后重新鉴权、恢复会话，ChannelGroup 管理在线连接；
  6. 应用层协议选型：WebSocket 适合双向推送，HTTP 适合请求/响应，HTTPS 的 SslHandler 放最前面；
  7. 需要连接池时，先明确复用粒度和请求关联，再考虑 HTTP/2 多路复用。
